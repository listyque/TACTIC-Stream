# Perforce-like проекты: установка и приёмка

Новый режим принадлежит отдельному проекту `file_project`. Сервер одновременно
обслуживает Classic и файловые проекты. ТХ — рабочий клиент, ТС — просмотр и
администрирование. Шаблон `perforce_like` встроен в wheel сервера: отдельный дамп
БД не нужен. Смена типа существующего Classic-проекта не является установкой.

## Установка

1. Перед обновлением сохраните согласованную резервную копию системной БД, всех
   проектных БД, конфигурации и приватного файлового хранилища. Установите Python
   3.14 и wheel сервера: `python -m pip install "./tactic_stream-VERSION-py3-none-any.whl[postgres]"`
   для PostgreSQL; для SQLite уберите `[postgres]`. Новая установка: `python -m
   tactic_stream --data-dir PATH init`, пароль администратора вводится интерактивно.
   Обновление существующей: `python -m tactic_stream --data-dir PATH upgrade` с
   её собственным конфигом.
2. В Configuration ТС включите `files`, сохранив остальные службы:
   `services/enable=tactic|queue|files`. После Save явно остановите и запустите
   сервер в согласованное окно обслуживания. Save не перезапускает сервер.
   Проверьте реально работающий процесс `files` в monitor status: значение в
   XML само по себе не подтверждает исправность воркера. Он проверяет uploads,
   собирает draft и выполняет retention/GC.
3. Создайте **новый** проект через мастер, выбрав **Perforce-like file project**.
   Эквивалент через штатный API для авторизованного администратора с текущим
   проектом `admin`:

   ```python
   server.execute_cmd('tactic.command.ProjectTemplateInstallerCmd', {
       'template_code': 'perforce_like', 'project_code': 'files_demo',
       'project_title': 'Files Demo',
   })
   ```

   Используются штатные Command/CreateProjectCmd и установка схемы. Существующий
   код проекта не перезаписывается: повторное создание выдаёт ошибку.
4. В Workspace actions создайте depot, основной stream и workspace. Привяжите
   depot к существующему доступному для записи repository alias. Приватные blobs
   располагаются в соседней папке `NAME.file-projects`, вне публичного asset alias;
   depot без привязки использует `DATA/file-projects`. Выдайте сервисной учётной
   записи права на папки. Одной резервной копии БД недостаточно для восстановления
   содержимого файлов.
5. Настройте штатные права project/search-type и `file_depot` view/edit для нужных
   проектов и depot. Проверьте обычного пользователя: read-only не может писать,
   чужие pending changelists/tasks не становятся редактируемыми. Воркер повторно
   проверяет права владельца и не публикует его данные от имени admin.
6. Распакуйте **исходный runtime** ТХ в новую папку, установите закреплённые
   зависимости из `requirements.txt`, запустите `launch.py`/`launch.pyw`. Используйте
   существующий экран подключения и собственный preset: тикеты и settings не
   входят в поставку. Выберите новый проект, workspace и локальную папку; задайте
   mappings и исключения. Для независимых клиентов создавайте отдельные workspace.
   Classic-проект сохраняет свой Classic Commit Queue.
7. В Storage administration задайте квоты, параллельность и retention перед
   большим прогоном. По умолчанию квоты не ограничены, параллельность передачи —
   4, срок заброшенных uploads/tasks — 7 дней, reverted — 30 дней, shelves и
   опубликованная история хранятся постоянно. Начните с GC dry-run. GC сохраняет
   историю, shelves, Have и активные задачи; blobs вручную не удаляйте.

Apache должен проксировать `/file-project/`, сохранять Range и разрешать потоковые
тела минимум 64 МиБ. Метаданные ограничены 1000 записями/3 МиБ на запрос, блоки и
архивы — 64 МиБ. Для общей установки используйте PostgreSQL; SQLite последовательно
обрабатывает записи. Защита квот, ссылок и GC также использует блокировку политики
хранилища проекта: параллельная передача байтов не означает параллельный submit.
При конкуренции до получения блокировки политики сервер возвращает обозначенный
HTTP 503; SDK ограниченно повторяет тот же запрос метаданных с паузами. Воркер
сохраняет queued/running задачу при временной конкуренции. Произвольные 503,
ошибки триггеров, SHA или прав автоматически не повторяются.

## Работа и восстановление

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Reconcile | Явное сканирование показывает новые, изменённые и отсутствующие файлы относительно Have и сервера. SHA считается вне UI-потока. |
| Checkout | Обычный допускает нескольких владельцев; эксклюзивный запрещает другого владельца. Локальные файлы не перезаписываются. |
| Upload | Видны общий счётчик файлов/байтов и текущий путь. Upload готовит draft; Submit публикует весь changelist отдельно. |
| Shelve/unshelve | Shelf сохраняет неизменяемые байты и версии. Unshelve запускает пакетную интеграцию; конфликты разрешаются до Submit. |
| Ошибка submit | Права, триггеры и откат всего changelist сохранены. Части не публикуются. При потерянном ответе сначала проверьте серверное состояние. |
| Get latest | Закреплённый manifest → проверка SHA → сохранение локальных файлов → подтверждение Have. Изменённые/неотслеживаемые файлы защищены без явного force. |
| Stop waiting | Останавливает работу клиента, сохраняя серверную задачу, журнал и частичные байты для Resume. Это отдельное действие от отмены серверной задачи. |
| Cancel task | Отменяет staging и восстанавливает исходный pending draft. Опубликованные данные сохраняются. Большая интеграция отменяется несколькими чанками. |
| Потеря соединения | При необходимости войдите снова; сохраните workspace root и журнал upload, затем Resume. Потерянный ответ не требует новой задачи. |
| Рестарт воркера/сервера | Сохранённые задачи обнаруживаются заново. Повтор offset/manifest/seal/submit/Have не создаёт лишних версий. |
| Изменился локальный источник | Resume отвергает новый fingerprint. Отмените прежнюю задачу и начните новую передачу. |
| Ошибка квоты/SHA/прав | Показывается серверная ошибка, публикации нет. Исправьте причину, проверьте draft/task и явно повторите или отмените. |

Журналы upload лежат вне workspace. Для докачки сохраняйте их и временные
`.tactic-BLOB.part`. При выключенном `files` новый upload отказывает до выделения
серверной задачи; завершённую передачу всё ещё можно проверить/повторить. После
включения службы требуется явный рестарт. Временная неисправность включённого
воркера диагностируется через monitor и прогресс задачи, восстановление сохраняется.

## Проверки и границы готовности

Архивный upload читает до 1000 blob одним штатным Search-запросом. Блокировки
хранилища и changelist защищают от параллельных transfer и legacy upload.
У каждого файла сохраняются native-права редактирования, проверка SHA и
триггеры сохранения. Ошибка откатывает метаданные и новые байты всего пакета.
Помеченную конкуренцию серверной блокировки повторяем до 120 секунд на команду
или блок, с отображением ожидания и возможностью остановить его. Освобождение
lease при сбое upload тоже повторяет помеченную конкуренцию; при потере воркера
или сети остаётся восстановление по истечению lease. Ошибки прав, SHA и триггеров
сохраняют отказ и откат.

`tools/file_project_checks.py` проверяет SQLite; `--postgres` создаёт и удаляет
собственный PostgreSQL-контейнер. `tests/test_file_workspace_ui.py` выполняет
сценарии в настоящем Edge, `tests/test_handler_file_workspace_ui.py` — в offscreen
Qt. `test_monitor.Runtime.test_owned_file_worker_restart_and_real_transfer`
проверяет настоящий рестарт и остановку собственных процессов. Benchmark
`tools/file_transfer_benchmark.py` использует новые случайные байты и проверяет
HTTP upload/submit/download/Have. `tools/file_project_scale.py` проверяет записи
каталога, версий и Have; это не передача миллиона физических файлов.

В поставке `verification/` содержит переносимые проверки native API, передач и
monitor. После установки wheel: `python verification/tools/file_project_checks.py`;
`--postgres` использует отдельный Docker-контейнер. Для проверки воркера задайте
`PYTHONPATH=verification/tests` и выполните `python -m unittest
test_monitor.Runtime.test_claimed_upload_recovers_after_file_worker_process_death`.
Инъекция сбоя оставляет сохранённый lease на 60 секунд: восстановление ограничено
его сроком и не является мгновенным. Контрольные суммы файлов — в `manifest.json`;
протокол автоматических проверок не заменяет ручную приёмку.

На проверенных Python 3.14/PySide6 6.11.1 и 6.11.2 диагностика ResourceWarning
воспроизводит оставшийся `Property` при завершении интерпретатора даже с одним
свойством обычного QObject, без приложения/сети/потоков. Предупреждение не скрыто
и не считается успешной приёмкой освобождения ресурсов. Фикстуры при этом
останавливают собственные воркеры и удаляют свои окна.

Поставка содержит wheel сервера, исходный ТХ и протокол проверок. Это **не**
Windows EXE/Electron и не подтверждение production-приёмки. Физический миллион
файлов/терабайты, целевые сеть и диски, чистая целевая Windows и полная ручная
приёмка ТХ требуют отдельного прогона. Существующие release gates сохраняются;
offscreen и тест метаданных не заменяют эти проверки.

## Результаты sync в SDK

FileTransferClient.download возвращает state=complete после завершения. Изменённый
или неотслеживаемый локальный файл возвращает state=blocked,
reason=local_modified_or_untracked, path и прежний task ID без исключения и
перезаписи файла. Перед сообщением об успехе вызывающий код обязан проверить
state. Сохраните локальные изменения и продолжите прежнюю задачу после устранения
конфликта; force автоматически не включается. Неожиданные транспортные ошибки
и ошибки целостности по-прежнему вызывают исключения.

## API исторического sync

ТХ 0.6.0.34 / ТС 0.112.71 добавляют штатные `revision_snapshot` и
администраторский `revision_upgrade`. В новых проектах сразу есть индексы
публикаций по stream/state/revision/time и файловых версий по stream/path/number.
Старые проекты обновляются через штатный schema API и максимум 1000 SObjects
в возобновляемой транзакции. Права и триггеры сохраняются; ошибка триггера
откатывает метаданные и курсор вместе. Старые записи восстанавливают только
имеющуюся точность времени до секунды; новые публикации — до микросекунды.
Схема Classic не меняется.

SDK `download(workspace, root, ...)`, `sync_begin` и download `transfer_begin`
принимают один селектор: `file_revision`, `changelist`, `revision` или `at_date`.
`file_revision` — №N каждого файла, `changelist` — номер/код опубликованного
чейнджлиста, `revision` — счётчик публикаций стрима. `paths` задаёт до 1000
локальных путей, `prefix` с `/` на конце — рекурсивное поддерево,
`source_stream` / `source_depot` — mapped-корень. Mappings и исключения
сохраняются. Без часового пояса дата ISO трактуется как UTC; дата без времени
включает весь день UTC. Состояние на публикацию удаляет ранее полученные файлы,
отсутствующие в нём. Отсутствующая файловая ревизия оставляет путь и Have,
возвращая `missing_revisions` и пример `missing_path`.

`force=True` включается явно: повторно получает совпадающие с Have файлы,
восстанавливает изменённые/отсутствующие копии и разрешает выбранные удаления.
Сначала сохраните локальные правки. Заблокированная задача той же области
атомарно перезапускается для Force; другую область/корень/ревизию нужно завершить
или отменить. Для Force повторите область без старого SDK `task`; обычный resume
сохраняет task ID. Ожидаемый конфликт локальных правок возвращает `blocked`.
Архивы и ranged-download читают закреплённый manifest sync, Have подтверждается
после проверки и записи. Параллельная локальная запись всё ещё останавливает download.

Диалог загрузки работает в ТХ; ТС использует общий API просмотра, SDK и Help.
Тесты временных SQLite/HTTP/QML проектов не подтверждают физические миллионы
файлов/ТБ и PostgreSQL. Поддеревья без учёта регистра пока читают своё mapping
ограниченными страницами; отдельного индекса casefold-префиксов пока нет.

## Метаданные рекурсивного checkout

ТХ 0.6.0.35 / ТС 0.112.72 передают папки в штатный `checkout` через
`directories` (source-префиксы с `/`, либо `""` для всего стрима) и
`local_directories` (префиксы Workspace). `paths` сохраняет контракт файлов.
Всего допускается 1..1000 выбранных корней; потомки раскрываются на сервере.
Пересекающиеся выборки дедуплицируются по неизменяемому `base_root` чейнджлиста.
Исключённые / unmapped пути пропускаются; права владельца, read-only mappings
и ordinary/exclusive locks сохраняются.

Сервер обрабатывает порции до 1000 путей в одной штатной транзакции и сохраняет
чейнджлист с edit_revision один раз. Поздняя ошибка lock/триггера откатывает все
предыдущие порции, locks и страницы; после отката тот же request ID можно повторить.
После успеха возвращается сохранённый receipt. Поле результата `paths` содержит
число открытых файлов. Это операция с метаданными без передачи байтов и submit.
Для новых файлов Head сначала выполняйте rebase старого чейнджлиста. Classic не меняется.

Проверены 1105 потомков, пересекающиеся выборки, исключения/read-only, поздние
ошибки locks/триггеров, повтор и реальные Qt/Chromium drag/drop.
Миллионный checkout не подтверждён: операция пока остаётся одной потенциально
долгой транзакцией, а локальные папки могут фильтровать весь каталог страницами.
Прежний PySide6 ResourceWarning при завершении остаётся зарегистрированным.

## Поставка lifecycle в исходниках (ТС 0.112.75 / ТХ 0.6.0.37)

Обновите исходники сервера и ТХ вместе, перезапустите их существующие launcher и
перезагрузите веб-интерфейс. Новые команды требуют соответствующей версии сервера.
Автоматического перезапуска рабочих служб эта правка не делает. Details / Checked
Out By / Preview и серверное сравнение доступны в обоих клиентах; локальное
наблюдение, Reconcile, права файлов и внешнее сравнение — задачи ТХ. Classic
сохраняет прежнюю работу.

Новые preview/shelf/handoff/resolve/inspector/transfer-команды проходят через
штатные Command/Search/SObject и security. Замена shelf проверяет ревизию и
архивирует прежнее содержимое. Submit остаётся атомарным для всего чейнджлиста.
Передача владения пока использует одну транзакцию: для миллиона файлов нужна
отдельная проверка bulk-job. Старые pending-сводки обновляются страницами через
`index_change` перед submit.

Полный объём из 124 пунктов сохранён в
[FILE_WORKSPACE_UI_PLAN.md](FILE_WORKSPACE_UI_PLAN.md): приняты 29/35 требований
этапа 2. Остальные шесть открыты, включая полную проверку восстановления и
прогресса. Копии для внешнего viewer намеренно остаются в cache workspace;
неудачные копии удаляются. Запуск установленного viewer, рабочий PostgreSQL,
физические миллионы файлов/ТБ и пакетная поставка пока не подтверждены.

## Серверные пакеты и рабочий сценарий — 2026-10-13

В ТХ changelist создаётся через ПКМ на пустом месте Pending. Перетаскивание
файлов/папок из Depot открывает их mapped-копии для редактирования: отсутствующие
копии берутся из базовой ревизии changelist, существующие локальные байты
сохраняются. Двойной щелчок по pending-файлу запускает его редактор. Наблюдение
обновляет также файлы в раскрытом changelist. Перед Submit/Shelve изменённые
открытые файлы подготавливаются на сервере, затем показывается review. Посторонние
файлы workspace не добавляются. Правка после review или смена native edit revision
требует новой проверки. Отмена review может оставить подготовленные uploads;
публикация требует отдельного Submit. ТС сохраняет просмотр/администрирование.

Зафиксированная серверная выборка передаётся одной native-командой `bulk_begin`.
Она включает immutable root, prefix, фильтры и необязательный включительный
диапазон `start_path`/`end_path`. Команда принимает `selection`, `operation`,
`change`, `edit_revision`, устойчивый `request_id`; checkout — `mode`, перенос —
`target_change`/`target_edit_revision`. Доступны `checkout`, `move_files`,
`remove_files` (выбранный revert), `mark_delete` (удаление только при Submit).
Сервис files выполняет задачу на сервере. `bulk_status`, `bulk_tasks`, `bulk_items`,
`bulk_cancel` показывают состояние и управляют задачей; worker-команды приватны.

Native-операции идут чанками до 1000 путей внутри одной транзакции, сохраняя права,
checkout и триггеры. Поздняя ошибка/отмена откатывает все чанки. Обе стороны rename
должны попасть в выборку. Applying показывает обработку до COMMIT; это ещё не
публикация. Stop waiting сохраняет задачу, явный Cancel не ждёт write lock SQLite.
Потерянный ответ COMMIT сверяется с той же задачей. Пул ограничен; длинная атомарная
запись всё ещё сериализует записи проекта SQLite. Миллион путей одной такой
операцией пока не квалифицирован.

Mappings/исключения редактируются формой с native preview. Отмена возвращает
активные настройки workspace. Перед переключением видны pending и transfer/bulk
задачи: они остаются в прежнем workspace. ТХ проверяет абсолютный корень, папки,
символические ссылки и свободное место перед сохранением; будущий download не
получает гарантии зарезервированного места.

Свежий замер SQLite: **1 000 000 логических файлов**, по миллиону version/checkout
записей, **два маленьких физических payload-файла**. Создание: 1717,54 с; пик памяти:
73,64 МиБ; страницы начала/конца по 1000 файлов: 10,53/12,12 мс; Have ack 1000 путей:
26,89 мс. Новые 1000 staged-версий после этого каталога: **1717,19 мс**, финальный
Submit: **19,67 мс**. Общий порог подготовки/публикации менее секунды не достигнут.

Остановленное скачивание теперь фиксируется на сервере как `blocked`, в том числе при конфликте с локальной правкой и восстанавливаемой ошибке передачи. Повтор той же выборки продолжает её зафиксированную задачу. Запрос другого файла, папки или ревизии в том же workspace и локальном корне атомарно заменяет остановленную задачу, сохраняя локальные правки, частичные файлы и подтверждённый Have. Выполняющаяся загрузка и задача с другим локальным корнем автоматически не отменяются. ТС показывает остановленную задачу в Transfers и позволяет отменить её. Задачу, оставленную активной старым клиентом, аварийно завершённым процессом или полной потерей связи, может потребоваться отменить в Transfers перед сменой выборки.


Подсказки прав в меню берутся из штатного Security. Поле writable у depot/stream
и в stream_status означает текущее право записи в depot. Метаданные состояния
файла и чейнджлиста содержат depot_writable независимо от страницы каталога.
Поле file_states.writable по-прежнему означает доступность записи в mapping
workspace. Для редактирования нужны оба разрешения. Эти подсказки — кеш для
отображения; каждая запись повторно проверяет штатные права, ревизии и блокировки.

ТХ 0.6.0.47 / ТС 0.112.95: переключение workspace сохраняет прежние pending,

## Восстановление, новые представления и ограничение памяти

После прерванной операции на панели доступна **Продолжить прерванную операцию**.
Журналы привязаны к серверу, логину, проекту, workspace и локальному корню; тикетов
в них нет. Продолжение использует исходный выбор файлов и штатную задачу/receipt.
Если ответ успешного Submit потерян, читается уже опубликованный чейнджлист;
повторной публикации нет. Для ещё pending Submit снова открывается Review.
Сохраняй кэш workspace и журнал аплоада до завершения восстановления. Повтор
импорта из Explorer при восстановлении принимает только побайтово одинаковые
уже скопированные файлы и сохраняет остальные локальные правки.

Rename переносит локальные изменённые байты после успешной штатной операции на
сервере. **Resume local moves** завершает прерванный перенос по тому же receipt;
другой существующий файл назначения не переписывается. Reconcile обновляет
Local/Have/Head и счётчики локальных незалитых файлов/байтов по чейнджлистам.
После локального изменения или новой edit revision счётчик честно требует
Reconcile, вместо повторного обхода миллионов файлов на каждый клик.

Из **View** открываются Workspaces, Streams, Depots, просмотр хранилища и
**Stream Graph**. Списки постраничные; узлы и связи графа ограничены и привязаны
к текущим опубликованным heads. Связи ветвления/слияния содержат реальные
опубликованные чейнджлисты. При изменении heads обнови граф. Масштаб, вкладки,
колонки и сплиттеры сохраняются; глубокие папки и выбранные файлы вне первой
страницы восстанавливаются прямым поиском. В памяти удерживаются до 8192 строк
дерева, до 8000 файлов раскрытых чейнджлистов, до 1000 на чейнджлист и 128
курсоров страниц. Для освобождённой ветки раскрой её заново; полный запрос
продолжает выполняться на сервере.

Внизу видны этапы сканирования, манифеста, аплоада, проверки, подготовки,
скачивания и Submit. Скорость и ETA считаются по реально измеренной передаче
после достаточного интервала и сбрасываются между этапами. Последний чанк
подготовки проверяется чаще; весь миллионный job не опрашивается с этой частотой.
Ошибка показывает путь файла и общую причину в Log; детали сохраняются в Debug Log.

В ТС оставлены просмотр и администрирование. В браузерном файловом проекте нет
checkout, локальных правок, shelve, submit и массовой передачи. Обычные Search
tabs и административный просмотр управляемых записей сохраняются. Браузер не
пытается определять изменения файлов на компьютере пользователя.
