# Внутренняя структура: выражения в фильтрах Search

> Как native Search вычисляет значения фильтров, как API проверяет вложенный доступ и как пишущие выражения участвуют в Command. Исходные правила фильтров сохранены; полная совместимость Search/API ещё не подтверждена.

## От фильтра к запросу

`Search.add_op_filters()` принимает документ фильтров, который используют `query`, `get_all_children`, `query_snapshots` и поиск в `get_unique_sobject`. Включённый `fast_query` обращается к тому же пути запроса. Реализация находится в `pyasm/search/search.py`; отдельной модели запросов нет.

Выражение вычисляет значение до того, как Search передаёт его параметром сравнения с колонкой. Оно не подставляется как сырой SQL и не выполняется отдельно для каждой строки результата.

```python
from pyasm.search import Search

search = Search('cg/assets')
search.add_op_filters([
    ['code', "@GET(cg/assets['code','DEMO_ARM'].code)"],
])
objects = search.get_sobjects()

# Тот же фильтр через исходный XML-RPC клиент
objects = server.query('cg/assets', filters=[
    ['code', "@GET(cg/assets['code','DEMO_ARM'].code)"],
])
```

Проект определяется активным контекстом и полным search type. Полный тип может адресовать другой зарегистрированный проект, но его права проверяются отдельно. Вычисленные значения, включая кавычки и русский текст, остаются параметрами запроса.

## Исходные правила значений

| Фильтр | Поведение |
| --- | --- |
| `[колонка, значение]` | Строка, начинающаяся с `@`, переменной вроде `$LOGIN`, `{@…}` или `{$…}`, вычисляется через `Search.eval(single=True)` и используется для равенства. Остальные строки остаются литералами. |
| `[колонка, оператор, значение]` | Работает то же определение выражения. Оставшаяся строка в `{…}` также вычисляется, включая строку со скобками, возвращённую первым выражением. |
| Вычисление `single=True` | Из результата-списка берётся первое значение; это не фильтр принадлежности списку. |
| `[колонка, 'in', значение]` / `'not in'` | Вычисленная строка с разделителями `\|` или список задаёт значения принадлежности; исходное удаление пустых значений сохраняется. |
| Пустой результат `@GET` | Даёт `None`; фильтр равенства становится `IS NULL`. |
| Начальные `None` или `''` в трёхчастном фильтре | Фильтр пропускается до вычисления, как в исходнике. |
| `[колонка, 'between', начало, конец]` | Эта ветка диапазона из четырёх частей не раскрывает выражения в границах. |

Например, `[колонка, '{0}']` сохраняет строковый литерал, а `[колонка, '=', '{0}']` вычисляет шаблон в скобках. `@VAR` остаётся исходной пустой операцией: не присваивает переменную фильтра и не выполняет вложенные аргументы. Встроенные переменные вроде `$LOGIN` берутся из текущего запроса. Дополнительного аргумента `vars` у `add_op_filters` нет.

```python
filters = [
    ['code', 'in', "@JOIN(@GET(cg/assets['code','in','DEMO_ARM|DEMO_CAT_PROP'].code),'|')"],
]
objects = server.query('cg/assets', filters=filters)
```

Сортировка, страницы, маркеры групп и JSON-документы фильтров сохраняют существующее поведение. Сырой SQL в одноаргументном API-фильтре остаётся запрещён. Прямой вызов `add_filter()` в ядре передаёт литерал параметром и не запускает это раскрытие выражений.

## Права, кэш и записи

API использует одну область expression access policy для `eval()` и раскрытия фильтров. Она проверяет вложенные типы и пишущие методы и восстанавливает предыдущие callbacks после успеха или ошибки. Значение, закэшированное доверенным серверным Python, не позволяет читателю обойти проверку закрытых типов в API. Доступ к внешнему типу запроса не выдаёт права на вложенные login, ticket или объекты другого проекта.

Вызовы администратора `query`, включённого `fast_query`, `get_all_children` и `query_snapshots` выполняются в существующем `ApiClientCmd`, как и `eval`; `get_unique_sobject` уже использовал Command. Разрешённые пишущие выражения участвуют в исходной транзакции и журнале. Ошибка следующего фильтра откатывает предыдущие записи. Успешное пишущее выражение сохраняет изменения, поэтому запрос с выражениями не обязательно является только чтением.

Обычный пользователь может вычислять разрешённые читающие выражения. `@UPDATE` и `@PYTHON` по-прежнему требуют сохранённых прав администратора и активного Command. Sudo и подмена объекта пользователя в памяти не дают права выполнять скрипты. Прямой вызов ядра наследует контекст вызывающего кода; пишущие серверные скрипты должны выполняться через Command.

## Проверено и ограничения

С исходным runtime сравнены 30 сценариев: фильтры из двух/трёх частей, шаблоны, переменные, null, single/списки, принадлежность через `|`, группы, JSON, колонки с именем таблицы и значения с кавычками. Всего 30 целевых Windows тестов также проверяют неизменённый XML-RPC SDK, серверный Python, вложенные policies и их восстановление, настоящего пользователя без прав записи, успешную запись и откат, прежние DDL, joins и Workflow. PostgreSQL проверяет запросы, детей, снапшоты, поиск уникального объекта и откат записи в отдельной БД. Тесты: `tests/test_search_expression_filters.py` и `tests/test_expression_paths.py`.

Timestamp-фильтры с часами БД теперь поддержаны в пределах проверенного синтаксиса; кавычки, СУБД и ограничения описаны в [справке о timestamp-фильтрах](timestamp_filters.ru.md). Среди оставшихся ограничений Search — сложные автоматические SQL-выражения, неподдержанные joins/связи и методы старого UI palette. Блок не добавляет методов или сигнатур API и не включает все выражения и операции админки.
