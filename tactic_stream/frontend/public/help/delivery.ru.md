# Установка, обновление и приёмка

> TACTIC Stream запускается из checkout, установленного Python wheel или самостоятельного серверного комплекта. Portable-комплект Windows x64 собран; приёмка на чистой Windows VM ещё предстоит.

## Portable-комплект для Windows

Распакуйте весь комплект и запустите `TACTIC Stream.exe`. Electron, Python, SQLite и зависимости обычного Handler включены. Первый запуск открывает штатный запрос пароля администратора, затем запускает локальный сервер. Закрытие окна останавливает его backend. Данные и браузерное состояние находятся в `%APPDATA%\TACTIC Stream`, за пределами папки программы; `--data-dir` выбирает отдельный каталог данных. `Handler.cmd` запускает обычный Handler: укажите локальный адрес из окна Stream в server preset и выберите проект. Настройки Handler хранятся в `%APPDATA%\TACTIC Stream\handler` или `TACTIC_HANDLER_SETTINGS_DIR`. Удалённое подключение Handler не зависит от локального EXE.

Перед заменой комплекта закройте оба приложения и скопируйте весь каталог данных. Обновление распаковывайте в новую папку программы с прежним каталогом данных. Штатное обновление схемы выполняется до запуска сервера. EXE не подписан; приёмка на чистой Windows VM, миграция legacy и полное восстановление ещё предстоят.

## Что поддерживается

Нужен Python 3.14+. Реализованы SQLite и PostgreSQL; приёмка использует SQLite на Windows и PostgreSQL 18.6 в Linux Docker. MySQL пока остаётся целью, а не поддерживаемым runtime. PostgreSQL требует extra `postgres` и родной XML-ресурс базы; секрет можно задать через `password_file`. Смена vendor не переносит существующие данные.

Сервер импортирует упакованные `pyasm` и `tactic`; ему не нужны каталог эталонного `legacy` и запущенный ТХ. Неизменённый XML-RPC клиент ТХ используется для проверки совместимости. Repository Sync, S3 и desktop/DCC bridge исключены.

## Самостоятельный сервер PostgreSQL

Серверный комплект содержит образы Stream, Apache/Webmin и PostgreSQL, Compose, управление и контрольные суммы SHA-256. На хосте нужны Docker Compose и Python 3.10+; код и зависимости приложения работают внутри образов без checkout и Node.js. Из полного каталога комплекта выполните `python manage.py load`, `python manage.py init`, затем `python manage.py check`. Инициализация запросит новый пароль администратора и откажется заменять существующую БД.

Перед обновлением сохраните БД, repository, конфигурацию и секреты `.local`. Сохраните прежнее имя проекта Compose и порты, безопасно скопируйте существующий `.local` в новый комплект, затем выполните `load`, `update`, `check`. Инициализация не переносит SQLite-данные. Включённый `README.ru.md` описывает установку, постоянные тома, порты и ограничения восстановления. Перенос данных и полная приёмка GUI остаются отдельными условиями.

## Запуск на Windows

После установки описанных зависимостей в `tactic_stream/.venv` запустите `START_TACTIC_STREAM.bat`. Батник выполняет `init --if-needed`, `upgrade` и `serve --open-browser`. Первая установка просит задать пароль администратора; существующую настроенную системную базу не пересоздаёт. Явный `init` по-прежнему отказывается работать поверх существующих баз. Это работает и для PostgreSQL: наличие файла SQLite больше не определяет путь запуска.

`TACTIC_DATA_DIR` задаёт каталог данных, по умолчанию `data`. `TACTIC_CONFIG_PATH` выбирает явный XML; иначе используется конфигурация собственного каталога данных. Прежние overrides сервисов и портов сохраняются. Браузер открывает корень приложения после готовности workers. Проект и workspace восстанавливаются из состояния пользователя/браузера; батник не навязывает вкладку Projects. `/admin/` не является адресом интерфейса. Родные маршруты транспорта `/admin/...` остаются API endpoints.

## Обновление и рестарт

Перед обновлением сохраните резервную копию собственного каталога данных, repositories и всех зарегистрированных баз; PostgreSQL нужно резервировать инструментами сервера БД. Остановите экземпляр через Ctrl+C в launcher или `tactic-stream --data-dir <каталог> stop` с той же конфигурацией. `status` читает состояние родного monitor. Дождитесь остановки monitor и workers, затем замените пакет и frontend-ресурсы. Выполните `upgrade`, затем `serve`; батник делает это после условной инициализации.

Обновление схемы проходит по системной базе и зарегистрированным собственным проектным ресурсам. Повторное выполнение безопасно и не сбрасывает объекты, версии или preferences. Внешний проектный ресурс отвергается вместо молчаливой миграции. У тикетов, выбранного проекта, вкладок, именованных layout и browser state остаются прежние владельцы сохранения; переустановка кода не удаляет их. Локальное состояние браузера привязано к origin/profile: другой адрес или приватная сессия его не наследуют.

## Frontend и установленный пакет

Перед сборкой wheel выполните `npm ci` и `npm run build` в `frontend`. Vite пересоздаёт генерируемый output из текущих chunks и `frontend/public`, включая справку и лицензии. Старые chunks больше не накапливаются. Пересобирайте wheel в чистом Python build-каталоге: setuptools иначе может сохранить файлы прошлой поставки.

JavaScript разделён на читаемые файлы отдельных функций. Wheel содержит source map каждого текущего JS для отладки браузера. JS использует ETag и перепроверку; CSS/fonts с хешами могут храниться в кеше долго. После обновления перезагрузите открытые вкладки. Стабильные имена JS не обеспечивают бесшовное rolling update между разными версиями серверов.

## CG-приёмка и её границы

В предоставленном `cg.zip` шаблон называется `niki_friends` по manifest.xml; имя архива этого не меняет. Его можно загрузить через Управление шаблонами и выбрать в штатном мастере проекта. Приёмка создаёт отдельные временные проекты и не меняет рабочий `cg_test`.

Тестовый набор содержит 32 объекта, 13 явных задач, 47 заметок и 45 проверяемых связей: вложенные и общие ассеты, эпизоды и шоты, категории и общие текстуры. Родной workflow может создать дополнительные задачи. Повторное заполнение проверяет идемпотентность. В тестовых проектах выключены только импортированные Telegram callbacks с сохранением кода; другие родные triggers работают. Проверки snapshots сохраняют содержимое прошлых версий и обновляют latest versionless; процедура текущего ТХ запускается без изменения.

На Windows файловые сценарии используют copy там, где у процесса нет права создавать symbolic links. На Linux проверяется поведение линков из шаблона. Это не подтверждение symlink-привилегии для любой Windows. API ещё не завершён полностью: доступны 127 входных точек с описанными ограничениями вариантов; полная старая HTML-оболочка и два контракта production-слоя исключены, MySQL отложен; см. [Ядро и совместимость API](help://api_compatibility).

Все временные acceptance-серверы, workers, браузеры и контейнеры завершаются в cleanup. Рабочий сервер пользователя не становится тестовой fixture. Числа регрессии и свидетельства поставки записываются в план и release-отчёты; эта статья не заявляет проверку всех production-данных или физического телефона.
