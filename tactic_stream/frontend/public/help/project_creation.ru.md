# Настройки и создание проектов

> Настройки проектов и быстрое окно выбора показывают активные, архивные, шаблонные и встроенные
> проекты TACTIC. Карточки отображают категорию, тип, жизненный цикл, код, описание, серверный статус
> и квадратное web-превью из репозитория. Фильтры архивных, шаблонных и встроенных проектов выключены
> по умолчанию и общие для обоих представлений; контролы перестраиваются, не перекрывая список.

## Основные элементы

Выберите и активируйте существующий проект. Команда редактирования открывает нативное модальное окно
для изменения имени, категории, типа, описания, признака шаблона, состояния архива и превью.

В «Конфигурация → Проекты» кнопка «Деактивировать текущий проект» очищает активное рабочее
пространство, не выходя из аккаунта, не архивируя и не удаляя проект на сервере.
Чтобы вернуться к проекту, активируйте его снова.
«Создать архив шаблона» экспортирует выбранный доступный для редактирования проект родной
командой TACTIC; признак шаблона не требуется. Архив хранится на сервере и содержит структуру
и настройки, но не рабочие объекты, задачи и снапшоты. Кнопка находится рядом с редактированием
и созданием проекта, а не внутри мастера. В узком виде доступны иконки с подсказками.

Встроенные проекты TACTIC видимы, но доступны только для чтения. Новое превью подготавливается через
обычную очередь Commit Queue и не загружается из UI-потока.

«Выбрать изображение» подготавливает замену превью. «Отменить выбор изображения» возвращает прежнее
превью до сохранения.

Редактор проекта и мастер создания заполняют нижний край нативного окна без зазоров
в углах, в том числе при изменении размера.

## Как пользоваться

- Создание нового проекта открывает нативный многошаговый мастер.
- Четыре шага — параметры, изображение, шаблон и проверка. Мастер использует общие компоненты MD3:
  навигацию, сгруппированные строки настроек и кнопки действий. В узком окне панель шагов становится
  компактной; название шага доступно в подсказке его иконки.
- Нажмите на предыдущий шаг, чтобы вернуться к нему. Следующие шаги доступны после перехода
  кнопкой «Далее». Сводка показывает превью, название, код, описание, категорию и подписанные настройки проекта.
- Панель действий прилегает к нижнему краю при изменении размера окна; внешними углами управляет нативная рамка окна.
- Укажите название (до 100 символов) и уникальный код (до 30 латинских букв, цифр и подчёркиваний,
  не начиная с цифры). Коды архивных проектов тоже заняты.
  На первом шаге можно добавить описание и категорию; они сохраняются в созданном проекте.
- Необязательное изображение загружается при создании проекта; его чекин выполняет TACTIC.
- Выберите пустой проект, проект-шаблон сервера, установленный ZIP-архив или встроенный шаблон.
  Названия, заданные на сервере, не переводятся.
  Внутри карточки между списком, действиями с шаблонами и пояснением сохраняются одинаковые интервалы.
- На первом шаге доступны пространство имён Search Type, признаки шаблона и главного проекта
  для пустых проектов. Namespace задаёт префикс новых Search Type (например, studio/shot).
  Пустое поле использует код проекта; имя проекта не меняется. sthpw и prod зарезервированы.
  На шаге шаблона по умолчанию выбрано «Нет темы». Тема меняет только веб-интерфейс TACTIC,
  но не внешний вид TACTIC-Handler. Смена главного проекта может потребовать перезапуска TACTIC. При копировании
  шаблона используются его собственные настройки.
- Управление шаблонами устанавливает, скачивает и удаляет пакеты сервера. «Создать архив шаблона»
  в разделе проектов конфигурации сохраняет настройки выбранного проекта.
  Удаление пакета не удаляет созданные проекты.
- Кнопка «Создать проект» сохраняет и открывает проект. После создания список проектов обновляется.
- Создание выполняют родные команды TACTIC в фоновом потоке, без автоматических повторов.
  Если проект создан, но его параметры не сохранились или проект не открылся, повторная попытка завершит
  эти действия без создания дубликата. При ошибке самой
  команды создания проверьте серверную ошибку и обновите список перед новой попыткой:
  родные команды могут сохранить часть изменений до возникновения ошибки.

## Серверный файловый режим (0.112.44)

Встроенный шаблон **Perforce-like file project** создаёт особый проект file_project
через CreateProjectCmd. По умолчанию остаётся classic; автоматической конвертации
нет. Это серверный режим: отдельный файловый интерфейс ТХ/ТС пока не подключён.
Оба вида проектов работают на одном сервере.

Native-команда `tactic.command.file_project_cmd.FileProjectCmd` управляет depot,
stream, workspace/Have, pending changelists, обычным и эксклюзивным checkout,
неизменяемыми версиями файлов и uploads. Edit принимает до 1000 путей в чанке.
Submit проверяет исходную ревизию stream и атомарно меняет корень каталога и
changelist в проектной БД. Сохраняются native ACL, validation и синхронные триггеры.
Триггер, требующий другой БД либо отложенной транзакции, вызывает отказ и полный
откат submit. Подготовленные uploads остаются для повторной попытки. Classic
global-search и системные change_timestamps для новых файловых записей не создаются;
своя история хранится в проектной БД. Classic чекин и Undo/Redo сохраняют свой путь.

Каталог хранится неизменяемыми страницами до 256 элементов, кэш чтения — 64
страницы, запись — порциями до 16 страниц. Ветки разделяют исходный корень до
правок. Sync фиксирует опубликованный changelist и выдаёт до 1000 файлов в чанке.
После записи файлов локально sync_ack продвигает сохранённый прогресс и Have.
workspace_status и uploads восстанавливают активные задачи/offsets после реконнекта.
Права depot: категория file_depot с code/project, native уровни view/edit, плюс
соответствующие права SearchType, записей и колонок. Для черновиков, uploads и
workspace дополнительно проверяется владелец. Read-only depot позволяет создать
свой workspace и скачивать; изменение stream требует write доступа.

Binary HTTP использует X-Tactic-Ticket: /file-project/upload для сырых чанков до
4 MiB, /file-project/download с HTTP Range для больших файлов и
/file-project/sync-download для потокового tar текущего чанка небольших файлов.
Tar включает существующие файлы до 4 MiB каждый; большие скачиваются через Range,
удаления обрабатываются клиентом по sync_next. Целый архив в RAM не собирается.
Blobs приватны в data/file-projects, с каталогами по префиксу UUID; привязка к
публичным classic repository aliases пока не реализована.

Изолированный синтетический каталог миллиона записей на SQLite: публикация корня
около 16 мс, страница 1000 элементов — 10–11 мс. Отдельная выборка 1000 разных
физических файлов (суммарно 500 KiB): 0,98 с от уже загруженных bytes до submit,
без сети; весь путь descriptor/upload/edit/submit — 3,25 с. Пиковый working set
процесса для обеих выборок — около 69 MiB. Это не миллион реальных uploads,
version records, сетевой замер или проверка терабайтных передач. В выборке 0.112.44
PostgreSQL не проверялся; проверки 0.112.45 описаны ниже.
Merge/rebase, shelve, edit leases, mappings нескольких
depot, локальный reconcile и квоты/GC — следующие блоки. Пока любое изменение head
требует явного разрешения конфликта; глубокой постраничной истории ещё нет.
upload_finish делает один полный потоковый проход SHA-256 до блокировки записи,
затем повторно проверяет состояние перед сохранением; фоновый verifier ещё не
реализован.

## Проверка устойчивости файлового ядра (0.112.45)

На SQLite и временной PostgreSQL 18.6 проверены гонки checkout/submit двух
пользователей, одновременные повторы upload/edit/подтверждения Have, порядок
native callbacks, отзыв прав depot/колонок и полный откат после позднего триггера
или ошибки COMMIT. Собственные дочерние процессы аварийно завершаются посреди
upload/edit/submit и сразу после коммита: реконнект восстанавливает offsets,
потерянный ответ можно безопасно повторить.

Файловый откат выполняется до освобождения блокировок БД и обрезает данные до
подтверждённого offset. Отсутствующие подтверждённые байты вызывают отказ, вместо
заполнения нулями. После ошибки на этапе COMMIT байты сохраняются: БД уже могла
закоммитить результат. Нужно запросить uploads/status и повторить операцию.
Неизменяемые страницы каталога используют native вставку «если отсутствует» и
проверку содержимого: два workspace могут одновременно создать одну страницу Have.
Ожидание блокировки строки ограничено пятью секундами. Права каждой строки/колонки
и синхронные триггеры проходят через штатное ядро.

Принадлежность БД проверяется один раз при привязке атомарной транзакции; SObject
продолжает проверять собственные права. Существующие checkout обновляются
ограниченными native пакетами; настроенные callbacks сохраняют последовательный
порядок. На свежих выборках 10000 путей PostgreSQL: edit добавления 1000 путей
сократился с 9,35 до 1,97 с, edit 1000 существующих — с 20,36 до 5,95 с.
Сеть клиента и физическая передача файлов не входят в замер. Секундный SLA пока
не достигнут.

Изолированные проверки: `tools/file_project_checks.py`; с `--postgres` создаётся
и удаляется собственный Docker-контейнер. `tools/file_project_scale.py --files
1000000` вызывает настоящий файловый API и проверяет число сохранённых
version/checkout. Маленький payload используется совместно для проверки ёмкости
метаданных; это не замер миллиона физических uploads или TB IO. TH/TS интерфейсы,
фоновые проверки больших файлов, квоты/GC и merge остаются следующими блоками.
Развёртывание на рабочем сервере и сбой питания не проверялись.

Полный metadata прогон SQLite сохранил миллион version и миллион checkout:
submit корня — 17,39 мс, страница 1000 — 10–11 мс, пик процесса 68,69 MiB.
Прогон начался до последних ускорений ownership/checkout; создание всех записей
заняло 26 мин 7 с. Это проверка ёмкости метаданных, а не TB IO. Отдельная актуальная
выборка 1000 различных физических файлов (500 KiB суммарно): 0,95 с от загруженных
bytes до submit, без клиентской сети/GUI; с upload/fsync весь путь — 9,47 с.
Classic start/finish/abort journal этот API явно отклоняет; использовать
submit/revert файлового changelist.

### Changelist: редактирование, перенос, shelve и конфликты

Новые операции доступны только проектам `file_project` через штатный
`execute_cmd('tactic.command.file_project_cmd.FileProjectCmd', kwargs)`.
Создание Classic-проектов и классический чекин не меняются. Схема остаётся версии 1:
shelf — неизменяемая запись `change` со статусом `shelved`, содержимое changelist
хранится в отдельном постраничном каталоге. Shelve, перенос и unshelve используют
готовые blobs и не копируют содержимое файлов.

`change_files(change, edit_revision?, after?, prefix?, limit?)` возвращает открытые
пути, режим checkout, базовую и черновую версии; максимум 1000 путей на страницу.
Для следующих страниц передавать полученную edit revision, чтобы обнаружить
параллельную правку. `update_change` редактирует описание, до 4096 байт UTF-8.
`remove_files` убирает выбранные правки из changelist и освобождает checkout.
Удаление опубликованного файла — операция `edit` с `delete: true`.
`move_files` переносит до 1000 путей между собственными pending changelist одного
stream, сохраняя ordinary/exclusive checkout и загруженные данные. Нужны `change`,
`target_change`, `paths`, `edit_revision`, `target_edit_revision`, `request_id`.
Если путь уже открыт в назначении или у него другая базовая ревизия, весь перенос
отклоняется; сначала выполнить rebase.

`shelve(change, edit_revision, request_id)` создаёт неизменяемую контрольную копию;
исходный changelist после этого можно редактировать или revert. Повтор запроса
возвращает тот же shelf. `changes` включает собственные записи shelved. Другой
пользователь с правом чтения депо может по коду shelf читать `change_files`, `list`,
`read`, `history`, скачивать данные и выполнять unshelve в собственный changelist.
История shelf показывает только фактически опубликованные ревизии.

Начать с `rebase_begin(change, edit_revision, request_id)` или
`unshelve_begin(change, shelf, edit_revision, request_id)`. Для unshelve назначение
должно быть основано на текущем head и принадлежать тому же stream.
Ответ содержит `integration` и курсор `after`. Повторять
`integration_next(change, integration, edit_revision, after, request_id)` до
`complete`: один запрос обрабатывает максимум 1000 открытых путей, а не весь stream.
Во время операции видны прежний черновик и опубликованный head; изменения содержимого
заблокированы. Можно загружать blobs с результатом ручного merge. Состояние переживает
перезапуск: получить `status` и продолжить с сохранённого курсора.

Rebase сравнивает базу, мои правки и head для каждого открытого пути. Изменения
других файлов не требуют ручного разрешения; одинаковые данные и одинаковые удаления
объединяются. При unshelve в сравнении участвуют локальные правки назначения.
`conflicts(change, integration, edit_revision, after?, limit?)` показывает конфликты
страницами. `resolve` принимает ограниченный массив `resolutions` из
`{path, choice: 'ours'|'theirs'|'blob', blob?}`. Ours — черновик/shelf,
theirs — зафиксированный head/локальное назначение. Результат merge должен быть
готовым upload назначения. `read`/`transfer` поддерживают
`conflict_side: 'base'|'ours'|'theirs'` вместе с change/integration/edit revision.
У отсутствующей/удалённой стороны нет скачиваемых данных. Бинарный download
принимает эти поля и Range, а также `change` или `shelf`.

`integration_finish(change, integration, edit_revision, request_id)` требует
завершённые чанки, ноль конфликтов и неизменившийся зафиксированный head.
Он атомарно переключает весь черновик и его базу, увеличивая edit revision.
После этого `submit` атомарно публикует весь changelist. Если head изменился снова,
нужен новый rebase; частичной публикации нет. `integration_cancel` сохраняет исходный
черновик и освобождает новые checkout unshelve чанками по 1000. Пока `cancelling`
истинен, повторять с новым request ID; завершение увеличивает edit revision.
Все записи сохраняют штатные блокировки, права project/depot/row/column и синхронные
транзакционные триггеры. Ошибка триггера откатывает запрос целиком: корни каталогов,
ревизии, квитанции повторов и изменения checkout.

Новые изменения требуют стабильный `request_id`; новый чанк или другие данные —
новый ID. Checkout также поддерживает ID и проверку edit revision, сохраняя старые
вызовы; изменённый checkout увеличивает ревизию. У `edit` остаётся параметр `chunk`.
Старые pending changelist без рабочего каталога индексируются повторными
`index_change(change)` до `complete`. Однократная миграция ограничена чанками,
восстанавливает и правки, и пути только с checkout, сохраняет exclusive и пропускает
неизменившиеся поддеревья. Большой старый checkout-каталог потребует нескольких вызовов.

Проверки: `tools/file_project_checks.py`, с `--postgres` для собственной временной БД;
замеры: `tools/file_change_benchmark.py --catalog-files 10000`.
Интерфейсы changelist ТХ/ТС, автоматический merge текста и
терабайтные передачи — следующие блоки. Миллион путей в новых рабочих каталогах и
production-нагрузка этим блоком не измерялись.

### Файловые проекты: depot, mapped workspace и настоящие ветки

Новые операции вызываются через тот же `FileProjectCmd` только в файловых проектах.
Classic и его чекин сохраняют прежний контракт.

**Хранилища.** `create_depot(code, repository?)` и
`update_depot(depot, revision, repository?, title?)` связывают логический depot с
настроенным alias repository; менять depot может администратор. Произвольные
пути клиента и alias plugins не принимаются. Приватные байты хранятся в соседней
папке `<папка-repository>.file-projects`, вне всех публичных repository. Обычные
HTTP asset aliases закрывают этот namespace. Каждый новый upload фиксирует
физическое расположение: смена привязки влияет только на новые загрузки, старые
версии читаются из прежнего места. Без alias остаётся приватное хранилище data.
`depots`, `streams(depot?)`, `workspaces` используют keyset `after`, `limit <= 1000`
и штатные права. Workspace видит только владелец. `stream_status(stream)` возвращает
опубликованный snapshot, ревизию и агрегаты каталога.

**Mappings.** При создании workspace передать, например:

```json
[
  {"stream":"main","source":"...","target":"src/...","writable":true},
  {"stream":"main","source":"cache/...","exclude":true},
  {"stream":"shared","source":"...","target":"vendor/..."}
]
```

Stream могут принадлежать разным разрешённым depot. Пути относительные POSIX;
`*` работает внутри компонента, завершающее `...` — рекурсивно. Последовательность
wildcard в source/target должна совпадать; последнее подходящее правило source
побеждает. До 256 правил. Положительные назначения должны иметь разные буквальные
префиксы; пересекающиеся/overlay назначения явно запрещены. Imports по умолчанию
read-only; writable mapping дополнительно требует штатного права записи в depot.
Основной stream обязательно включён. `case_sensitive:false` использует case-folded
ключи Have и запрещает два существующих серверных файла с одним локальным путём.

`update_workspace(workspace, view_revision, request_id, stream?, mappings?,
local_root?, case_sensitive?)` требует завершить sync и pending changelist.
Смена только основного stream перенаправляет его правила, сохраняя imports.
Смена mappings сохраняет Have для последующей очистки; смена local root или политики
регистра очищает только Have, не локальные файлы. Changelist фиксирует view на момент
создания. `create_change` может выбрать другой writable mapped `stream`.
`switch_workspace(workspace, revision, request_id)` меняет выбранный workspace для
логина/проекта через compare-and-swap; `workspace_active` читает выбор. Чужой workspace
недоступен.

**Have и sync.** Создание workspace без mappings сохраняет прежний single-stream
sync. Mapped sync фиксирует опубликованные версии всех источников при старте и
обрабатывает до 1000 серверных записей за запрос, включая отфильтрованные. Пустой
чанк тоже надо подтверждать, чтобы продвинуть курсор. `sync_next` возвращает
`local_path`, `source_path`, `stream`, `version`, `published_change` и `_have` —
предыдущую локальную базу. Смена mappings выдаёт удаления ранее tracked путей;
неучтённых локальных файлов в этой очистке нет. Tar чанка малых файлов содержит
mapped локальные пути, большие файлы читаются защищённым download/Range.
После полного подтверждённого sync следующие полные sync пропускают неизменившиеся
поддеревья каталога и обрабатывают серверные различия. Частичный prefix и новая view
используют ограниченный обход. Отмена сохраняет уже подтверждённый Have, но не
создаёт checkpoint полного sync. `have(workspace, root?, after?, prefix?, limit?)`
показывает подтверждённые ревизии и защищает пагинацию от смены Have.
Клиент обязан проверять байты, защищать локальные правки по `_have` и подтверждать
целый чанк только после безопасной записи/удаления. Сервер не проверяет диск клиента.
Sync восстанавливается после рестарта; повторный/stale ack не продвигает Have дважды.

**Сверка локального содержимого.** `reconcile(workspace, files, view_revision?,
have_root?, heads?)` принимает до 1000 локальных описаний, суммарно 2 MiB:
`{path,size,sha256}` либо `{path,missing:true}` относительно workspace root.
Возвращает local clean/modified/added/missing/unmapped, server
current/newer/deleted/untracked, Have, серверный файл и writable. Между чанками
передавать полученные `heads` (stream → submitted change), `have_root`, `view_revision`
для стабильного сравнения; накапливать heads для новых stream. Права проверяются
в каждом запросе. Хеширование/инвентаризация выполняются клиентом; сервер не читает
`local_root`. Экраны ТХ/ТС подключаются отдельным следующим блоком.

**Ветки и merge.** `create_stream(..., parent)` фиксирует настоящий submitted change
родителя и разделяет его immutable каталог и байты без копирования всех файлов и
фиктивных ревизий. `merge_begin(change, source_stream, edit_revision, request_id,
source_change?)` требует актуальную базу назначения, общего предка и один depot.
Далее используется устойчивый протокол `integration_next`, `conflicts`, `resolve`,
`integration_finish`, затем `submit`. Здесь `ours` — входящий источник, `theirs` —
назначение с его pending правками. Сравнение SHA/size идёт от настоящей общей базы;
результат связан с предыдущей ревизией назначения и `integrated_from` версией/change
источника. Поддержаны удаления и binary/custom merged payload. Источник остаётся
зафиксированным при новых submit, а смена head назначения запрещает finish/submit.
Последний интегрированный root источника меняется только при успешном атомарном
submit, поэтому повторный merge берёт новые изменения. Remove/move файлов и правка
контента консервативно очищают pending merge checkpoint: исключённые изменения
доступны следующему merge. Старые ветки без проверенной базы требуют административный
`stream_ancestry(stream,parent_change,baseline_change)`, совпадающий с реальными
submitted snapshot; база не угадывается. Автоматический текстовый merge и merge
между разными depot не реализованы.

Запись только через штатные Search/SObject/Command с правами project/depot/row/column
и синхронными триггерами. Ошибка откатывает запрос вместе с receipts; submit публикует
целый changelist атомарно. Предыдущие успешные чанки интеграции остаются приватной
заготовкой, которую можно продолжить или отменить.

Проверки: `tests/test_file_workspace.py`, native SQLite/PostgreSQL через
`tools/file_project_checks.py --postgres`. Замер `tools/file_project_benchmark.py
--files 1000000 --checkin-files 0` проверяет синтетические catalog/Have и sparse sync;
это не миллион физических ревизий, скачивание или терабайтный throughput.


## Массовая передача, докачка и политика хранения

Для файловых проектов добавлен отдельный pipeline. В Configuration → Server →
Services and workers включите «Массовая передача файлов» (`services/enable=tactic|files`
либо `tactic|queue|files`) и перезапустите сервер. Процесс `files` под монитором
проверяет uploads, выполняет staging и GC; standalone ASGI использует ту же опцию.
Classic остаётся на прежнем чекине. Интерфейсы ТХ/ТС для этого режима — следующий блок.

Метаданные сохраняются штатными FileProjectCmd/Search/SObject/Command, с правами
проекта/depot/строк/колонок, синхронными hooks и откатом. Каждый шаг worker заново
авторизует владельца: отзыв прав останавливает публикацию. Сервис записывает ошибку,
но не публикует от имени администратора. Промежуточные чанки — приватный staging;
весь changelist появляется только после успешного атомарного submit.

`transfer_begin(change,request_id,submit,expected_files?,expected_bytes?)` создаёт
upload. Ожидаемые объёмы дают общий прогресс до окончания manifests.
`transfer_manifest(task,request_id,files)` принимает 1..1000 `{path,size,sha256?}`
в пределах 2 MiB, резервирует квоты и возвращает blob ID. Повтор receipt идемпотентен.
`transfer_next(task,after)` постранично выдаёт manifest и подтверждённые offsets.
`transfer_digests(task,items)` принимает до 1000 пар blob/checksum. `transfer_seal`
требует весь заявленный набор и отправляет его на фоновую проверку и пакетный staging.
`transfer_status`, `transfer_tasks(after,limit)` и `transfer_cancel` показывают общие
счётчики файлов/байтов, проверенных и подготовленных файлов, текущий путь и ошибки.
Worker-операции недоступны обычным credentials.

`/file-project/command` направляет JSON в native API (лимит транспорта 3 MiB).
PUT `/file-project/transfer-upload?project&task&blob&offset` принимает поток до 64 MiB
с Content-Length, fsync, подтверждённым offset и блокировкой writer на уровне ОС.
Во время приёма большого тела транзакция БД не удерживается. Defaults: 4 byte-writer
на проект (настройка 1–16), также лимит 4 на веб-воркер. `batch=1` принимает строгий
USTAR до 1000 завершённых файлов в пределах 64 MiB с hooks и атомарным откатом
файлов/метаданных. После обрыва следующий writer обрезает неподтверждённый хвост.
`/file-project/manifest` отдаёт страницу NDJSON. Размеры/offsets — signed 64-bit;
байты передаются без XML-RPC/base64.

`transfer_begin(kind='download',workspace,client_root)` фиксирует sync/view и
возобновляет активную задачу этого workspace для того же локального корня.
`transfer_next` выдаёт до 1000 записей и Have; `transfer_ack(task,ack_revision,paths)`
двигает Have после локального сохранения всего чанка. `/file-project/sync-download`
отдаёт малые файлы tar-потоком. POST `{sync,ack_revision,paths}` скачивает только
подмножество pinned-плана после обрыва/потери ack. Большие файлы скачиваются через
`/file-project/download` с Range и фиксированным published_change. Mappings,
исключения, imports и source/local paths сохраняются. Для filtered/incremental
загрузки итоговый объём неизвестен до конца обхода; общий подтверждённый счётчик
работает сразу, без предварительного пересчёта всего каталога.

`tactic_client_lib.file_transfer.FileTransferClient` реализует передачу: локальный
SQLite-журнал (сервер сохраняет всё native API), ограниченные окна, tar прямо из
исходных файлов, параллельность и SHA-256. Журнал нужен для докачки той же задачи;
другому набору нужен новый журнал. Download сохраняет частичные большие файлы,
проверяет SHA-256, вызывает fsync и атомарно заменяет итоговые файлы. Локальные
изменения, неучтённые файлы и symlink/небезопасные пути блокируются; явный `force=True`
разрешает overwrite. Прогресс содержит totals, подтверждённые счётчики, текущий путь
и продвижение блока/файла. Callback может идти из transfer-thread: GUI должен
переносить его события в UI-thread. После обрыва клиент перечитывает префикс для SHA;
worker после рестарта перечитывает текущий большой файл, сохраняя ранее проверенные.

Для старого проекта администратор выполняет `storage_upgrade`, затем ограниченные
шаги `storage_index` до indexed: чтение доступно, allocations ждут окончания.
Новые проекты получают индексы сразу. `storage_status` показывает usage;
`storage_policy(revision,policy)` меняет правила через CAS. Лимиты байтов/файлов 0 —
без ограничения. Размер резервируется до allocation, квота освобождается после
физического GC. Defaults: idle uploads — 7 дней, terminal tasks — 7 дней, reverted
черновики — 30 дней, shelves — бессрочно, quarantine grace — сутки. Submitted history,
workspace, приватные черновики и живые download-ссылки защищены; pending changelist
не откатывается автоматически. `gc_interval_seconds=86400` — GC раз в сутки;
0 отключает расписание. `gc_begin(dry_run=True)` показывает кандидатов, false создаёт
native mark/sweep, quarantine и повторяемое удаление, включая старые upload-spool.
Retired blob нельзя вернуть в ready. Отсутствующая ссылка останавливает GC;
изменение корней повторяет marking до дальнейшего sweep. **Ограничение:** непрерывные
правки могут откладывать GC; для завершения при постоянной записи нужен write barrier.

Проверки: `tests/test_file_transfer.py`, перезапуск/остановка своего worker в
`tests/test_monitor.py`, PostgreSQL-контракты и новые случайные HTTP-наборы в
`tools/file_transfer_benchmark.py`. Миллион записей проверен только как каталог/Have;
физическая передача миллиона файлов и терабайт пока не измерена.

## Рабочий интерфейс ТХ и администрирование в браузере

В мастере проекта выберите **Perforce-like file project**. Режим принадлежит проекту (`file_project`); один сервер одновременно обслуживает Classic и файловые проекты. В ТХ открывается отдельный рабочий интерфейс, в ТС — просмотр и администрирование. Смена типа существующего Classic-проекта не переносит его данные.

ТХ поддерживает дерево changelists по состояниям, выбор файлов, обычный/эксклюзивный checkout и владельцев блокировок, описание, перенос/удаление из списка, полки, историю реальных версий, локальное SHA-сравнение, Have, Get latest, uploads с дисковым журналом и продолжением, явную подготовку удалений и разрешение конфликтов с вручную объединённым файлом. Сравнение запускается явно; постоянного файлового watcher и автоматического текстового merge пока нет.

ТС показывает depot/stream/workspace и mappings, содержимое списков, депо и Have по страницам, владельцев checkout, историю, полки и конфликты. Доступны серверные операции над changelist и разрешение конфликтов выбором нашей/их версии. Работа с локальными папками и массовые передачи выполняются в ТХ. Наблюдение за передачами получает одну ограниченную страницу задач, без запроса на каждый файл. Задачи ограничены текущим логином.

Администрирование хранилища содержит квоты байтов/файлов, параллелизм передач, сроки хранения в секундах, защитный период и интервал GC. Нулевая квота снимает ограничение; нулевой срок полок сохраняет их; нулевой интервал GC отключает плановые запуски. Политика сохраняется с проверкой ревизии. Пробный GC показывает кандидатов без удаления байтов; безопасный GC ставит штатную защищённую задачу очистки с заданными retention/grace. Обновите состояние GC для счётчиков. Нужен работающий сервис `files`.

При активном upload сервер блокирует редактирование и submit. Отмена или ошибка возвращает весь исходный черновик после частичной подготовки; завершённый upload оставляет файлы подготовленными до отдельной публикации. Публикация использует штатную Command-транзакцию, ACL и триггеры: сохраняется всё или откатывается всё. Прекращение ожидания клиентом сохраняет серверную задачу для продолжения.

Не более 200 файлов на странице и 1000 в manifest. SHA и байтовое IO выполняются вне UI-потока ТХ, с дисковыми caches и ограниченными буферами. Сейчас история ограничена последними 1000 опубликованными версиями, текстовый предпросмотр — 256 КиБ. ТХ сохраняет выбранную неизменяемую версию с проверкой SHA. Миллионы физических файлов и терабайты передачи через GUI пока не измерялись.

Ориентир: [списки изменений P4V](https://help.perforce.com/helix-core/server-apps/p4v/current/Content/P4V/files.submit.html), [полки](https://help.perforce.com/helix-core/server-apps/p4v/current/Content/P4V/files.shelve.html).

В обоих клиентах используются компактные общие панели, контекстные команды и нижние вкладки истории, конфликтов и передач. В **Действиях с рабочим пространством** находятся настройки и администрирование хранилища, в **Действиях со списком изменений** — описание, shelves, merge и revert, в **Действиях с файлами** и контекстном меню строки — checkout, перенос и удаление. Настройки и описание открываются отдельными диалогами. Разделители меняют размеры дерева и деталей; в узком окне дерево открывается по кнопке.

## Восстановление передачи

При выключенном `files` новый upload отказывает до выделения серверной задачи. Включите службу в Configuration ТС и явно перезапустите сервер: Save не делает рестарт. Проверьте исправность воркера в monitor status. После обрыва сохраняйте журнал upload и тот же workspace root для Resume. Stop waiting сохраняет задачу; Cancel server task восстанавливает исходный pending draft. При потерянном ответе Submit/Have сначала проверьте/повторите ту же задачу, не создавайте новую передачу. Изменившийся источник требует отмены и новой передачи.

Инструкция установки и резервного копирования — `FILE_PROJECT_DELIVERY.ru.md`; создавайте новый проект из встроенного `perforce_like`. Базы и приватные blobs резервируются вместе. Поставка исходников/wheel и offscreen-тесты не подтверждают физический миллион файлов/терабайты или установку Windows EXE/Electron.

Временная конкуренция до получения блокировки политики обозначается `file_project_busy`: запросы метаданных ограниченно повторяются с паузами, серверная задача сохраняет queued/running. Произвольные HTTP-ошибки, сбои триггеров, прав и SHA не повторяются. После падения воркера восстановление может ждать его сохранённый lease на 60 секунд. Python 3.14/PySide6 выдаёт Property ResourceWarning при завершении даже минимальной программы с одним свойством; это отмечено как нерешённый вопрос приёмки runtime.

Архивный upload читает до 1000 blob одним штатным Search-запросом под блокировками хранилища и changelist. Права каждого файла, SHA, триггеры и откат всего пакета сохраняются.

Слева находится дерево depot, справа, в основной рабочей области — чейнджлисты с номерами и раскрываемыми файлами. Стрелка раскрывает depot, stream, папку или чейнджлист. Дочерние узлы загружаются страницами; «Загрузить ещё» продолжает только выбранную ветку. Выбор папки переключает рабочую область на файлы depot; «Файлы чейнджлиста» возвращает чейнджлисты. Каждый чейнджлист показывает номер в проекте, описание, владельца и состояние; его файлы можно выделять для команд. Перенос файлов и unshelve принимают номер чейнджлиста проекта, например #42. При выборе чейнджлиста фильтр папки depot сбрасывается. «Обновить» загружает текущую опубликованную версию.

В файловых проектах доступны обычные вкладки поиска объектов Search. Служебные файловые таблицы читаются через штатный файловый API; администратор может просматривать их схему и число записей в Search Types. Интерфейс Perforce-like открывается в доке Commit Queue. Его можно объединять в стек с Search, перемещать или выносить штатными средствами докинга. «Развернуть панель» занимает всю рабочую область; восстановление возвращает раскладку без перезаписи сохранённых пропорций. Восстановленный из кэша проект выбирает файловый интерфейс до обновления с сервера.

## Черновик и безопасность шаблонов

Четыре общих шага сохраняют черновик при возврате назад. Изменённый черновик требует подтверждения закрытия; выполняющуюся операцию закрыть нельзя. Если результат создания неизвестен, сначала обновите каталог. Если код уже существует, повторяется только открытие проекта. Перед скачиванием ZIP или удалением выберите шаблон в менеджере; удаление открывает отдельное блокирующее подтверждение. Установка ZIP и выбор изображения используют диалог файлов своего клиента.
