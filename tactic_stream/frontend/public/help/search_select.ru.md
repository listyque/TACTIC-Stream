# Внутренняя структура: Search и его Select

> Search и объект из get_select() теперь строят один запрос. Привязанные фильтры, права, связи, копии и пагинация сохраняются при переключении между исходными интерфейсами.

## Один запрос, два исходных интерфейса

`Search` разрешает зарегистрированный тип, проект, ресурс БД и класс SObject. `Select` хранит SQL-проекцию, группировку, сортировку и пагинацию. Объект из `search.get_select()` принадлежит этому Search и не может незаметно отбросить его фильтры.

```python
from pyasm.search import Search

search = Search('cg/assets')
search.add_filter('pipeline_code', 'asset')
select = search.get_select()
select.add_filter('name', 'Robot')
select.set_limit(20)
select.set_offset(0)
objects = search.get_sobjects()
```

Используйте реально зарегистрированные тип, колонки и код pipeline. Обычные значения фильтра остаются привязанными параметрами БД. Апострофы или SQL-текст в значении не превращаются в исполняемый SQL.

Search и его Select используют общие упорядоченные списки WHERE и JOIN. Поэтому postfix-операторы `begin` / `and` / `or` сохраняют порядок смешанных вызовов. Пагинация обоих интерфейсов меняет один Select; действует последнее присваивание. Offset без limit по исходным правилам не включает пагинацию. Обычное чтение сохраняет фильтры retired, класса и безопасности.

## Прямое выполнение и счётчики

```python
search = Search('cg/assets')
search.add_filter('name', 'Robot')
select = search.get_select()
select.add_column('code')
select.set_limit(1)

statement = select.get_statement()
assert statement == search.get_statement()
rows = select.execute(search.get_sql())
total = search.get_count()
```

Прямое выполнение Select возвращает SQL-кортежи; `get_sobjects()` создаёт SObject. Существующая сериализация XML-RPC превращает кортежи в массивы. Для обычных запросов строк счётчики Search и Select игнорируют пагинацию. Существующий native-счётчик Select с группировкой/distinct использует подзапрос; базовый счётчик Search продолжает считать подходящие исходные строки. Для агрегатных проекций эти режимы могут иметь разный смысл.

Select выполняется на ресурсе своего Search. Передача Sql другого проекта отклоняется; замена базовых таблиц или всего запроса через `set_statement()` тоже запрещена. Отдельный `Select()` сохраняет собственный контракт доверенного SQL-конструктора.

Результаты объектов сохраняют исходный кэш Search. После изменения уже выполненного запроса используйте `get_sobjects(redo=True)` для повторного чтения.

## Копии, удаление фильтров и SQL-текст

`search.copy()` и `search.get_select().copy()` создают отдельные фильтры, параметры, связи и пагинацию. Новый фильтр копии не меняет оригинал. Копия Search заново проверяет права текущего пользователя, а не наследует разрешение прежнего администратора. Пустой/запрещённый Search даёт пустой прямой Select; в исходном ядре прямой Select ошибочно позволял читать его строки.

`get_wheres()` показывает native-условия, включая маркеры параметров вместо исходных встроенных значений. Для удаления сгенерированного условия передайте именно это условие в `remove_where()`; соответствующие параметры удалятся вместе с ним. Прямое изменение списка условий без синхронизации параметров отклоняется при компиляции или выполнении. Это не формат сериализации.

При формировании SQL маркеры распознаются вне строк, идентификаторов, комментариев и PostgreSQL dollar quotes. Буквальные `?` и `%s` остаются текстом. Привязанное выполнение PostgreSQL также экранирует буквальный процент для psycopg: при чтении объектов, кодов, id, счётчиков и связанных запросов.

## Права и прямые JOIN

Типизированные фильтры Select используют проверку метаданных и параметры Search. `add_where()`, некавыченные SQL-значения, SQL-проекции и прямые JOIN сохраняют существующую проверку аутентифицированного администратора/серверного скрипта. Общий native-коннектор Sql также требует активного администратора; читатель использует разрешённое чтение Search/API. Копирование запрещённого запроса не открывает доступ заново.

Прямые JOIN внутри одного ресурса используют исходный конструктор Select и добавляют метаданные присоединённых колонок в Search. Schema JOIN продолжают использовать настроенные связи. Прямые JOIN между ресурсами пока не поддерживаются. Направления связей описаны в [справке о connect](connections.ru.md), права выражений и транзакции — в [справке о фильтрах](search_filters.ru.md).

Быстрые списки code/ID основного типа при существующей проекции или JOIN
получайте через `Search.get_sobject_codes()` / `get_sobject_ids()`. Извлекается
фактический ключ базовой таблицы вместо первого выбранного значения.
Aliases, дубликаты JOIN и пагинация сохраняются; подробности и ограничения —
в [справке о модели ядра](core_model.ru.md).

## Сохранение и восстановление Select

```python
search = Search('cg/assets')
search.add_filter('name', 'Robot')
select = search.get_select()
select.add_column('code', as_column='asset_code')
select.set_limit(20)
state = select.dumps()

receiver = Search('cg/assets')
receiver.get_select().loads(state)
receiver.add_filter('name', 'Robot')
rows = receiver.get_select().execute()
```

`dumps()` возвращает исходную структуру JSON Select: таблицы, колонки и aliases, упорядоченные WHERE/JOIN, группировку/HAVING, сортировку, distinct и страницу. Привязанные значения экранируются в сохраняемых SQL-условиях; текст, похожий на маркеры параметров, остаётся текстом. Действующие ограничения null/retired тоже сохраняются. JSON содержит значения запроса, но не подключение, пароль, владельца Search или разрешения доступа.

`loads()` восстанавливает состояние принимающего Select, сохраняя его Search, проект, ресурс БД и подключение. Права текущего Search проверяются заново, ограничения получателя остаются, метаданные связанных колонок восстанавливаются даже для старого экспорта без `join_tables`. Новые типизированные фильтры снова используют привязанные параметры. Успешная загрузка сбрасывает кэш SObject; невалидная не меняет прежний запрос и параметры. Ошибка внутри серверного Python также откатывает предшествующие записи через обычную транзакцию Command.

Загрузка SQL-условий в owned Select требует контекста аутентифицированного администратора/скрипта. Читатель не получает доступ к raw SQL через сохранённое состояние. Замена базовой таблицы, чужая БД/схема, replacement statement, словари raw-фильтров, непривязанные параметры и неподдерживаемый синтаксис JOIN отклоняются. Неизвестные поля владельца/подключения/разрешений в JSON не меняют получателя. Это состояние запроса, а не перенос прав или автоматический перевод SQL между СУБД.

Исходный экспорт ошибочно записывал aliases в `columns`; загрузчик читал другое поле и незаметно возвращал полные строки. Native-экспорт сохраняет настоящие колонки и aliases. Исходный экспорт без проекции читается; повреждённая исходная проекция с потерянными именами колонок отклоняется без догадок.

## Проверки и оставшиеся ограничения

31 сценарий выполнен на реальном неизменённом исходном ядре и native SQLite: смешанные фильтры, вложенные группы, списки/null/boolean, кавычки, прямой SQL, пагинация/счётчики, JOIN и копии. Пустая область и наследование retired имеют независимые source/native ожидания: прямое owned-выполнение сохраняет ограничения Search, которые исходный прямой Select пропускал. Проверки Windows также охватывают исходный XML-RPC SDK, откат предшествующей записи, права читателя, удаление параметров, исходные сигнатуры и существующие контракты запросов/безопасности. Изолированная PostgreSQL проверяет смешанные фильтры, буквальный процент/маркеры, прямые JOIN, копии, чтение объектов/кодов/id, счётчики и пустую область.

Ещё 16 сценариев сериализации выполняются на неизменённом исходном ядре и native SQLite, с отдельными ожиданиями потери проекции и обходов области в исходнике. Native-проверки охватывают атомарность невалидной загрузки, кэш объектов, aggregate/distinct/quote mode, отказ читателю и откат через исходный XML-RPC SDK. Изолированная PostgreSQL проверяет aliases, JOIN без экспортированных метаданных, буквальный процент/маркеры, новые привязанные фильтры и откат после невалидной загрузки.

Замена SQL/базовых таблиц, сырые словари фильтров, прямые JOIN между ресурсами, полная совместимость PostgreSQL `DISTINCT ON` и MySQL ещё не завершены. Это не означает полной совместимости API или админки. Синтаксис часов БД и кавычки описаны в [справке о timestamp](timestamp_filters.ru.md).

С версии 0.112.7 native self-instance запросы задают отдельные SQL aliases таблицы линков и источника. Owned Select dumps/loads сохраняют aliases и проверенные колонки таблиц, включая одновременные parent/child условия. Определения концов и оставшиеся контракты записи описаны в [справке о связях одного типа](help:core_model).
