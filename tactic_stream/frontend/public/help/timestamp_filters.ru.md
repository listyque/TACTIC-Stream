# Внутренняя структура: timestamp-фильтры с часами БД

> Динамические timestamp-значения в native Search, SQL конкретной СУБД и исходные правила кавычек API. Время вычисляет база; значение фильтра не выполняется как произвольный SQL.

## Где вычисляется время

`Search.add_filter()` определяет тип колонки, запрашивает проверенное timestamp-выражение у её `DatabaseImpl` и включает его в запрос. База вычисляет выражение при выполнении SQL. Stream не подменяет его временем Python-сервера в момент создания фильтра.

```python
from pyasm.search import Search

search = Search('cg/assets')
search.add_filter('timestamp', 'NOW', op='<')
objects = search.get_sobjects()

# Переносимый исходный интерфейс арифметики часов конкретной СУБД
search = Search('cg/assets')
cutoff = search.get_database_impl().get_timestamp_now(offset=1, type='day', op='-')
search.add_filter('timestamp', cutoff, op='<')
objects = search.get_sobjects()
```

У выбранного типа должна существовать timestamp-колонка. Поддержаны объявленные типы `timestamp`, `datetime` и `datetime2`. Слово `NOW` в текстовой колонке не становится выражением времени.

## Значения и СУБД

| Значение | SQLite | PostgreSQL |
| --- | --- | --- |
| `NOW`, включая нижний и смешанный регистр | `CURRENT_TIMESTAMP` базы | `now()` базы |
| `CURRENT_TIMESTAMP` в любом регистре | Текущее время базы | Текущее время базы |
| `DATETIME(...)` | Без аргументов либо с литералами строк/чисел/NULL и модификаторами SQLite | Отказ: это синтаксис SQLite. |
| `now()` и сгенерированные интервалы | Используйте переносимый интерфейс `get_timestamp_now`. | Поддержаны `now()` и формы `now() + '0.5 day'::interval` / вычитания. |
| `CURRENT_TIMESTAMP(0)` — `(6)` | Отказ | Поддержана точность часов СУБД. |

Например, SQLite принимает `DATETIME('now','-1 day')`, `DATETIME('now','start of day')` и `DATETIME(0,'unixepoch')`. Строковые аргументы используют одинарные SQL-кавычки и удвоенные апострофы для экранирования. Вложенный SQL, идентификаторы и дополнительные команды не принимаются как автоматические timestamp-выражения. Если корректный вызов модификатора SQLite возвращает SQL NULL, сохраняется этот результат базы; текущее время вместо него не подставляется.

SQLite нормализует колонку и динамический результат через существующую функцию `spt_timestamp`. Одинаковые моменты с разными UTC-смещениями сравниваются как равные; сохранённые микросекунды остаются значимыми. У `DATETIME` SQLite сохраняется собственное поведение точности: Stream не придумывает отброшенные функцией дробные разряды. PostgreSQL сохраняет native семантику timestamp и часов транзакции. Часы обеих СУБД не являются временем на телефоне пользователя.

Дневные колонки вроде `due_date` сохраняют прежнее поведение календарной даты. Токен часов всё равно включает время и не превращается в полночь автоматически. Четырёхчастный date-helper `between` требует настоящих разбираемых дат, убирает время и включает конечный день. Он не принимает `NOW` как границу даты.

## Исходные правила кавычек API

```python
# Исходный XML-RPC SDK: специальный NOW работает с оператором сравнения
objects = server.query('cg/assets', filters=[['timestamp', '<', 'NOW']])
```

Трёхчастные API-фильтры используют значения в кавычках. `NOW` — исходное исключение, отменяющее кавычки. `CURRENT_TIMESTAMP` и `DATETIME(...)` в таком же фильтре остаются строковыми литералами. SQLite может сравнивать их как текст, а PostgreSQL — отвергнуть как неправильное timestamp-значение. Эти результаты не означают вычисление часов.

Прямой Search с `quoted=None` или `False` разрешает поддержанные выражения времени. Явный `quoted=True` сохраняет `CURRENT_TIMESTAMP` и `DATETIME(...)` литералами; `NOW` сохраняет своё специальное исходное поведение. Двухчастные API-фильтры используют кавычки по умолчанию и поэтому могут распознать динамическое значение, но их оператор — равенство.

Для сравнения с оператором и сгенерированным смещением используйте разрешённый серверный Python и исходные `Search` / `get_timestamp_now`, как в примере выше. Новых параметров и методов XML-RPC это не добавляет.

## Валидация, права и транзакции

Native helper `DatabaseImpl.get_timestamp_filter` проверяет поддержанный синтаксис часов. Его использует и `process_value`, поэтому автоматические timestamp-значения при подготовке native Select/Insert/Update проходят общую проверку. SQL-подстановки после функции, подзапросы и дополнительные команды отклоняются. Явный сырой SQL в доверенных SQL-конструкторах остаётся отдельным существующим контрактом; произвольный SQL через значения API-фильтров этим не включается.

Права на search type, проект и методы API сохраняются. Настоящий пользователь без прав записи может применять разрешённый фильтр часов без права запуска скриптов. `@UPDATE` / `@PYTHON` в других выражениях фильтров сохраняют требования администратора и Command. Отказ timestamp-значения откатывает предыдущие записи в том же Command.

SQLite `process_value('timestamp', None, 'timestamp')` теперь сохраняет nullable-значение без кавычек вместо вызова `startswith` у `None`. Неправильное числовое timestamp-значение в этом processor даёт понятный `TypeError` вместо исходного `AttributeError`; числовые time-аргументы SQLite должны находиться внутри поддержанного `DATETIME(...)`.

## Проверено и ограничения

С фактическим исходным runtime сравнены 42 сценария при одинаковых часах, установленных только на приватных тестовых соединениях SQLite. Ошибки исходника имеют отдельные ожидания: преобразование NOW с учётом регистра, колонки с именем таблицы, сравнение UTC-смещений, небезопасные SQL-префиксы, nullable/неправильные значения processor и `now()` в кавычках у исходного PostgreSQL processor. Последнее — сравнение processor, а не заявление о запуске исходного PostgreSQL-сервера.

31 Windows тест проверяет неизменённый XML-RPC SDK, серверный Python, настоящего читателя, null/retired-строки, смещения часов, точность timestamp, SQL-конструкторы, запись/откат в фильтрах и жизненный цикл tickets. Настоящий отдельный PostgreSQL проверяет часы, интервалы, точность, native Select и откат. Тесты: `tests/test_dynamic_timestamp_filters.py`, `tests/test_datetime_filters.py`, `tests/test_statements.py` и `tests/test_expression_paths.py`.

Сложные автоматические SQL-выражения ещё не завершены. Поддержанные фильтры, JOIN, пагинация и копии Select/Search, а также оставшиеся ограничения сериализации/замены запроса описаны в [справке Search/Select](search_select.ru.md). Это не полная совместимость API и всех СУБД; MySQL не входит в эти проверки.
