# Внутренняя структура: объекты и выражения

> Как TACTIC Stream связывает типы, объекты, поля, контекст запроса и выражения. Эта справка пополняется по мере переноса ядра. Проверенные механизмы описаны отдельно от оставшихся ограничений.

## Путь вызова

Запрос клиента проходит через HTTP/XML-RPC обработчик, `ApiXMLRPC.dispatch`, контекст проекта и пользователя, затем соответствующий метод ядра. Серверный Python работает с теми же классами `pyasm`/`tactic`, что и API. В рабочем сервере нет импорта исходного `legacy` или Handler.

Для операций записи используется `Command.execute_cmd`: команда связывает изменения с транзакцией, журналом и триггерами. Создание Python-объекта и изменение его полей ещё не означают запись в БД. Ошибка команды должна откатить уже выполненные записи; файловые операции используют также свой журнал отмены.

## SearchType, Search и SObject

| Понятие | Для чего нужно | Где находится реализация |
| --- | --- | --- |
| `SearchType` | Метаданные типа: таблица, класс, namespace, база данных, поля. Обычные типы зарегистрированы в `sthpw/search_object`. | `pyasm/search/search.py` |
| `Search` | Поиск объектов с фильтрами, связями, сортировкой и проверками доступа. | `pyasm/search/search.py` |
| `SObject` | Один объект: значения полей, ожидающие сохранения изменения, сериализация, commit/delete. Ассеты, задачи и заметки используют эту общую основу. | `pyasm/search/search.py` |
| `Project` | Активный проект и разрешение полного типа и ресурса БД. | `pyasm/biz/project.py` |
| `DbResource` / `Sql` | Выбор подключения и SQL-диалекта; отделены от предметной модели. | `pyasm/search/sql.py` |
| `SearchKey` | Адрес объекта, например `cg/assets?project=cg_test&code=DEMO_ARM`. | `pyasm/search/keys.py` |

У SObject есть прочитанные значения (`data`) и ожидающие сохранения изменения (`update_data`). `get_value()` учитывает изменения; `get_data()` по умолчанию возвращает объединённые данные. `set_value()` проверяет значение и права на колонку, но не сохраняет объект. Для постоянного объекта запись выполняет `commit()` внутри штатного контекста команды.

`get_sobject_dict()` добавляет `__search_key__` и `__search_type__`. API дополнительно приводит значения к транспортному формату. Python-объект внутри ядра и словарь, полученный клиентом, — разные формы одного результата.

## Запись проектных объектов и права обычного пользователя

С версии 0.112.9 обычный пользователь может создавать, изменять и удалять
**проектные типы** (вне `sthpw/` и `config/`) и их instance-линки через
существующие SObject, Command и XML-RPC API. Это не даёт права менять системные
определения, выполнять файловые операции или произвольный серверный Python/SQL.

| Проверка | Требование |
| --- | --- |
| Пользователь и транзакция | Авторизованный пользователь запроса, активный native Command, зарегистрированный ресурс проекта. |
| Проект | Подходящее правило `project` должно давать `allow`. |
| Тип | `insert` для создания, `edit` для изменения, `delete` для удаления; без правила — отказ. Уровни накопительные, как в AccessManager. |
| Поля | `sobject_column` использует фактический проект объекта; отложенные поля проверяются ещё раз при commit. |
| Существующая строка | Свежий Search должен видеть её при текущих правах и фильтрах; объект из кеша не обходит изменённое правило. |

Например, группа с такими правилами может менять существующие ассеты в
`cg_test`, но не создавать и не удалять их:

```xml
<rules>
  <rule group="project" code="cg_test" access="allow"/>
  <rule group="search_type" code="cg/assets" project="cg_test" access="edit"/>
</rules>
```

`insert` добавляет создание, `delete`/`allow` — удаление. Типу instance-линка
нужно собственное правило: право на ассет не разрешает создавать запись
связи. Исходный `handle_commit_security()` ограничивал только custom scripts;
проверки колонок могли позволить пользователю с view/edit создать строку без
пишущего права типа/проекта. Stream намеренно закрывает эти пробелы;
17 сценариев настоящего исходного runtime имеют отдельные native ожидания.

`ApiXMLRPC.check_method_access` допускает обычные CRUD и add/remove instance;
правами владеет SObject. `Sql._do_security_dml` записывает проверенный объект
параметризованным SQL на SQLite/PostgreSQL. SQLite разрешает одну таблицу
только на время этого statement и восстанавливает авторизацию в `finally`;
произвольный SQL/DDL не наследует разрешение. Обычные native SQLite подключения
вне активного Command остаются закрытыми. Полный native SQL API не объявлен готовым.

Commit/delete сохраняют триггеры, XML транзакции, логи объектов/change timestamps
и обновление поискового индекса. Интегральный индекс использует ограниченный
native `Sudo`, восстанавливаемый и при ошибке; прямо менять его обычный
пользователь не может. Новая запись очищает только собственный redo, с
проверкой пользователя и типа в конечном SQL. Удаление есть в XML транзакции;
как в исходнике, при индексации SObjectLog оно пропускается. Ошибка триггера
и поздний отказ массовой операции откатывают объект, индекс и журнал.

Проверены неизменённый SDK по настоящему XML-RPC от обычного пользователя,
отказы типа/полей/проекта, смена прав после staging, фильтры текущих строк,
запрет raw SQL, сохранённые журнал/индекс/redo, существующие аккаунты/сообщения
и изолированные SQLite/PostgreSQL. Шаблон cg также проходит на временных данных.
Остальные системные/конфигурационные и файловые записи и права отдельных путей Workflow скриптов
требуют отдельного переноса. Задачи/история статусов, эффекты Workflow
и постоянная диагностика описаны ниже.
Полный API не проверен; правило проекта не обходит эти ограничения.

## Задачи и история статусов

С 0.112.11 обычный пользователь может создавать, менять и удалять `sthpw/task`
через native SObject/Command и существующие объектные методы API; `create_task`
использует тот же путь. Логический проект берётся из `project_code` задачи,
даже когда текущий запрос открыт в другом проекте. Нужны project `allow`, права
операции типа задачи (`insert`, `edit`, `delete`), видимость текущей строки и
правила колонок. Отложенные поля и фактические bound-поля SQL проверяются повторно.

Задача должна ссылаться на видимого редактируемого родителя **проектного типа**
в своём проекте. Сохранённые `search_code` и `search_id`, если заданы, обязаны
указывать на этого родителя. Обычный пользователь пока не может менять
`project_code`, `search_type`, `search_code` и `search_id` существующей задачи:
перенос зависимостей не завершён, возвращается `UnsupportedContract`. Задачи
проекта/системного родителя сохраняют административный путь. Эти права не
открывают определения, произвольный SQL, серверный Python, `add_initial_tasks`
и другие защищённые методы API.

`StatusLog.create(sobject, value, prev_value=None)` сохраняет исходную сигнатуру
и штатные поля связи. `StatusLogTrigger` пишет изменённые непустые статусы задачи,
включая начальный; повтор статуса ничего не добавляет. `Task.create` использует
триггер либо исходную ручную историю при отключённых триггерах, без дубля
начальной записи. У задачи API без заданного статуса начальной истории нет.
Журнал содержит ссылку на источник, аутентифицированный login, предыдущий/новый
статус, проект источника, timestamp и штатный сгенерированный code. Исправлена
ошибка оригинала: история задачи другого проекта сохраняет проект задачи,
а не текущего запроса.

Перед созданием истории права источника проверяются повторно. `StatusLog:writing`
временно указывает на **один SObject истории**, разрешая вставку и присваивание
сгенерированного code. Общие guard/binder проверяют пользователя, строку,
системный ресурс и операцию; область восстанавливается в `finally`, включая
ошибку commit. Общих Sudo/admin прав нет. Прямое изменение/удаление истории
обычным пользователем и raw SQL остаются закрыты.

История входит в транзакцию вызывающей команды. `actual_end_date` завершённой
задачи, её история и журналы откатываются при поздней ошибке триггера, массовой
операции или журнала. Это отличается от постоянной диагностики с независимой
командой. 

Проверены настоящее исходное ядро (с отдельным ожиданием исправленного проекта
истории), неизменённый SDK по HTTP XML-RPC и одинаковый сценарий в изолированных
SQLite/PostgreSQL: завершение/повтор статуса, отказы типа/проекта/родителя/поля,
отозванные staged-права и конечный SQL, подмена связей, защита истории/raw SQL,
откат ошибок массовой операции/триггера/журнала и очистка области разрешения.

Принудительная вставка с заданным ID проверяется как вставка, а не изменение
отсутствующей строки; исходный импорт плагина/шаблона сохраняет её идентификатор.
Изменение/удаление существующих строк по-прежнему проверяет свежие read-policy.


## Эффекты Workflow и обычный пользователь

С 0.112.12 исходный декларативный Workflow допускает смену статуса задачи
обычным пользователем и `call_pipeline_event(search_key, process, event, data={})`.
Родитель должен быть видимым редактируемым проектным объектом. Заново проверяются
права проекта, типа, текущей строки и колонок; задачи сохраняют собственные ACL.
Альтернативный pipeline должен принадлежать тому же проекту/типу либо быть общим.
Цели hierarchy/dependency проходят те же проверки родителя и графа.
Сохранены native validation, регистрация транзакции и блокировка состояния.

`Workflow:writing` временно указывает **один SObject эффекта и его родителя**.
Общие SObject guard и SQL binder разрешают его insert/update/присвоение кода,
проверяют код/ID/тип родителя, фактическую проектную базу, текущего автора,
неизменность владельца существующей строки, свежую read-policy и итоговые ACL
колонок. Общих прав администратора/Sudo или доступа к таблицам/SQL это не даёт.
`Workflow:message_source` связывает штатный messaging helper с ключом родителя
`skey|process|status` либо `skey|process|state`. `Workflow:note_source` разрешает
только исходную автоматическую заметку `process/error` при revise-событии.
Каждый scope восстанавливается в `finally`, в том числе при ошибке кода или commit.
Прямые API-записи состояний, истории, сообщений и заметок защищены отдельно.

Состояние процесса, общее/dependency-состояние, packages, сообщения с историей,
автоматические заметки ошибок, задачи, StatusLog и журналы входят в транзакцию
вызывающей команды. Отказ прав, поздняя ошибка триггера/записи либо защищённый
callback откатывают весь переход. База состояний и проект сообщений определяются
**фактическим проектом родителя**, даже при другом текущем проекте запроса.
Прежний перенос альтернативных pipelines заполняет пустой в исходнике
`pipeline_code` состояния. Остальные сверенные статусы задачи и содержимое
сообщений с их порядком совпадают с настоящим исходным runtime.

Python callbacks теперь используют явное разрешение доверенного запуска, описанное ниже.
Произвольные node handlers остаются административными; серверный JavaScript не перенесён.
Тесты проверяют настоящий исходник, неизменённый SDK/XML-RPC, native error notes,
отказы колонок/родителя/read-policy, подмену ссылок и bound SQL, отзыв прав после
staging, откат callback/поздней записи, хранение эффектов при другом контексте и
одинаковый сценарий SQLite/PostgreSQL (`tests/test_user_workflow.py`). Полный
охват остальных межпроектных графов и права файлов ещё не проверены; dependency описан ниже.

## Разрешение доверенного Python

С 0.112.13 обычный пользователь может запускать исходные `PythonCmd`,
`PythonTrigger`, сохранённые/inline Python callbacks Workflow и
`execute_python_script`, если access rules его групп явно разрешают исходный
ключ `api_cmd` — `tactic.command.PythonCmd` — и доступ к текущему проекту:

```xml
<rules>
  <rule group="project" code="cg_test" access="allow"/>
  <rule group="api_cmd" key="tactic.command.PythonCmd" project="cg_test" access="allow"/>
</rules>
```

Для этого исходного правила команды нужен `key`, а не `code`. Разрешение
проверяется и при незаданном `security/api_cmd_restricted`. В отличие от
разрешающего default исходника, обычный пользователь без явного grant
по-прежнему не запускает Python. При включённом ограничении `api_method`
внешний вызов `execute_python_script` проверяет и это правило.
Администратор сохраняет исходный путь; временный Sudo или admin flag в памяти
не заменяют настоящие права аутентифицированной сохранённой учётной записи.

`check_script_execution(..., python=True)` используется только в PythonCmd,
PythonTrigger и предварительной проверке dispatcher. Проверяются личность
запроса, активная сохранённая учётная запись, текущий проект, исходное правило
команды и активная транзакция Command. Остальные административные callers
сохраняют `python=False`: grant не открывает редакторы шаблонов/plugins/config,
raw SQL, произвольные node handlers или Expression `@PYTHON`. Пути скриптов,
inline code, Mako input/kwargs, автор локального SDK и транзакция сохраняют
исходные контракты.

Это **доверенный серверный Python, не песочница**. Разрешённый код может
импортировать Python-модули и обращаться к файлам/процессу сервера; grant
предназначен доверенным авторам. Отдельных ACL путей скриптов или ограниченного
языка Python пока нет. Grant не даёт прав редактировать сохранённые скрипты и
не меняет права UI Script Editor. Native SDK-записи сохраняют ACL объектов/полей.
Ошибка callback откатывает задачи, состояния, сообщения/историю и предыдущие
native-записи объектов; независимые постоянные журналы диагностики сохраняют
собственную политику.

С настоящим исходным runtime сверены inline и сохранённый Workflow callback
обычного пользователя с изменением родителя через неизменённый local SDK.
Тесты также проверяют SDK/XML-RPC и отказ api_method, native PythonTrigger,
отсутствие grant, отказы проекта/типа/полей, fake admin/Sudo, обязательную
транзакцию, поздний откат Python и одинаковый сценарий SQLite/PostgreSQL.
Права файлов, остальные варианты межпроектных графов и полный API ещё не завершены.

## Межпроектные зависимости

С 0.112.14 dependency может запустить дочерний Workflow в другом проекте,
дождаться его задачи и завершить вызывающий процесс после окончания дочернего.
Каждый проект сохраняет свою конфигурационную БД и состояния; общие задачи,
сообщения и история сохраняют фактический проект объекта и автора запроса.

`Pipeline.get_process_sobject()` читает `config/process?project=<владелец pipeline>`.
Обработчик Workflow использует существующий кеш Pipeline с инвалидацией при
изменении определений. Второй кеш, привязанный к вызывающему проекту, удалён.
Исходное чтение искало процесс в конфигурационной БД вызывающего проекта и
теряло чужой процесс. Это явно отмеченное исправление бага, сверенное в обоих
направлениях и с контрольными чтениями внутри одного проекта.

Для native `process|...` события с Pipeline и SObject общий `Trigger.call`
выбирает фактический проект объекта до подбора и исполнения триггеров.
Временно заменяется только поле проекта запроса: пользователь, ticket,
пул соединений и Command-транзакция остаются прежними. `finally` возвращает
контекст после успеха, отказа или ошибки callback. Так выбираются сохранённые
скрипты проекта callback и его явное разрешение `PythonCmd`.
Grant вызывающего проекта не разрешает Python в дочернем проекте.
Обычному пользователю нужны права редактирования каждого затронутого родителя.

Исходная проектная схема ограничивала `spt_process_state.state` 256 символами;
JSON ожидающих dependency может быть длиннее. Создание проекта PostgreSQL,
обновление конфигурации плагина/шаблона и `Store.upgrade()` переводят колонку
в `text`, сохраняя существующие значения. Повторное обновление сохраняет
длинные состояния. SQLite уже принимает их без ограничения varchar.

На двух физических проектных БД проверены запуск зависимости, ожидающая
дочерняя задача, обратное завершение, inline/сохранённый callback в своём
проекте, отказы project/type/Python grant и поздний откат объектов, состояний,
задач, сообщений, StatusLog и transaction journal. Один сценарий проходит
SQLite/PostgreSQL и неизменённый SDK по настоящему XML-RPC; тестовые серверы
и БД удаляются. Проверен dependency; все межпроектные hierarchy, progress
listeners и конфигурационные overrides этим не объявляются готовыми.

До commit ошибка откатывает все участвующие соединения. Отдельные commit
каждой БД сохранены, как в TACTIC: распределённой атомарности нет.
Ошибка позднего commit сообщает уже сохранённые БД; нельзя утверждать,
что их строки откатились. Права файлов и полный API остаются в плане.

## Постоянная диагностика

С 0.112.10 аутентифицированные пользователи могут использовать исходные
`DebugLog.log(level, message, category)`, `DebugLog.debug(message, category)`,
`ExceptionLog.log(error, message=None)` и XML-RPC `log`. Уровни: `critical`,
`error`, `warning`, `info`, `debug`; неверный уровень даёт `ValueError`.
Native логирование возвращает SObject, API `log` возвращает `True`.

DebugLog сохраняет login, уровень, категорию и сообщение. ExceptionLog — login,
класс исключения, сообщение и traceback с нормализованными разделителями путей.
Автор обязан совпадать с аутентифицированным контекстом; анонимная запись и
подмена автора запрещены. Права метода API и колонок продолжают действовать.

Общий `_write_log` открывает отдельный контекст запроса и native `Command` на
системном ресурсе. Транзакция отключает undo recording и sync, логирование —
триггеры. `Diagnostics:writing` временно указывает на **один новый SObject**,
разрешая только вставку и штатное присваивание сгенерированного code. SQL binder
проверяет фактического автора, ресурс, операцию и bound-поля. Область удаляется
в `finally`; общих прав на системные таблицы, SQL или администратора нет.
Прямые API записи в таблицы журналов остаются ограничены.

При ошибке `Command.execute_cmd` откатывает вызывающую транзакцию, очищает
весь стек упавших вложенных команд и затем сохраняет исключение один раз.
Следующая команда снова является корневой и штатно откатывается. Ошибка
соединения диагностики сообщается, не заменяя исходную бизнес-ошибку.
Batch после входа обычного пользователя закрывает административный контекст
аутентификации и соединения, создавая контекст фактического пользователя.

Если вызывающая команда уже писала в системную БД, независимое логирование
даёт `UnsupportedContract`: оно не присоединяется незаметно к этой записи и
не откатывает её. Это исключает конфликт SQLite writers и сохраняет тот же
контракт на PostgreSQL. Отложенная постоянная диагностика и email-уведомления
ещё не реализованы.

Проверены ordinary/admin вызовы на настоящем исходном runtime, неизменённый
SDK по HTTP XML-RPC, запреты метода/подмены автора/raw SQL, сохранение debug
после отката, одно исключение вложенной ошибки, откат следующей команды,
аутентификация и одинаковый сценарий на изолированных SQLite/PostgreSQL.
Этот путь диагностики в БД отделён от JSONL сессий браузера/Handler.

## Виртуальный SObject

`sthpw/virtual` — исходный временный тип TACTIC. Его метаданные создаёт `SearchType.get()` без записи в реестр. В метаданных указаны класс `pyasm.search.SObject`, база `sthpw` и условное имя таблицы `unknown`; физической таблицы не существует.

Поля виртуального объекта задаются во время работы. Информация о колонках и их SQL-типах пустая; обычная сериализация собирает поля из `data` и `update_data`, включая `id`. Исходный normal-режим такого объекта возвращает все его поля даже при переданном списке `columns`. Fast-режим учитывает этот список.

```python
from pyasm.search import SearchType

obj = SearchType.create('sthpw/virtual')
obj.set_value('label', 'Временный результат')
result = obj.get_sobject_dict()
```

Новый объект имеет `id = -1` и ключ `sthpw/virtual?id=-1`. Этот ключ обозначает временный объект; использовать его как ссылку на сохранённый ассет нельзя. `commit()` и `delete()`, включая запрос SQL через `return_sql`, завершаются явной ошибкой: сохранять нечего. Значения полей остаются в памяти для дальнейшего чтения.

Виртуальный объект сохраняет проверки прав `set_value()`. Его нельзя использовать для обхода правил доступа к колонкам или объектам БД.

## Контексты выражений: state, date и vars

`ExpressionParser` находится в `pyasm/biz/expression.py`. Вызов `eval()` получает начальные объекты, режим результата и контексты. `@GET` читает значения, `@SOBJECT` возвращает объекты.

`state` — словарь состояния, явно переданный текущему вызову парсера. Это не глобальная настройка приложения и не транзакционный API `set_state`. Парсер помещает значения в виртуальный SObject; поля со значением `None` пропускаются.

```python
from pyasm.biz import ExpressionParser

result = ExpressionParser().eval(
    '@GET(state.label)', state={'label': 'Выбранный процесс'}
)
# ['Выбранный процесс']
```

Ноль и `False` сохраняются. Чтение пропущенного поля нового объекта обычно возвращает пустую строку. Повторный вызов с другим `state` не должен использовать результат предыдущего состояния.

`date` создаёт виртуальный объект с полями `today` и `now`. Оба значения берутся с серверных часов при вычислении. В исходном контракте `today` содержит также время: это не полночь и не дата телефона пользователя.

```python
result = ExpressionParser().eval('@GET(date.now)')
date_objects = ExpressionParser().eval('@SOBJECT(date)')
day = ExpressionParser().eval("@FORMAT(@GET(date.now),'31/12/1999')")
```

Внутри ядра поле даты может быть `datetime`; в словаре API оно передаётся строкой. Для стабильного формата используйте `@FORMAT`; неизвестное имя формата сохраняет исходное значение. Даты и денежные форматы могут зависеть от настроек проекта и локали сервера.

`vars` — другой механизм: значения подставляются в выражение через `$NAME`.

```python
result = ExpressionParser().eval('$LABEL', vars={'LABEL': 'Publish'}, single=True)
# 'Publish'
```

Исходный `@VAR(NAME,value)` не присваивает переменную: он возвращает пустой список и не выполняет вложенные выражения. В single-режиме результат — `None`. Неполный вызов в Stream даёт `SyntaxError` вместо исходного `IndexError`.

XML-RPC `server.eval()` принимает `vars`, но не аргумент `state`. Передавать `state` можно в серверном Python через `ExpressionParser.eval()` или `Search.eval()`. Не добавляйте этот аргумент к клиентскому вызову API.

## Контекст запроса, кэш и права

`RequestContext` содержит активные Store, пользователя, проект и Container. Контекст изолирован между запросами; Container хранит временные метаданные и результаты в его пределах. Парсер учитывает начальные объекты, состояние и пользователя при построении ключа кэша. Записи и откат инвалидируют результаты выражений.

API устанавливает проверки доступа для вложенных вызовов выражений и восстанавливает их после результата или ошибки. Чтение `state`/`date` также проходит проверку виртуального типа; заполнение полей сохраняет исходную проверку доступа к колонкам. Чтение временной даты не выдаёт доступ к закрытым типам. Произвольный серверный Python доступен только разрешённым пользователям.

`NamingUtil` использует тот же парсер при вычислении шаблонов и передаёт объекты своего naming-контекста. Поэтому изменение парсера проверяется также в Naming, а не только через API.

Фильтры со значениями-выражениями используют исходный путь Search.eval. Правила значений, права API и поведение Command описаны в [справке о фильтрах Search](search_filters.ru.md).

Фильтры часов БД и их исходные правила кавычек описаны в [справке о timestamp-фильтрах](timestamp_filters.ru.md). SQLite сравнивает поддержанные динамические timestamp-значения как моменты времени; PostgreSQL сохраняет семантику часов базы и интервалов.

Search и его Select используют общие фильтры, копии и пагинацию; подробности в [справке Search/Select](search_select.ru.md).

## Записи родителя и детей через API

`server.get_parent(search_key, columns=['name'])` читает родителя, определённого схемой.
`server.get_all_children(search_key, child_type, filters=[], columns=['code'])` читает
детей через исходные связи Search и общий путь фильтров. Непустой `columns` ограничивает
возвращаемые поля, пустой список возвращает полную запись. `__search_key__` и
`__search_type__` остаются доступны, даже если не запрошены. Отсутствующее поле равно
`None`; отсутствующий родитель — `{}`, отсутствие детей — `[]`.

Серверный `get_parent` по умолчанию включает retired-родителя, а неизменённый
Python-клиент исключает его. При необходимости передайте `show_retired` явно.
Дети сохраняют исходное исключение retired-записей. Права проекта/типа и вложенных
выражений продолжают действовать. Пишущий фильтр участвует в текущем Command и
откатывается, если последующий фильтр завершается ошибкой.

В исходном сериализаторе API `columns` перезаписывался всеми ключами записи. Stream
исправляет этот дефект существующим общим сериализатором; поведение исходника и
правильная проекция проверены отдельными ожиданиями. Deprecated-аргумент `columns`
у core `SObject.get_parent()` по-прежнему игнорируется, как в исходнике: проекция API
выполняется при сериализации, а не меняет поиск связи.

Проверки: `tests/test_schema.py` сравнивает настоящее исходное ядро, проверяет
неизменённый XML-RPC клиент и серверный Python, retired, два проекта, права читателя
и откат. `tests/test_schema_postgres.py` сравнивает проекции родителя/заметок на
изолированных SQLite и PostgreSQL. Поддержка instance JOIN и её ограничения описаны ниже;
полная совместимость связей и API этим не подтверждена.

### Дети через промежуточный instance-тип

Для связи схемы с `relationship="instance"` метод `get_all_children()`
использует общий `Search.add_relationship_filter()`, как чтение связанных
объектов. Search соединяет цель, instance-таблицу и источник, затем фильтрует
колонку присоединённого источника по переданному объекту. Этот же путь
используется в `query(parent_key=...)`: исходный фильтр оставлял такие запросы
без ограничения родителем. Исходный обратный фильтр одного объекта обращался
к неверной таблице и предполагал одинаковые имена ключей; обе ошибки
исправлены в общем методе.

```python
# Для instance-связи, объявленной между этими типами проекта:
children = server.get_all_children(
    'cg/scenes?project=cg_test&code=DEMO_EP01',
    'cg/assets', columns=['code', 'name'],
)
```

Instance-тип и оба связанных типа должны быть доступны для чтения. Нет
линков — `[]`; запрет чтения instance-таблицы даёт ошибку, а не раскрывает
связанные записи. Дополнительные фильтры, проекция, подсчёт и откат транзакции
используют существующие пути Search/API. JOIN сохраняет результат на каждую
совпавшую промежуточную строку: несколько линков могут повторять одну цель.
По умолчанию retired-цели исключаются, но новое правило retirement для
присоединённых instance-строк не добавляется. Полные записи включают
`_related_code` присоединённого источника; проекция может его исключить.

Поддержаны разные зарегистрированные типы и направленное чтение self-instance
в одной базе (см. ниже). Instance-связь между разными базами отклоняется до
JOIN. Буквальный режим `relationship="many_to_many"`
пока не поддержан. Это не исключает связи `type="many_to_many"`, которые
используют `relationship="instance"`.

Сравнение с настоящим исходным runtime отделяет его отсутствующую ветку
детей, ошибку обратного ключа и нефильтрованный parent-запрос от правильных
ожиданий. Проверены оба направления, повторные/retired/пустые цели, разные
имена ключей, права читателя, откат, неизменённый XML-RPC и серверный Python.
Изолированные SQLite/PostgreSQL проверяют создание, чтение и удаление линков.

### Пакетный поиск instance-связей и поиск с фильтрами

`Search.add_relationship_filters(sobjects, op='in', path=None, type=None)`
ограничивает instance JOIN ключами переданных объектов. Исходная ветка
присоединяла все строки источника и игнорировала список и оператор. Stream
использует фактическую ключевую колонку схемы в обоих направлениях. Входные
объекты должны принадлежать одному типу и тому же ресурсу, что цель; смешанные
типы и проекты на разных ресурсах отклоняются до JOIN.

`Search.get_related_by_sobjects(sobjects, related_type, filters=[], path=None,
show_retired=False)` возвращает словарь с search key каждого входного объекта.
Нет совпадений — пустой список. Фильтры цели применяются до группировки;
несколько линков сохраняют несколько строк. В пакетном пути `_related_code`
содержит фактический ключ схемы: это может быть имя или ID вместо `code`.
Поэтому группировка работает и при разных ключевых колонках сторон.

`Search.add_relationship_search_filter(search, op='in', delay_null=False,
use_multidb=None, path=None)` выполняет фильтры и пагинацию поиска источника,
извлекает фактическую ключевую колонку и применяет фильтр к тому же JOIN.
Ключи извлекаются тем же быстрым путём, что code/ID: выбранные aliases
не подменяют ключ схемы. Текущие права проверяются заново. Заранее загруженные
объекты или count не замораживают этот поиск. Retirement-настройка источника
учитывается; явно переданные объекты не отбрасываются только из-за retired.

```python
# Серверный Python; нужна instance-связь в схеме проекта.
from pyasm.search import Search

selected = Search('cg/scenes')
selected.add_filter('code', 'DEMO_EP01')
assets = Search('cg/assets')
assets.add_relationship_search_filter(selected)
records = assets.get_sobjects()
```

`not in` сравнивает ключ каждой присоединённой строки источника. Цель,
связанная и с выбранным, и с другим источником, может вернуться по другому
линку; это не anti-JOIN со смыслом «нет связей с выбранными». Пустой вход
не находит записей при обоих операторах. Для переданного Search instance-ветка
возвращает `True` даже без результатов; `delay_null` не откладывает этот пустой
результат. Retirement промежуточных строк и поведение дубликатов не менялись.
При совпадении типов поиск читает направленные связи, если определена
instance-связь; fallback по identity остаётся для типов без такой связи.
Межресурсный instance-поиск ещё не завершён.
Произвольные агрегатные проекции источника не проверены.

Проверки включают 20 дополнительных сценариев пакетного поиска на настоящем
исходном runtime, оба направления, `in`/`not in`, пустые и заранее загруженные
поиски, разные ключевые колонки, aliases проекции, права на промежуточный тип,
серверный Python через неизменённый XML-RPC SDK, откат и SQLite/PostgreSQL.

### Направленное чтение instance-связей одного типа

С версии 0.112.7 `get_all_children`, `query(parent_key=...)`, фильтры связи
по одному объекту/списку/Search и `get_related_by_sobjects` используют общий
направленный instance-поиск ядра. Дерево результатов использует этот же путь.
В исходном ядре совпадение типов возвращало входной объект либо завершалось
ошибкой вместо чтения таблицы связей. Сравнение сохраняет эти результаты как
явные дефекты; ожидания Stream следуют существующей схеме направлений Handler.

В схеме проекта нужны self-связь и оба именованных конца:

```xml
<connect from="cg/assets" to="cg/assets" relationship="instance"
         instance_type="cg/asset_in_asset"/>
<connect from="cg/asset_in_asset" to="cg/assets" relationship="code"
         from_col="search_code" to_col="code" path="parent"/>
<connect from="cg/asset_in_asset" to="cg/assets" relationship="code"
         from_col="parent_code" to_col="code" path="child"/>
```

В Handler конец от строки связи к участнику называется `parent`, а конец
к владельцу — `child`. Без `path` либо с `path='parent'` поиск возвращает
участников владельца. С `path='child'` он возвращает владельцев участника.
Явно именованная self-связь также выбирает участников. Неизвестный путь,
отсутствующий или отключённый конец схемы вызывают ошибку: поиск не выбирает
направление молча и не подменяет результат самим владельцем.

```python
from pyasm.search import Search

owner = Search.get_by_code('cg/assets', 'DEMO_ROBOT')
members = owner.get_all_children('cg/assets')
owners = Search('cg/assets')
owners.add_relationship_filter(members[0], path='child')
records = owners.get_sobjects()
```

Концы могут использовать связи `code` или `id`. Фильтры и группировка по
`_related_code` берут реальные ключи схемы, включая ID. Запрос отдельно
задаёт SQL aliases таблицы связей и объектов источника: два направления
могут одновременно ограничивать один поиск. Копирование и сохранение/
восстановление Select сохраняют aliases. У результатов остаются обычные
SearchType и search key целевого объекта. Оборванные ссылки не превращаются
в существующие объекты источника.

Повторные связи остаются повторными строками; циклы и ссылки на себя читаются
по одному ребру без рекурсивного обхода. Сохраняются retirement цели, проекция
и страница поиска источника, построчный `not in`, счётчики и обычные права
чтения instance-типа. Без связей возвращается пустой список. Проверены
13 сценариев настоящего исходного runtime, неизменённый XML-RPC/серверный Python,
отказ в чтении линков, откат, code/ID ключи, восстановление aliases и отдельные
SQLite/PostgreSQL. Дерево шаблона `cg.zip` проверено в собственном временном проекте.

### Направленная запись instance-связей одного типа

С версии 0.112.8 `owner.add_instance(member)` заполняет обе колонки линка:
endpoint path `child` задаёт владельца, `parent` — участника, как в примере
схемы выше. Оба пути должны быть включёнными code/id связями с разными
колонками линка. Исходный runtime разрешал один путь дважды и перезаписывал
владельца участником; native запись исправляет эту ошибку.

```python
owner = Search.get_by_code('cg/assets', 'DEMO_BODY')
member = Search.get_by_code('cg/assets', 'DEMO_ARM')
link = owner.add_instance(member)
outgoing_links = owner.get_instances('cg/assets')
owner.remove_instance(member)
```

Соответствующие XML-RPC методы принимают search keys. `get_instances`
возвращает исходящие **записи линков**, `get_all_children` — объекты-участники.
Дубликаты и ссылки на себя разрешены. Удаление убирает все активные линки
точной направленной пары; обратные связи, другие участники и retired-линки
остаются. Без совпадений операция ничего не меняет. Retired-объект всё ещё
можно адресовать по ID; отсутствующий участник не скрывает исходящий линк.

Создание и удаление проверяют сохранённые, доступные сейчас объекты с
неизменёнными ключами одного типа, проекта и ресурса БД. Неполная схема,
устаревшие, отсутствующие, несохранённые объекты и разные проекты отклоняются.
Чтение линков использует обычные права типа. С версии 0.112.9 запись
проектных instance-линков обычным пользователем использует общие проверки
проекта/типа/полей/текущей строки, описанные выше. Системные и файловые
записи защищены отдельно.

Изменения используют native commit/delete, триггеры, транзакционное логирование
и откат Command. 16 code/ID сценариев сравниваются с настоящим исходным
runtime и отдельными ожиданиями направлений; проверены успешное сохранение,
дубликаты/удаление и откат после ошибок настоящих insert/delete-триггеров.
Неизменённый SDK/XML-RPC, настоящий PostgreSQL в сравнении с SQLite и временный
проект из `cg.zip` проходят. Межресурсные JOIN, произвольные агрегатные
проекции ключей и полный паритет API остаются незавершёнными.

### Быстрые списки кодов и ID

`Search.get_sobject_codes()` и `Search.get_sobject_ids()` читают БД без создания
SObject. Они возвращают фактические `code` или `id` основного типа Search.
Исходные helpers брали первое выбранное значение: существующая проекция `name`
или JOIN могла превратить список кодов в имена или ID. Stream исправляет
дефект с независимыми ожиданиями при проверке настоящего исходного runtime.

```python
from pyasm.search import Search

search = Search('cg/assets')
search.add_column('name', as_column='code')
search.add_filter('name', 'Robot')
codes = search.get_sobject_codes()  # Реальные коды ассетов вместо имён из alias.
ids = search.get_sobject_ids()     # Реальные числовые ID.
```

Обычное добавление ключевой колонки остаётся видимым в Select вызывающего кода.
Существующие проекции и aliases сохраняются. Копия запроса добавляет реальную
колонку основной таблицы для извлечения через штатные compiler и connector.
Сохраняются фильтры, строки JOIN, дубликаты, distinct-флаги, явная сортировка
и пагинация; неявная сортировка не добавляется. Повторные вызовы code/ID
не оставляют служебную дополнительную проекцию в исходном Search. Значения
не берутся из кэша загруженных объектов; несохранённые атрибуты SObject
не подменяют значения БД. NULL-код остаётся `None`; пустой или запрещённый
поиск возвращает `[]`. Retirement и bound-параметры используют правила Search.

Custom `alter_search` выполняется один раз на Search, как прежде. Исполняемая
копия заново проверяет текущие права основного типа и вложенную read-policy;
запрос, созданный под Sudo, не сохраняет эти права после выхода из Sudo.
Code/ID helpers и извлечение ключей источника instance используют общий путь.
Записи перед последующей ошибкой по-прежнему откатываются через Command.

22 сценария настоящего исходного runtime проверяют проекции, звёздочку,
aliases, присоединённые поля, NULL/retired, пагинацию и второй проект.
Native-проверки также охватывают повторные вызовы, custom hooks, восстановление
read-policy, Sudo, неизменённый XML-RPC SDK/серверный Python и rollback.
Изолированные SQLite/PostgreSQL проверяют оба ключа, дубликаты JOIN, aliases
и пагинацию. Произвольные grouped/aggregate проекции источника и межресурсные
JOIN этими проверками не подтверждаются.

## Append и группы кадров обычного пользователя — 0.112.16

`add_file` и `add_group` находят существующий snapshot и его видимого родителя;
`group_checkin` находит объект напрямую. Dispatcher допускает эти операции в тот же
native check-in-контекст, что и `simple_checkin`. Проверяются project allow,
редактирование родителя, операции snapshot/file и затрагиваемые поля под реальным
пользователем. Metadata не может перенести file в другой snapshot или изменить
родителя/проект. Работают исходные FileAppendCheckin/FileGroupCheckin/FileGroupAppendCheckin,
naming, триггеры, Command и FileUndo. Draft File/FileGroup теперь получает `search_code`
до первого commit, поэтому проверка родителя видит полную принадлежность записи.
Публичные конструкторы/фабрики сохраняют исходные сигнатуры и поведение по умолчанию.

Файлы заранее помещаются в каталоги аутентифицированного ticket. Неизменённый SDK:
`add_file(snapshot_code, "extra.txt", "reference", mode=None)` и
`add_group(snapshot_code, "image.####.exr", "frames", "1-3", mode=None)` читают ticket upload.
`group_checkin(search_key, "render", "image.####.exr", "1-3", mode=None)` читает ticket
server handoff, как в TACTIC. Binary `upload_file` загружает в ticket upload; для handoff
нужны файлы по настроенному серверному пути. Для уже подготовленных файлов не вызывайте
SDK с `mode="upload"`: он пытается дополнительно сделать HTTP upload с диска клиента.
Сам API group с `mode="upload"` читает ticket upload напрямую. API local/inplace/свои
классы требуют администратора; остальные файловые методы сохраняют прежние ограничения.

В strict naming физические aliases требуют явных определений `latest_versionless`
или `current_versionless`. Существующие latest aliases обновляются после append и
group check-in, не перезаписывая версии. Naming должен разделять пути типов файлов
и версий. Если исходный naming отключает alias, принудительная копия не создаётся.

На SQLite/PostgreSQL и через неизменённый SDK/XML-RPC проверены массив append,
последовательности `####`/`%04d`, шаг `1-3/2` и metadata, содержимое настоящих latest

ошибка. Второй append массива может упасть после первого; внешняя Command возвращает
все строки и прежнее содержимое версий/aliases. Потреблённые create uploads остаются
в durable undo-cache; перед повтором загрузите их заново. Между commit разных БД

## HTTP staging обычного пользователя — 0.112.17

Исходный SDK передаёт в `/tactic/default/UploadServer/` только ticket;
`set_project()` меняет XML-RPC envelope, но не HTTP-форму загрузки. UploadServer
поэтому следует исходному UploadServerWdg: активный аутентифицированный пользователь
может подготовить файлы в личном каталоге ticket до выбора проекта/объекта. Это
доступно и читателю, но не даёт права check-in в repository. Check-in по-прежнему
требует project allow, редактирование родителя и права snapshot/file/полей.
Binary XML-RPC `upload_file(ticket, filename, data)` сохраняет проверку проекта.
Доступный проект не угадывается, права admin не выдаются.

`Api.http_upload → Command → FileUpload → FileUndo` использует штатные create/append
и rollback. Только для этого HTTP-запроса контекст `Checkin:writing.ticket_upload`
пропускает проверку проекта при личном staging. Сохранены persisted active identity,
аутентифицированный пользователь, настроенные ограничения API-метода и обязательная
Command-транзакция. Контекст запроса заканчивается после операции; произвольный
FileUndo вне разрешённой операции закрыт. Пути и цели symlink остаются внутри
каталога своего ticket. Чужой transaction ticket и custom upload_dir явно не поддержаны.

Неизменённый SDK теперь выполняет `upload_file(local_path, chunk_size=113)`,
`simple_checkin(search_key, context, local_path, mode="upload")`,
`group_checkin(search_key, context, "image.####.exr", "1-3", mode="upload")`,
`add_file(snapshot_code, local_path, file_type, mode="upload")` и
`add_group(snapshot_code, "image.####.exr", file_type, "1-3", mode="upload")`.
Автоматический режим сначала загружает с диска клиента, затем вызывает исходную
XML-RPC-операцию. Это отличается от описанных выше manual-вызовов подготовленных файлов.

Проверены binary/Unicode chunks, offset resume, пустые файлы, автоматические SDK-вызовы,
невалидная/retired identity, пути и чужой ticket, ошибка второго файла с восстановлением
первой замены. SQLite/PostgreSQL выполняют одинаковый native-путь. HTTP-запрос ограничен
64 MiB с учётом multipart/base64, поэтому большой файл нужно делить. Каждый chunk
коммитится отдельно: предыдущие успешные chunks сохраняются после ошибки следующего
запроса. Resume offset — заданный клиентом индекс chunk, а не подтверждённый сервером
байтовый offset. У исходного append нет ключа идемпотентности: повтор после неизвестного
исхода запроса может удвоить байты. Rollback check-in сохраняет штатный create undo-cache.
Права обычного пользователя для check-out и undo/redo журнала ещё не проверены;
полный API-паритет не заявлен. Тесты: `test_user_checkin.UserHttpCheckin/UserHttpTransport`
и UploadServer в `tests/test_transport.py`. Repository Sync и S3 исключены.

## Checkout обычного пользователя — 0.112.18

`checkout(search_key, context="publish", version=-1, file_type="main", level_key=None)`
возвращает три соответствующих списка: `client_lib_paths`, `sandbox_paths`, `web_paths`.
Сервер выбирает Snapshot, проверяет исходную блокировку контекста на version 1 и
вызывает `checkout`, затем `checkout|<base_search_type>`. Сам сервер файлы не копирует.
Явная версия, current (`None`), versionless (`-1`), все типы (`*`) и указанный level
проверены на приватных SQLite/PostgreSQL. Для sandbox необходима штатная настройка
`checkin/win32_sandbox_dir` или `checkin/linux_sandbox_dir` для ОС клиента.

Обычному пользователю нужны `project allow` для фактического проекта родителя (с
0.112.25 он может отличаться от проекта запроса) и `search_type view` для родителя, `sthpw/snapshot`, `sthpw/file` и
необязательного level. Явные запреты `sobject`/`sobject_column` на просмотр также
останавливают операцию до callbacks. Все загруженные поля этих строк должны быть
видимы: callback получает полный штатный словарь Snapshot, а naming читает поля
объектов. Отсутствующие или скрытые выбранные File-ссылки отклоняются. Это строгая
проверка всей операции, а не общая политика сериализации строк с фильтрацией полей.
Выбор snapshot для администратора сохраняет прежнее поведение. Если включён
`api_method_restricted`, отдельно проверяется разрешение метода checkout.

Callbacks получают текущую Command: исправлена ошибка `ApiXMLRPC.errors`, которая
маскировала исходное исключение обработчика. Sudo и repository-write scope не открываются.
Читатель может выполнять checkout без обработчиков записи; изменение родителя из
callback требует его прав edit. Python callback дополнительно требует существующего
явного `api_cmd` grant для `tactic.command.PythonCmd`. Ошибка same-transaction callback
откатывает предыдущие изменения обработчиков и их журнал. Отложенные callbacks
сохраняют штатную границу после commit и не откатывают уже закоммиченного вызывающего.

Неизменённый SDK выполняет локальный ввод-вывод после успешного RPC:

```python
server.checkout(search_key, context="publish", version=2,
                file_type="*", to_dir=existing_directory, mode="copy")
server.checkout(search_key, context="publish", version=2,
                file_type="*", to_dir=existing_directory, mode="download")
server.checkout(search_key, context="publish", version=2,
                to_dir=existing_directory, to_sandbox_dir=True)
```

Copy/download и sandbox проверены через временный XML-RPC/HTTP сервер. Ошибка копирования
или скачивания на клиенте не откатывает успешный RPC и может оставить часть локальных
файлов. Статические HTTP aliases repository сохраняют исходное публичное поведение
Apache: ACL checkout не добавляет авторизацию пользователя к этим URL.
Заблокированный/отсутствующий snapshot локально выдаёт штатный ApiException; существующая
общая обработка XML-RPC скрывает эти подробности. Причину сохраняет ExceptionLog.
Checkout между проектами и последовательности описаны ниже.
Создание/чтение level aliases описано ниже в 0.112.27; replay произвольных
межпроектных callbacks не объявлен завершённым. Тесты: `test_user_checkout.UserCheckout/UserCheckoutTransport`,
`CommandApiParity`, `SnapshotLevelsParity`. Полный API-паритет не заявлен;
Repository Sync и S3 исключены.

## Undo/redo собственного CRUD проекта — 0.112.19

Обычный пользователь может вызывать исходный API неизменённым SDK:

```python
server.undo()                         # последний собственный undo-журнал проекта
server.redo()                         # самый ранний собственный redo-журнал проекта
server.undo(transaction_id=journal_id)
server.redo(transaction_id=journal_id)
```

Штатный путь: `ApiXMLRPC → UndoCmd/RedoCmd → TransactionLog → SObjectUndo`.
Undo преобразует insert/update/delete в delete/edit/insert; redo выполняет insert/edit/delete.
До replay проверяются текущий project allow, право операции типа, явные права строки и edit
для изменяемых полей. При отсутствии правила строки действует уже проверенное разрешение
операции типа; явный deny сохраняется. Удаление не требует edit отдельных полей. Сама запись
строк также сохраняет штатные проверки. Отсутствующий или скрытый read-фильтром объект для
update/delete обычного пользователя теперь вызывает отказ вместо ложного завершения журнала.

Журнал должен быть сохранён в БД, принадлежать аутентифицированному пользователю и текущему
проекту, иметь нужный type `undo`/`redo`. Каноническая строка блокируется и перечитывается:
PostgreSQL использует `FOR UPDATE`, SQLite — `BEGIN IMMEDIATE`. Изменённый/staged payload
и повторное неверное направление отклоняются. При конкурентном undo одного ID выполняется
один replay, второй получает отказ. Ограничения API-метода проверяются отдельно. Проверки
живут в TransactionLog: локальный native caller также не может проиграть поддельный
несохранённый или изменённый в памяти журнал.

CRUD-журнал включает integral-строки `sthpw/sobject_list` общего поиска. Они тоже
восстанавливаются штатным узким Sudo только на время каждой индексной операции. Проект и
родительский type/code/исходный ID индекса должны соответствовать объекту того же проверенного
журнала; остальные системные строки запрещены. Исходный ID допускается, поскольку source
rename/replay-журнал может сохранять прежний code в индексе. Восстанавливается записанный
payload индекса: исторические индексы заново не строятся, исходная политика identity/timestamp
не меняется. Общего sudo для пользователя/журнала нет. Ошибка undo/redo откатывает предыдущие
строки, индекс, направление журнала и change timestamps внутри native-транзакции. Новая
обычная запись сбрасывает redo-ветку этого пользователя, как в исходнике.

Этот релиз покрывает **CRUD SObject проекта и его integral-индекс поиска**, несколько объектов
и переименование code. Replay обычного пользователя для file/upload/check-in, схемы, task,
note, других системных и multi-site журналов не включён. Любой такой узел отклоняет весь
журнал до изменений; `ignore_files=True` не обходит границу. Произвольный `execute_transaction`,
client start/finish/abort и resumed-session операции сохраняют прежние ограничения.
Администраторский file/schema/client-session replay доступен; регрессии проверены.

Тесты: `test_user_undo.UserUndo/UserUndoTransport` на SQLite/PostgreSQL и временном XML-RPC
сервере с неизменённым SDK. Проверены CRUD/default/explicit выбор, сброс redo, поздние ошибки
undo/redo, rollback индекса, конкурентный повтор undo, owner/project/direction, отказы
type/record/column/method/read-filter, подмена staged XML и отказ реального личного upload
журнала. Сравнения с исходными Undo/FileUndo/SchemaReplay/TransactionState проходят.
Отдельные commit разных БД сохраняют штатную границу partial commit: распределённой
транзакции нет. Полный API-паритет не заявлен. Оставшийся file/system replay обычного
пользователя — следующий блок совместимости; Repository Sync и S3 исключены.

## Undo/redo собственного check-in (0.112.20)

Обычный пользователь теперь может проигрывать сохранённые собственные check-in журналы
через неизменённые `undo(transaction_id=...)` / `redo(transaction_id=...)`. Это расширяет
CRUD/индекс проекта из 0.112.19: штатные **SObjectUndo, FileUndo и FileUndoReplay** вместе
восстанавливают записи snapshot/file, байты версий и versionless. Проверены первая/вторая
версия, append типа файла и последовательности кадров через FileGroup/FileRange.

Канонический журнал блокируется и перечитывается с проверкой owner/project/direction.
Preflight требует видимого редактируемого исходного родителя в текущем проекте, прав view
и обратной операции для repository type/record/column, неизменных ownership-полей. Пути
должны соответствовать файлам этого родителя (с раскрытием кадров и .link), личной upload
директории ticket из журнала или его устойчивому undo-кэшу. Ссылки директорий не могут
выводить за эти корни. Временный Checkin:writing разрешает только текущий проверенный
узел журнала и восстанавливается в finally. Общего sudo для журнала нет.

Полный журнал уже содержит записи и операции versionless. Поэтому восстановление
is_latest/is_current не создаёт versionless повторно: иначе удалялись бы file-записи,
которые нужны следующим узлам replay. Числовые identity-поля из XML сравниваются с
типизированными ID базы одинаково. Поздняя ошибка SQL/metadata/IO компенсирует именно
выполненные/попытанные файловые узлы даже после закрытия check-in scope. Частичный
результат redo удаляется, если целый исходный файл сохранился в кэше; байты не теряются.

Check-in replay пользователя требует **всех его файлов**: ignore_files=True отклоняется.
Отдельный upload-only журнал, schema/task/note/другие-system/multisite и resumed client
sessions остаются закрыты. Исторические versionless-узлы без backup state требуют
миграции. Числовые ID repository-записей могут пересоздаваться, как в native SObjectUndo;
code и исходные anchors родителя сохраняются. Отдельные commit БД сохраняют прежнюю
границу partial commit: это не распределённая транзакция и не восстановление после
падения процесса/файловой системы. Проверены SQLite/PostgreSQL, исходный SDK XML-RPC,
байты/metadata, отказы прав/путей, поздние ошибки и частичные записи. Полный API-паритет
не заявлен; Repository Sync/S3 исключены.

## Запись задач/заметок и undo/redo (0.112.21)

Обычный пользователь может вызывать штатный `create_note` для видимого редактируемого
**объекта проекта**. Автор — текущий аутентифицированный пользователь. Передача чужого
`user`, редактирование чужой заметки, смена ownership или перенос задачи/заметки к другому
родителю отклоняются. Право читать приватные заметки не даёт права их редактировать.
Сохраняются проверки project/type/record/column. Ответ требует видимой ветки на том же
объекте проекта. Заметку с ответами, включая приватные, нельзя удалить, пока не удалены
ответы. Проверка целостности использует локальный sudo только для обнаружения потомков,
не раскрывая их содержимое.

Штатный `SObjectUndo` теперь проигрывает **собственные сохранённые журналы** обычного
пользователя с задачами или его заметками. Сохраняется блокировка owner/project/direction.
До изменений проверяются исходный родитель, его видимость и право edit, видимость задачи/
заметки, права обратной операции type/record/column и неизменность parent/author/thread.
Проверены создание, правка полей и удаление задач; создание, текст, переименование code,
удаление заметок и ветки ответов на SQLite/PostgreSQL и через исходный XML-RPC SDK.
Поздняя ошибка пакета откатывает и данные, и состояние журнала.

Заметки сохраняют числовой ID при восстановлении insert/delete: `parent_id` должен
ссылаться на ту же ветку. Исторический insert-журнал без этого anchor запоминает ID
перед undo и сохраняет дополненный канонический XML. Занятый ID вызывает отказ с откатом,
а не перезапись занявшей его заметки. Один и тот же тест исходного и native ядра показывает
намеренное исправление: исходный TACTIC пересоздаёт ID корня и оставляет ответ без родителя;
native сохраняет оба. Поведение числовых ID других типов SObject не менялось.

**Граница поддержки:** смена статуса задачи также может создавать `sthpw/status_log`,
Workflow state, сообщения и другие системные эффекты. Такие журналы отклоняются **целиком**,
пока не перенесены проверки replay для каждого эффекта. История не пропускается. Отдельно
записанная собственная Workflow-заметка поддерживается. Заметки на системных родителях,
reparenting, schema, отдельный upload, multisite и resumed-session replay остаются закрыты.
Отдельные commit БД сохраняют границу partial commit; распределённая атомарность не заявлена.
Repository Sync/S3 исключены, полный API-паритет не заявлен.

## Статусы задач и полный Workflow replay (0.112.22)

Собственные сохранённые журналы теперь отменяют и повторяют смену статуса задачи и
**Workflow в одном проекте** вместе: задачи, историю статусов, состояния процессов,
сообщения status/state (включая packages), историю сообщений и собственные заметки.
Штатный SObjectUndo проигрывает все записанные эффекты по порядку. Replay не запускает
Python callbacks повторно и не отправляет уведомления. Поздняя ошибка откатывает уже
изменённые данные и направление журнала.

Исходный SObjectUndo исключал сообщения из журнала. Теперь native Workflow записывает их
тем же logger в точном scope Workflow:writing и помечает корень XML
`workflow_replay="complete"`. Журналирование сообщений вне Workflow не менялось.
Исторические Workflow-журналы состояний/сообщений без этого marker отклоняются: безопасно
восстановить отсутствующие backups сообщений нельзя. Обычная история статуса задачи без
Workflow-состояний/сообщений поддерживает replay и без marker.

Preflight сохраняет блокировку owner/project/direction. Каждому эффекту нужен видимый
редактируемый исходный родитель проекта; истории статуса также нужен исходный объект в
том же журнале с совпадающим ID. История сохраняет аутентифицированного автора. Проверяются
текущие запреты view, обратной операции, record и column. Производные эффекты по умолчанию
следуют разрешённому родителю, как при прямом Workflow; права прямой записи системных
таблиц это не даёт. Временный Workflow:replay разрешает только текущую запись и операцию.
Bound SQL должен совпадать с подготовленным объектом после штатного преобразования СУБД,
включая JSON PostgreSQL. Scope восстанавливается в finally; другая запись и подмена SQL
отклоняются.

ID задач/process_state сохраняются при insert/delete replay, как ID заметок, чтобы
status_log продолжал ссылаться на тот же источник. Занятый ID вызывает отказ, а не
перезапись другой записи. Числовые ID других бизнес-объектов работают по-прежнему.
Сохранённые GMT-даты остаются GMT при redo: их преобразование как нового локального ввода
вызывало смещение в native. Один и тот же исходный/native тест проверяет частичное
восстановление Workflow и устаревшие сообщения исходного ядра, полное восстановление
native; даты проверены с явным не-UTC часовым поясом сервера и UTC preference пользователя.
Проверены SQLite/PostgreSQL, штатный SDK, pending/in-progress/complete, сообщения/packages,
история, отозванные права/read filters, точные scope/SQL отказы и поздний rollback.

**Сохранённые границы:** cross-project replay, старые Workflow-журналы без backups сообщений,
adoption пустого legacy pipeline owner, неперенесённые системные эффекты, schema, отдельный
upload, multisite и resumed sessions отклоняются целиком. Уже отправленные внешние эффекты
исходной операции не отменяются. Отдельные commit БД сохраняют partial commit; распределённая
атомарность и полный API-паритет не заявлены. Repository Sync/S3 исключены.

## Replay Workflow между проектами (0.112.23)

Собственные полные Workflow-журналы теперь поддерживают undo/redo зависимостей между
физическими проектными БД. Запуск зависимого процесса и возврат его завершения восстанавливают
вместе записанные изменения объектов, задачи, свои заметки, состояния процессов, историю
статусов и сообщения. Replay выполняют прежние штатный SObjectUndo и точный поузловой scope
Workflow:replay; Python callbacks повторно не запускаются. ID задач/заметок/состояний
сохраняют исходные связи.

Журнал остаётся в инициирующем проекте: его сохранённые автор, namespace и направление
undo/redo блокируются и проверяются. Открытие того же журнала из другого проекта не даёт
права replay. Для каждого эффекта исходный видимый редактируемый родитель определяет
фактический проект проверки project/view/обратной операции/записи/колонок. История статусов
требует исходную запись в том же журнале с исходным ID. Изменения объектов, задачи, свои
заметки и индекс другого проекта допускаются только для этих проверенных Workflow-родителей,
а не для произвольных чужих записей. Общего sudo на журнал нет.

SQLite, PostgreSQL и исходный XML-RPC SDK проверяют оба направления зависимости, результаты
callbacks/заметки, сохранение ID, отзыв прав в любом проекте, скрытых родителей, запреты
записей/колонок и неверный namespace. Искусственная ошибка после записей в обе проектные БД
откатывает их изменения вместе с системной историей, индексами и направлением журнала.
Проверяется ошибка до физического commit; распределённой атомарности это не обеспечивает.
Один неизменённый скрипт в обоих ядрах подтверждает дефекты оригинала: запись состояния
в БД вызывающего проекта и оставшиеся после undo сообщения. Новое ядро использует фактические
БД родителей и восстанавливает сообщения из полного журнала.

**Оставшиеся границы:** Workflow без полных backups сообщений, adoption старого пустого
pipeline_code, произвольный межпроектный CRUD и файловый replay между проектами,
неперенесённые системные эффекты, schema, отдельный upload, multisite и resumed sessions
остаются закрыты. Уже отправленные внешние эффекты не отменяются. Раздельные commit БД
сохраняют partial commit. Полный API-паритет не заявлен; Repository Sync/S3 исключены.

## Replay назначения pipeline старому состоянию (0.112.24)

Старые process_state могут иметь пустой pipeline_code. Штатный native Workflow уже назначает
такой записи основной pipeline родителя при обычной смене статуса. Теперь собственный полный
журнал отменяет это назначение до пустого значения и повторяет записанного владельца вместе
со статусом, данными состояния, сообщениями и историей. Исходная запись и ID сохраняются.

Preflight разрешает только записанный update из пустого значения к исходному видимому
основному pipeline родителя. Определение процесса должно оставаться видимым; __PIPELINE__
допускается как агрегат графа. Исходный ID состояния проверяется. Текущий владелец должен соответствовать направлению undo/redo,
а все записанные изменения — одной цепочке назначения того же владельца. Каждый узел журнала
получает своё ожидаемое значение pipeline до/после: обновления до назначения сохраняют пустого
владельца, последующие — записанного. Прежние проверки владельца/ACL и staged SQL в runtime
контролируют именно это значение. Остальные поля владения неизменяемы. Исключение не разрешает
произвольную смену непустых pipeline, смену pipeline родителя, замену принятой записи через
insert/delete или прямую запись обычного пользователя в process_state.

SQLite/PostgreSQL и исходный SDK проверяют назначение в обеих проектных БД, запуск/завершение
зависимости, сохранение ID/данных/своих заметок, отзыв прав на колонку pipeline, скрытые
определения процессов, подмену текущего владельца/родителя/журнала/SQL и поздний откат.
Один неизменённый скрипт выполняется в обоих ядрах: оригинал оставляет старого владельца пустым
и сообщения после undo; native Workflow назначает владельца, а undo возвращает пустое
значение и прежние данные состояния.

Исторические Workflow без полных backups сообщений восстановить по-прежнему нельзя.
Произвольный межпроектный CRUD/файловый replay, неперенесённые системные эффекты, schema,
отдельный upload, multisite и resumed sessions закрыты. Уже отправленные эффекты не отменяются.
Раздельные commit БД сохраняют partial commit; распределённая атомарность и полный
API-паритет не заявлены. Repository Sync/S3 исключены.

## Checkout между проектами — 0.112.25

Полный search key родителя может указывать на другой проект. Checkout проверяет доступ
к этому проекту и выбирает Snapshot, naming/sandbox и config callbacks в проекте родителя.
Временно меняется только поле проекта: пользователь, права, Command, транзакция и SQL pool
сохраняются. Finally возвращает исходный контекст запроса после успеха или исключения,
в том числе при вложенном вызове внутри Command.

Проверяются доступ к каждому связанному проекту и все загруженные строки/поля, включая
level из третьего проекта. Для Python callback нужен PythonCmd grant в проекте родителя.
Разрешение или checkout trigger вызывающего проекта его не заменяет. Checkout не даёт
читателю права редактировать объект. Ошибка same-transaction callback откатывает изменения
и журнал; прежние границы deferred/partial commit сохраняются. Журнал остаётся в проекте
исходного запроса; undo/redo произвольных межпроектных callbacks этой проверкой не покрыт.

Приватные SQLite/PostgreSQL и неизменённый SDK проверяют реальные версии/versionless,
все типы файлов, level своего/третьего проекта, copy/download/sandbox, запреты проекта,
строки/поля, блокировки, отсутствующие ссылки, class/saved-Python callbacks и поздний откат.
Один скрипт запускается без изменений в обоих ядрах: оригинал пропускает checkout callback;
новое ядро вызывает обработчик родителя и возвращает проект вызывающего. Checkout
последовательностей описан ниже; level-scoped aliases описаны ниже в 0.112.27. Сервер не откатывает клиентский
ввод-вывод после RPC; статические repository URL сохраняют публичную модель Apache.

## Checkout последовательностей — 0.112.26

Checkout разворачивает выбранный File последовательности в пути конкретных кадров по
сохранённому FileRange через штатный FileGroup. Например, image.####.png с 1-5/2 даёт
image.0001.png, image.0003.png, image.0005.png в каждом из client_lib_paths, sandbox_paths
и web_paths. Соответствующие позиции относятся к одному кадру. Для file_type="*"
последовательности и обычные файлы сохраняют порядок snapshot XML; конкретный тип
по-прежнему выбирает первый подходящий File. Пути обычных файлов/каталогов не меняются.
Методы путей Snapshot сохраняют прежнее явное управление expand_paths.

Исходный SDK использует эти списки для copy, HTTP download и sandbox checkout.
Оригинальный сервер возвращал буквальный шаблон, который SDK не мог скопировать как
файл. Один неизменённый probe проверяет это отличие на настоящем исходном ядре.
Callbacks получают развёрнутые пути. Сохраняются права пользователя и фактический
проект родителя; прав записи repository и sudo не добавляется. Повреждённый диапазон
или несогласованное число путей/ссылок вызывает ошибку до callbacks. Checkout не чинит
метаданные и не исключает кадры диапазона молча. Сам RPC клиентские файлы не копирует.

Приватные SQLite/PostgreSQL и исходный SDK проверяют hash/printf, диапазоны с шагом,
отрицательные кадры, явную/current/latest версии, несколько типов последовательностей
с обычным файлом, реальные байты copy/download, запреты прав, повреждённые диапазоны
и поздний откат callbacks. Ошибка клиента после успешного RPC может оставить часть
локальных копий и не отменяет закоммиченные callbacks. Семантика статических repository
URL сохраняется. Level-scoped aliases описаны ниже; replay произвольных межпроектных callbacks
ещё не проверен; полный API-паритет не заявлен. Repository Sync/S3 исключены.

## Latest/current aliases по уровням — 0.112.27

Для объекта, context и level_key check-in создаёт и обновляет отдельные alias Snapshot
LATEST (-1) и CURRENT (0) с точными search type и ID уровня. Область без уровня тоже
отдельная. get_snapshot(..., level_key=..., versionless=True) и
get_paths(..., level_key=..., versionless=True) выбирают именно этот alias. Без level_key
выбирается только alias без уровня; отсутствующий alias даёт пустой результат.
Snapshot.get_versionless сохраняет исходную публичную сигнатуру и выбор без уровня.
Уровень в вызовах API и check-in передаёт внутренний метод штатного Snapshot.

Пример: check-in v1 и v2 уровня A сохраняют коды его latest/current aliases.
Если у v2 is_current=False, latest указывает на v2, а current остаётся на v1.
Файлы и aliases уровня B не меняются. Strict naming должен задавать отдельные пути
latest/current и разные пути уровней, например
{project.code}/{context}/{snapshot.level_id}/latest и соответствующий каталог current.
Для системных проектов сохраняется исходное исключение database naming.
Существующий путь, не принадлежащий выбранному alias, отклоняется вместо перезаписи.
Перед повтором нужно исправить naming; неуспешный check-in откатывает свои строки
и файловые операции через штатные Command/FileUndo.

Приватные SQLite/PostgreSQL и неизменённый XML-RPC SDK проверяют три независимые
области, версии, реальные байты, стабильные коды, запреты записи по ACL, позднюю ошибку
триггера и коллизию двух уровней. Один неизменённый скрипт в обоих ядрах явно показывает
ошибку оригинала: исходный API возвращает один последний versioned snapshot для всех
уровней; новое ядро возвращает шесть правильных aliases. Это намеренное исправление,
а не заявление о совпадении ошибочных результатов.

Удаление/переназначение level aliases и level-specific durable replay журнала в этом
выпуске ещё не проверены; удаление level snapshot остаётся явно заблокированным.
Создание aliases между проектами и MySQL в эти проверки не входят. Границы публичных
repository URL и частичного commit независимых БД сохраняются.
Полный API-паритет не заявлен; Repository Sync/S3 исключены.

## Групповой чекин в браузере

Drop Plate и Commit Queue вызывают `execute_cmd` с классом `tactic.command.browser_checkin_cmd.BrowserCheckinCmd`. Действия `match`, `templates`, `plan` читают штатное распознавание/naming без записи в репозиторий. `checkin` проверяет ticket/проект, edit-права объекта, snapshot/file/полей и имена загрузок внутри каталога ticket. Именно эта доверенная команда доступна обычному пользователю с нужными правами; произвольный `execute_cmd` остаётся операцией администратора.

`file_matching.py` извлечён из `global_functions.py` ТХ, `checkin_query.py` содержит его расширенные процедуры naming/чекина. Инструмент извлечения фиксирует адаптации runtime: явный локальный SDK, явный процесс и сжатые диапазоны разреженных кадров. Источники и адаптации перечислены в compatibility manifest.

Распределение версий защищает штатная блокировка Snapshot. FileUndo подготавливает файлы, IconCreator создаёт производные, FileAppendCheckin регистрирует их внутри той же Command. Metadata определяет каждый кадр/тайл. DeleteCmd удаляет всю принадлежащую снапшоту группу. Когда ТХ сохраняет metadata после регистрации inplace, общий путь commit SObject возвращает члены, удалённые именно этой активной транзакцией, через воспроизводимые перемещения журнала. Undo/redo и rollback сохраняют эффекты БД и файлов; второй копии вне журнала нет. Назначение за пределами выбранного репозитория и чужие занятые пути отклоняются.

`versionless_mode` читается из проектного `config/prod_setting` через ProjectSetting, затем из серверного `checkin/versionless_mode`. Значения: `copy`, `hardlink`, `symlink`. Браузерные группы обновляют latest ссылками на нумерованные файлы согласно настройке; versionless-only копируется. Hardlink требует одну файловую систему, symlink — разрешение ОС. После ошибки ссылки нет незаметного fallback на копию. Metadata разреженных кадров остаётся сжатой; члены выдаются страницами.

Повторный браузерный или серверный queued-check-in сохраняет код снапшота `latest`: обновляет его определение и регистрирует новые File штатным FileAppendCheckin. Прежние File-записи удаляются через SObject; FileUndo удаляет только отсутствующие в новой группе пути и их служебные ссылки. Совпадающие пути уже заменены журналируемым staging и не удаляются повторно. Нумерованные версии сохраняются, check-in/File-триггеры и права продолжают проверяться, ошибка откатывает записи и содержимое файлов. Вместо удаления/создания latest происходит обновление существующего снапшота; отдельно запрошенное удаление через DeleteCmd по-прежнему удаляет всю группу. Клиент ТХ и его обычная inline-процедура не меняются.

Серверная очередь сохраняет исходное расширение собранного файла, чтобы IconCreator выбирал штатный обработчик изображения или видео. Неизвестные бинарные расширения, например `.toc`, пропускают создание превью; явно переданное изображение preview обрабатывается как раньше. Известные повреждённые изображения продолжают выдавать предупреждения, файлы без расширения проверяются обработчиком изображений.

Браузерные File handles живут в памяти. Восстановление хранит метаданные отдельно для login в `tactic_stream.commit_queue.<login>` и не возвращает разрешение на файлы. Шаблоны хранятся в `tactic_stream.matching_templates`. Это описание реализованных механизмов, а не новые методы серверного API. Проверены SQLite, штатные скрипты и Chromium; production PostgreSQL/MySQL и физические телефоны требуют отдельной приёмки.

## Контейнеры задач/общения и native-команды (0.112.34)

TaskManager.vue владеет фильтрами, ключами выбранных задач и локальными планами создания,
редактирования и расписания. TaskWorkspaceCmd читает настроенный каталог, TaskWorkspaceEditCmd
подготавливает проверенные планы и сохраняет их; TaskScheduleCmd рассчитывает и записывает
расписание. Быстрые карточки процессов и компактные строки используют эти же команды,
без независимого хранилища задач.

NotesPanel.vue владеет контекстом объект/процесс/точная задача, черновиками и защитой ревизии.
TaskInspectorHeader.vue и TaskDetails.vue отображают данные и сообщают о действиях.
TaskInspectorCmd объединяет native-поля, выбор процессов, счётчики связанных задач,
WorkHoursSummary и заметки/историю. DiscussionReadCmd/AddNoteCmd/ChangeNoteCmd работают
с каноническими целями заметок и авторством. Профили читаются пакетно. DiscussionReadCmd возвращает авторизованного current_user;
NotesPanel использует его в локальном ключе текста черновика вместо истекающего ticket.
Восстановление проверяет точную цель; файловые handles и выбор ответа остаются в памяти. Заметки родителя/процесса
и дополнительных задач различаются; счётчики процесса учитывают оба вида. Обновление раз
в 30 секунд работает только в активном Инспекторе и сохраняет правки с исходной ревизией.
Задержавшийся ответ не записывается в изменившуюся цель.

Заметки только с файлами используют FileCheckin внутри Command, FileUndo и metadata производных
предпросмотра. Вложения чатов и собственные аватары сохраняют проверенную область владельца
и существующее разрешение edit на записи репозитория. Пробный объект блокировки версий
сохраняет родителя Checkin:writing, а не притворяется частично заполненным снапшотом.
Проверки родителя/проекта/файлов, участников приватного скачивания, удаления и отката действуют.

HTTP сначала проверяет запрос целиком и использует системное пространство только при явно
пустом проекте у сообщений, обновлений, профилей и чтения ссылок. Отсутствующий/null проект
невалиден. Проектные цели ссылок требуют выбранного проекта и текущих прав. Глобальное общение
не выбирает и не сохраняет проект admin для рабочего пространства.

Настроенные команды UI задач и Discussion пока требуют admin. Права публичного SDK, реальные production DB,
различия оборудования/браузеров и полное покрытие API проверяются отдельно.
