# TACTIC 5.0 — Vue source fork 0.14

Полное дерево исходников на основе **последнего выпущенного 0.13**. Предыдущая попытка 0.14 не дала архива; её отчёт не является результатом этой сборки. В этой поставке действительно реализованы и проверены локальный запуск **трёх оригинальных процессов TACTIC за одним шлюзом**, общие сессии, контроль процессов и заполнение выбранных ячеек через существующий буфер таблицы.

Ядро остаётся `5.0.0.a02`; исходный commit `17c78e0dfb20a6fef16d70df6aa7b0c9bf20a596`. `NATIVE_UI_VERSION=0.14`. В комплекте прежний Vue **3.5.13** и готовая сборка из 40 SFC. Это не заявление о последней версии Vue. Админка, sidebar, таблицы, формы и обработчики по-прежнему используют исходный `widget_config`, XML и команды TACTIC. Новая прикладная модель или копия рабочих таблиц не создаётся.

## 1. Обновление и запуск трёх процессов

**Не удалять `local_data`, не выполнять INIT заново и не повторять SETUP/UPGRADE ради этого этапа.** Ранее необходимые исправления схемы должны быть уже выполнены; эта версия не отменяет CHECK_LOCAL_DB и не ставит отметку `upgraded` вручную. Остановить прежний сервер и сохранить резервную копию данных/репозитория. Распаковать новое дерево отдельно.

Из НОВОГО корня `TACTIC-5.0`, подставив фактические пути к уже работающим Python и данным:

```bat
set "TACTIC_PYTHON=D:\TACTIC_OLD\TACTIC-5.0\.runtime\python\python.exe"
set "DATA=D:\TACTIC_OLD\TACTIC-5.0\local_data"
START_CLUSTER.bat --data-dir "%DATA%" --port 9123 --workers 3
```

Открыть `http://127.0.0.1:9123/tactic/admin/`. После обновления — Ctrl+F5. Используется настоящий администратор TACTIC. Прежние разрешения записи/загрузки берутся из `<data-dir>/config/native-ui.json`; они не включаются новой сборкой автоматически. Данные и Python могут находиться в разных старых каталогах.

При внешней конфигурации сохранить свой аргумент:

```bat
START_CLUSTER.bat --config "D:\TACTIC_TEST\config\tactic-conf.xml" --data-dir "D:\TACTIC_TEST" --port 9123 --workers 3
```

По умолчанию `--workers 3`, допустимо 2–8. Шлюз слушает 9123; три TACTIC — 9124, 9125, 9126, все только на `127.0.0.1`. Другой диапазон задаётся `--worker-base-port 9200`. Все порты должны быть свободны и не пересекаться. Это **четыре OS-процесса: три TACTIC плюс supervisor/HTTP-шлюз**, не три потока одного сервера. Node, Apache, Redis и отдельный прокси устанавливать не нужно: шлюз использует уже включённый Cheroot.

Остановка всей группы — **Ctrl+C в окне START_CLUSTER**. Для однопроцессного режима оставлен прежний:

```bat
START_TACTIC.bat --data-dir "%DATA%" --port 9123
```

Нельзя одновременно запускать standalone и cluster на одном каталоге данных. Для offline-обновления БД остановить ВСЮ группу. Не открывать внутренние порты в интернет. `portal/auto_upgrade=true` в XML-конфигурации запрещает запуск группы: миграция должна выполняться отдельно при остановленных процессах. Linux-launcher требует непривилегированного пользователя, запуск от root отклоняется.

Все прежние BAT сохранены; добавлен только `START_CLUSTER.bat`. Загрузчик Python/pip, URL, зависимости и штатные seed-базы не изменены. **Windows BAT/PowerShell здесь не исполнялись**; изолированный embedded Python и Windows-блокировка проверены по коду, не запуском Windows. Совместимость всех установок из этого не следует.

## 2. Как распределяются запросы

Шлюз балансирует round-robin между здоровыми процессами **только явный список native GET-операций и `POST /api/ui/v2/query`**. Таблицы используют POST, поэтому балансировка лишь GET не распределяла бы основную выборку. Прочие POST/PATCH/PUT/DELETE, вход/выход, legacy/RPC и неизвестные пути проходят через процесс **1** и последовательную очередь шлюза.

Это граница маршрутизации HTTP, а не замена исходного Search/Command/Transaction или произвольной логики внешних плагинов. Read-worker не получает другую DB-роль: исходные методы могут иметь служебные записи. Заявление «никакой код reader никогда не пишет» не делается. Запросы из внешних программ, подключённых к БД напрямую, этой очередью не управляются.

В SQLite по-прежнему один писатель в один момент. Три процесса позволяют обслуживать независимые запросы в отдельных интерпретаторах, но не дают три параллельные SQL-записи или гарантированное ускорение втрое. WAL и структура пользовательских баз не менялись. Для нескольких машин, PostgreSQL-кластера и публичного HA-развёртывания эта локальная группа не является готовой системой.

Исходные XML-RPC/DCC-маршруты сохранены и направлены на ведущий процесс; проверены оригинальные get_ticket/ping через шлюз. Для исходного lazy REST redispatch сохранён приватный заголовок loopback-запроса; в группе этому внутреннему запросу запрещено следовать перенаправлениям. **Все произвольные legacy/RPC/custom операции отдельным прогоном не покрыты.**

### Сессии

Native-сессии разделяют приватное локальное `sessions.sqlite3` внутри `<data-dir>/native-cluster/<run-id>/`. Это техническое хранилище HTTP-сессий, **не новая база проектов или новая таблица пользователей**. В нём хранится исходный TACTIC ticket, который проверяется настоящим `XmlRpcInit` при запросе. В браузер ticket не выдаётся; cookie хранится в хранилище по хешу. Срок сессии — 8 часов, максимум 1000, общий лимит попыток входа — 10/минуту на адрес. Все запросы локальны, поэтому пользователи данного gateway разделяют один IP-лимит.

Перезапуск одного worker сохраняет вход; выход отзывает сессию у всей группы. **Полный перезапуск группы требует входа заново**: новая группа получает новый run-id и store. После штатной остановки session-файлы удаляются. После аварии старый приватный каталог может остаться; автоматическое восстановление его сессий не выполняется. Защитить весь каталог данных правами ОС: Windows наследует ACL каталога, chmod не заменяет Windows ACL.

### Фоновые задачи и кэши

FirstRun выполняет только ведущий процесс. Регистрация периодического scheduler также только у него; первичный запуск и замена writer не запускают отдельный scheduler в readers. **Оригинальные бизнес-триггеры и WebInit остаются в каждом процессе**, чтобы обычные команды не теряли workflow. В cluster используется исходный базовый режим CacheStartup вместо full process-cache; инициализационное удаление старых tickets не повторяется в каждом worker. Обычный standalone сохраняет прежнее поведение.

## 3. Сбои и блокировки

У supervisor отдельная эксклюзивная owner-блокировка. Все процессы группы удерживают совместную lifetime-блокировку установки; standalone и offline-upgrade требуют эксклюзивную. Перед запуском новой группы выполняется эксклюзивная проверка, поэтому она не начинает работу поверх ещё живых детей прежнего supervisor. **Старые версии launcher не знают новых блокировок — их обязательно остановить вручную.**

Упавший worker перезапускается в той же роли и на том же порту. Ведущий не заменяется произвольно одним из readers. Если он недоступен, новые записи получают 503 до отправки. При потере ответа от уже отправленной команды возвращается 502/ошибка потока: **результат может быть неизвестен, автоматического повтора нет даже для чтения**. Проверить запись/версии перед ручным повтором. Exactly-once для внешних эффектов и всех команд не обещается.

Health-проверка — раз в секунду, timeout 1 секунда; перегруженный процесс может временно считаться недоступным. Работающий, но зависший процесс не убивается автоматически: это не средство принудительного завершения долгой команды. Повторные реальные падения ограничены пятью restart за 60 секунд, затем останавливается вся группа. У worker watchdog: если heartbeat supervisor устарел примерно на 20 секунд, worker завершится, освобождая lifetime-lock. Во время аварии сохранение может остаться с неизвестным результатом, а не повторяется.

Шлюз — единая точка входа/отказа. Нет WebSocket, HTTP Upgrade, входных chunked bodies, HTTPS/TLS и внешнего bind. Тела ограничены 32 МиБ на запрос; существующие части resumable uploads по 4 МиБ укладываются. Это не уменьшает файловый лимит очереди до 32 МиБ. Потоки передаются блоками по 64 КиБ. Параметр `--timeout` (10–3600, default 300 секунд) относится к ожиданию upstream; увеличение не делает команду обратимой при сбое.

Внутренние HTTP-порты требуют приватный заголовок supervisor. Внешние forwarded/служебные заголовки от клиента удаляются. Проверенный public Host сохраняется, чтобы Origin/CSRF проверялись относительно единого адреса. Host ограничен localhost/127.0.0.1 и выбранным портом. Исходные права и CSRF не отключены.

Приватные логи worker могут содержать диагностические данные исходного TACTIC, включая tickets/аргументы. Не публиковать их целиком. В архив с отчётами **не включены** сырые worker logs, рабочие сессии или временные базы. File-lock сценарии проверены на Linux/local FS; Windows LockFileEx и сетевые NFS/SMB здесь не проверены.

## 4. System Info

Штатный `system_info` продолжает открываться по widget_config. В его панели добавлены **три PID, роль, доступность, принятые запросы, текущие запросы и число рестартов**, время обновления и процесс, ответивший на текущий запрос. Есть ручное обновление; новые постоянные кнопки в таблицы не добавлены. Статус — диагностика группы, не проверка целостности БД. `/__cluster/health` возвращает локальную краткую готовность без конфигурационных секретов.

## 5. Заполнение ячеек и создание/редактирование

В меню выделенных строк и `Правка` добавлено **«Заполнить выбранные ячейки…»**. Выбрать поле из исходной конфигурационной таблицы, ввести значение через существующий `FieldInput`, получить предпросмотр для каждой строки. Для каждого объекта разрешается свой оригинальный CellEdit/edit_item, допустимые значения и ревизии. Одно значение не считается автоматически подходящим всем строкам.

```text
Выделение → поле/значение → серверный предпросмотр → применить в буфер
                                                           ↓
                                  исходный Save Changes / EditMultipleCmd
```

Предпросмотр проверяет типы, права, конфигурацию и известные поддержанные обработчики, **не выполняет команды сохранения**. Конечные validation/action/trigger TACTIC срабатывают только при Save Changes. Не следует считать preview доказательством успешности произвольных custom actions. Неперенесённые редакторы не пропускаются молча.

Применение в буфер выполняется целиком: если последняя JSON-ячейка невалидна или черновик изменился после preview, первые строки не попадают в частично применённое состояние. Прочие набранные поля сохраняются; исходные записи не мутируются. Числа за пределом точности JavaScript и явный NULL сохраняют свой смысл. Лимит 100 выбранных записей; старый общий лимит 1000 изменённых ячеек действует при Save.

Сохранение по-прежнему одно `/table-changes` → оригинальный `EditMultipleCmd`/update_multi/общая DB-транзакция. Нет нового SQL-UPDATE или немедленной записи из Fill. Проверены rollback исходного NonEmptyAction, конфликты, повторное чтение и связь с настройками каждого редактора. Это **не полный перенос Excel Paste/Fill Down, custom callbacks или inline insert новых строк**.

В общей ConfiguredForm добавлена защита от двух submit в одном JS-такте: одна отправка, отдельный снимок данных, снятие busy после ответа/ошибки. Это защита интерфейса от двойного клика, **не долговечная идемпотентность создания и не разрешение автоматически повторять POST после сетевой ошибки**. Создание по-прежнему через исходный Insert/EditWdg и команды. Sidebar, отображение ячеек, меню и компактная панель 0.13 сохранены.

Login/password, ticket, Search/SObject, команды, транзакции и persistence настоящие. **Только проверка подписи лицензии явно изолирована `--isolate-license` в тестовом процессе**. **Windows BAT/PowerShell, PostgreSQL/MySQL, HTTP TLS, все пользовательские плагины, сетевые диски, реальные нагрузки/файлы 2 ГиБ и вся legacy API-матрица не проверены.** Внешний тестовый `cgi.py` не включён в поставку. Новый XML-RPC smoke сначала передал неверный plain ticket вместо оригинального словаря stub; исправлен тестовый конверт, не API TACTIC. Эти неуспешные попытки не смешаны с финальными результатами и не выданы за дефекты рабочего кода.

## 7. Воспроизведение и состав

В developer-окружении (Node/Playwright/Chromium только для сборки/тестов):

```bat
python -W ignore -m unittest discover -s tests/native_ui -v
node tests/native_ui/test_grid_state_012.cjs
node tests/native_ui/test_table_toolbar_013.cjs
node tests/native_ui/test_fill_state_014.cjs
node tools/native_ui/build.cjs
python tools/native_ui/audit_config_parity.py --out config-parity.json
python tests/native_ui/run_cluster_014.py --output D:\TEMP\tactic014-check --chromium C:\path\chrome.exe
```

Последний runner не принимает рабочую БД: создаёт и удаляет свою временную установку. Добавлять `--isolate-license` только в изолированном CI без криптографических зависимостей; `--bridge` только при реальном запрете прямой навигации. Production START_CLUSTER не принимает эти тестовые флаги. На Linux запускать тесты от непривилегированного пользователя с правом записи в своё дерево тестирования.

Карта изменений — `SOURCE_MAP_014.md`; diff относительно фактической .13 — `changes-from-0.13.patch` и JSON. Состав и SHA-256 — манифест упаковки. **Полный перенос всех виджетов, custom actions, обычных ролей, расширенного planner/review, multisite и полноценного headless ядра не завершён.** Существующие ограничения сохраняются. Старые `src/tactic/ui`, `src/pyasm/widget`, `src/pyasm/web` удалять нельзя.

Для возврата к одному процессу остановить cluster и использовать START_TACTIC; для legacy — START_LEGACY. Это не откат записанных данных. Для отката исходников использовать 0.13; данных/файлов — свои резервные копии. Архив не содержит runtime, пользовательских паролей/БД/сессий, тестовых installation/payload, caches/pyc/.git и файлов шрифтов. Исходные seed-базы сохранены побайтно.
