# TACTIC 5.0 — Vue source fork 1.1

Полное дерево исходников на основе **1.0**. Ядро остаётся `5.0.0.a02`, первоначальный commit `17c78e0dfb20a6fef16d70df6aa7b0c9bf20a596`. `NATIVE_UI_VERSION` — `1.1`; Vue — прежний `3.5.13`, готовая сборка включена. Загрузчик Python/pip и зависимости не обновлялись.

Этот этап исправляет проверенные проблемы **Global → специальные виджеты, общая таблица/форма, pipeline и schema**. Полной совместимости каждого custom-виджета и пункта legacy пока нет. Впервые этот набор проверялся не только с synthetic fixture: поднят исходный CherryPy/TACTIC, использованы полные копии штатных SQLite-баз, настоящий вход по паролю, исходные модели и команды. В тестовом процессе явно изолирована только проверка подписи лицензии; в production она не отключена.

## 1. Обновление существующей установки

**Не удалять `local_data`, не выполнять INIT заново, не переустанавливать рабочий Python.** Распаковать 1.1 отдельно. Остановить ВСЕ старые процессы TACTIC и другие программы, открывшие SQLite. Сохранить резервную копию данных и файлов.

Из НОВОГО корня `TACTIC-5.0` в cmd, подставив свои реальные пути:

```bat
set "TACTIC_PYTHON=D:\TACTIC_OLD\TACTIC-5.0\.runtime\python\python.exe"
set "DATA=D:\TACTIC_OLD\TACTIC-5.0\local_data"

CHECK_LOCAL_DB.bat --data-dir "%DATA%"
```

**Для старой управляемой SQLite может потребоваться UPGRADE**, в отличие от инструкции 1.0. Найдена ошибка прежней схемы: `id serial PRIMARY KEY` не выдаёт автоматический `id` в SQLite. В отчёте CHECK это `identity_issues`, код возврата 3. Для неё выполнить из НОВОГО дерева:

```bat
UPGRADE_LOCAL_SQLITE.bat --data-dir "%DATA%"
CHECK_LOCAL_DB.bat --data-dir "%DATA%"
```

UPGRADE требует подтверждения `UPGRADE`, создаёт backup, работает на отдельных копиях, проверяет результат и только затем устанавливает файлы. Первый CHECK с кодом 3 не объединять с UPGRADE через `&&`. Не менять вручную флаг `upgraded`. Если CHECK уже успешен и `identity_issues` отсутствуют, повторное обновление ради интерфейса не требуется.

Далее явно разрешить нужные записи в уже выбранной тестовой установке:

```bat
CONFIGURE_NATIVE.bat --data-dir "%DATA%" --writes on
START_TACTIC.bat --data-dir "%DATA%" --port 9123
```

CONFIGURE требует `ENABLE`, не пишет в БД, но меняет режим приложения. Для check-in дополнительно `--uploads on`. Для возврата к чтению — `--writes off`. Сервер после изменения настроек перезапустить.

Адрес: `http://127.0.0.1:9123/tactic/admin/`. Настоящая учётная запись администратора. Node/npm для обычного запуска не нужны. BAT запускать из 1.1; данные и Python могут находиться в разных прежних каталогах.

### Настройки больше не теряются при распаковке новой версии

Source-файл `src/tactic/ui_api/config.json` по умолчанию остаётся:

```json
{"site":"", "allow_writes":false, "allow_uploads":false}
```

Новый helper сохраняет явно выбранные администратором параметры в **`<data-dir>/config/native-ui.json`**. Они переопределяют source-настройки; предыдущая версия файла сохраняется как `.previous`. Это только конфигурация транспорта native UI, не замена `widget_config` или `tactic-conf.xml`. Обычные права TACTIC и проверки операций остаются включёнными. Отключённая запись теперь объясняется в интерфейсе, а не выглядит как сломанная кнопка.

При использовании своей PostgreSQL/MySQL-конфигурации сохранить прежний `--config` и `--data-dir`. **Managed SQLite UPGRADE к PostgreSQL/MySQL не применять.** Новое исправление идентификаторов относится к SQLite; эти серверные СУБД в данной поставке не тестировались.

## 2. Каждый штатный пункт Global

Список не зашит во Vue: берётся из `_global_admin` в исходном DEFAULT и разрешённых переопределений `widget_config`. В штатной конфигурации **13 ссылок**. Они проверены через настоящий backend и в браузере. Дополнительные пункты из пользовательской рабочей БД не объявляются проверенными без этой конфигурации.

| Пункт | Источник / что работает | Ограничение |
|---|---|---|
| Projects | `sthpw/project`, исходный `table`, фильтры и `ProjectWdg` database/version | Создание через общий плюс запрещено самим view; preview ещё не полностью перенесён |
| Template Projects | Исходный `template`, фильтр шаблонов, те же модели | `ProjectTemplateUpdateWdg` / упаковка шаблона ещё не реализованы |
| Users | Оригинальные insert/edit, LoginAction, PasswordAction, чтение, создание/редактирование и inline | Встроенный admin защищён от смены логина/пароля этим generic UI |
| Groups | Оригинальные формы, исходный `add_to_project`, участники, доступ и XML HiddenRow | Drag/drop старого DropElementWdg не повторён; назначения через специальную панель |
| Users In Groups | Настоящий UserAssignCbk и `login_in_group`, выбор группы и участников | Не полная визуальная эмуляция старого planner |
| Global Translations | `sthpw/translation`, исходные поля/формы и команды | Все custom локализационные widgets не заявляются |
| Exception Log | Исходный журнал, view и фильтры | Создание выключено исходной ссылкой |
| Debug Log | Исходный журнал | Создание выключено исходной ссылкой |
| Widget Settings | `sthpw/wdg_settings`, реальная конфигурационная таблица | Исходное ограничение вставки сохраняется |
| License | Отдельный License Manager: исходные метаданные, выбор файла Renew | Успешная проверка подписи/замена здесь не подтверждена; v1 с pickle не принимается |
| System Info | Исходные данные и прежняя диагностика структуры | Не административный shell и не миграция из браузера |
| System Config | Отдельный Vue-редактор `DbConfigWdg` / `DbConfigContentWdg`, реальный XML файл | После сохранения ручной restart; bootstrap/создание директорий не выполняются |
| Database Resource | Исходные формы, пароль write-only, `projects` HiddenRow и `add_project` EditWdg | Добавление — регистрация исходной ссылки на базу, не создание/миграция базы |

### System Config

Перенесены семь исходных групп: Database Setup, Installation, Asset Management, Mail Server, Services, Look and Feel, Security. Имена ключей и секций взяты из `db_config_wdg.py`. Существующие дополнительные checkin aliases также отображаются. Чтение — из активного `Config.get_config_path()`, запись — только изменённых разрешённых ключей.

Сохраняются чужие секции, атрибуты, комментарии и CDATA. Невалидный XML, внешние сущности, неоднозначные дубли и неверные типы отвергаются. Перед записью сверяется SHA-256 исходного файла, создаётся приватная побайтная копия, затем выполняется atomic replace. Это не межпроцессная транзакция с произвольным внешним редактором файла.

Пароли не возвращаются в JSON: виден только факт настройки. Пустое поле оставляет существующий секрет. Отдельное удаление существующего секрета через UI пока не реализовано. Новый текстовый редактор не выдаётся за идентичную реализацию всех прежних кнопок bootstrap/restart.

### License

Читаются исходные `License.get_data`, `get_current_users`, `get_message`, `is_licensed`. Ключи и подписи клиенту не выдаются. Команда `RenewLicenseCbk` вынесена в `tactic/core/license_commands.py`; старый путь её реэкспортирует.

При замене сначала вызывается **настоящий `License(..., verify=True)`**, и только затем исходный `RenewLicenseCbk` с проверкой ревизии. Поддержан подписанный XML v2. Legacy v1 использует pickle и требует отдельного переноса, endpoint отказывает до его исполнения. Никакого обхода лицензирования в рабочем коде нет. В текущей среде отсутствует Cryptodome, поэтому успешный криптографический сценарий не заявляется.

## 3. Общие таблицы и формы — реальные ошибки и исправления

В 1.0 было не только намеренное read-only по умолчанию. Существовал общий запрет на системные типы, который не снимался для исходных административных форм; JSON-значения не полностью попадали в исходные action handlers; новые специализированные компоненты не были подключены к корневой диспетчеризации `App.vue`.

Теперь для проверенных Users/Groups/Database Resource доступны только разрешённые исходные поля и обработчики. Блокировки ticket/trigger и остальных специальных системных типов не сняты глобально. Истинный `show_insert=false`, права поля и read-only view продолжают действовать.

`NativeEditCmd` на время исполнения предоставляет **валидированные** JSON-значения через WebContainer, чтобы исходные LoginAction/PasswordAction и action группы могли прочитать связанные поля. После успеха или исключения предыдущие form values восстанавливаются. Исходный NonEmptyAction по-прежнему проверяет непустое поле; он не подменён обычной записью. Native-контекст регистрирует исходный TacticServerStub с текущими ticket/project/site.

Форма создания отправляет исходные defaults вместе с изменёнными значениями; обычный TextWdg отображается как однострочное поле, PasswordWdg — как пароль. Существующий пароль не подставляется назад. Изменение и inline используют тот же путь валидации и команд; устаревшая ревизия даёт конфликт без стирания набранного текста.

У таблиц сделана более плотная сетка. Отдельные виджетные ячейки не превращаются в сырые строки: участники группы, User Assign, Global Rules, Access Rules HiddenRow, проекты Database Resource и ProjectWdg имеют native-представления. Пользовательский JavaScript из `cbjs_action` не исполняется: для двух штатных кнопок проверяются точные нормализованные определения и используются соответствующие операции. Другие callbacks не маскируются этим сопоставлением.

Нажатие на HiddenRow открывает вложенную конфигурационную таблицу; её область ограничена записью или настоящим отношением Schema. В action передаётся исходный target, а не произвольное описание виджета от браузера.

**Не все специальные колонки всей системы перенесены.** Preview/сложные expressions, весь Save All буфер, каскадный DeleteWdg и неизвестные пользовательские display/action handlers остаются отдельными задачами. Успешные проверки обычных форм не означают автоматическую совместимость произвольного Python/JS widget.

## 4. Pipeline и Schema

Исправлены разные причины, которые раньше давали одинаковое впечатление «ничего не работает»:

- Основная вкладка теперь передаёт GraphEditor исходный target, как вложенный WidgetHost.
- Исходный параметр `pipeline` — **начальный выбор**, а не запрет выбрать другой граф. Он больше не используется как ограничение доступа. Права и принадлежность проекту проверяются отдельно.
- Конфигурация source-only schema читается через оригинальный `Schema.get`, даже когда записи `sthpw/schema` ещё нет. Встроенные admin/sthpw/unittest остаются read-only, поскольку сам TACTIC берёт их из исходников.
- Для рабочего проекта первое сохранение создаёт исходную schema-запись, последующие сохраняют её XML. Создание/миграция колонок этим графом не выполняется.
- При работе администратора с pipeline другого проекта `config/process` разрешается в контексте проекта-владельца. Контекст и stub восстанавливаются после операции.
- В форму нового pipeline возвращён выбор SearchType, пустые списки и начальное открытие обрабатываются явно.
- Изменённые свойства узла считаются несохранёнными. «Сохранить граф» применяет их, даже если отдельная кнопка Apply не нажата. Ошибка разбора не выбрасывает введённые значения. Поздний ответ старого запроса не подменяет текущий граф.

На оригинальных моделях проверены создание pipeline, два процесса, связь, сохранение через **PipelineSaveCbk/ProcessInfoCmd**, повторное чтение XML и `config/process`, а также сохранение из admin с правильным владельцем. Проверено реальное сохранение schema на тестовом проекте.

Исходная PipelineSaveCbk синхронизирует определения процессов, включая удаление устаревших. Проверки использования процессами задач/runtime-состояний сохраняются. Глобальные сложные переименования с историей, все advanced property panels и DDL редактор схемы не объявляются готовыми.

## 5. Почему потребовалась ещё одна поправка SQLite

В прежнем результате апгрейда у шести таблиц остался `id serial PRIMARY KEY`: `spt_client_trigger`, `spt_ingest_rule`, `spt_ingest_session`, `spt_plugin`, **`spt_process`**, `spt_url`. SQLite принимает такой DDL, но вставленная строка получает `id=NULL`. Оригинальная команда после insert не находила созданный процесс по ожидаемому идентификатору.

Исправление находится **в offline staged-upgrade**, не в запросе Vue и не в автоматическом INSERT retry. Декларация становится `INTEGER PRIMARY KEY AUTOINCREMENT`. Пустой id получает уже существующий ROWID. Сохраняются rowid, заполненные совпадающие id, значения и SQLite storage classes, индексы, триггеры. Конфликтующие/нечисловые идентификаторы, составные ключи, custom views и неоднозначный DDL останавливают обновление без установки его копий.

Для уже обновлённой схемы не запускаются заново 402 старых метода. Выполняются проверка/ремонт ключей и прежняя проверка целостности. После успешного ремонта повтор — ноль исторических методов и ноль перестроений. Пользовательские XML-конфигурации и резервные копии проверены на сохранность.

Это не универсальная починка любых повреждённых связей или всех исторических SQL-схем. Старые процессы не знают нового cooperative lock: остановка всех серверов и инструментов обязательна. Восстановление прерванной установки — прежний `RESTORE_LOCAL_SQLITE`, не автоматический откат после дальнейшей работы пользователей.

## 6. Что действительно проверено

Точные текущие результаты находятся в `docs/native-ui/1.1/validation/`; промежуточные failed-прогоны не считаются итоговыми.

1. **Регрессия:** 921 unit-тест, 322 HTTP-сценария, 212 browser-сценариев; сравнение 80 XML/487 views/11370 свойств. Это прежний изолированный synthetic harness, отдельный новый сервер для каждого набора.
2. **Оригинальный сервер:** 83 HTTP-сценария + 42 браузерных. Полные временные копии seed, настоящий FirstRunInit/CherryPyStartup, пароль и ticket TACTIC, реальные SQLite/модели/NativeEditCmd/UserAssignCbk/PipelineSaveCbk. Один отдельный test installation для последовательного HTTP→browser пути; это не рабочие данные пользователя.
3. **Полный staged-upgrade:** исходный seed (402 метода), эмуляция старого результата 1.0 (6 SERIAL таблиц и реальные записи), ремонт (0 исторических методов), повтор (0). Отдельно 11 проверок сохранности данных/backup/повторяемости.

Общее число HTTP — 405, browser — 254, но **важно различать два backend-а**, а не считать все эти проверки сквозными. Unit SQL-тесты тоже не приравниваются к полному серверу.

В original-server тесте используется явный `--isolate-license`: только проверка подписи лицензии заменена в тестовом процессе. Подлинность подписи/успешная замена лицензии не доказаны. Аутентификация, Search, SQL, команды, серверные записи и файловая конфигурация не заменены fixture-объектами. Production не импортирует этот test harness и не выключает криптографию.

Прямая навигация Chromium была попробована и заблокирована (`native-navigation.log`). Браузерные сценарии используют явно включённый HTTP bridge, поэтому нативные cookies/CSP/navigation им не доказаны. Cookie/CSRF/Origin проверяются настоящими HTTP-запросами. Новые скриншоты помечены **ORIGINAL TACTIC + SQLITE SEED / TEST DATA / isolated signature / HTTP bridge**: реальные модели, но специально созданные записи, не база пользователя.

**Windows BAT/PowerShell, фактическая загрузка окружения и PostgreSQL/MySQL здесь не проверялись.** Есть настоящее выполнение исходного сервера на Linux/Python 3.13 с указанной изоляцией лицензии, не подтверждение всех установок. Внешний `cgi.py` использовался только в окружении тестирования и не упакован.

Повторение в developer-окружении:

```bat
python tests\native_ui\run_validation_11.py --output docs\native-ui\1.1\validation\repeat --chromium "C:\path\to\chrome.exe"
python tests\native_ui\run_original_11.py --output docs\native-ui\1.1\validation\original-repeat --chromium "C:\path\to\chrome.exe"
python tests\native_ui\run_identity_upgrade_11.py --output docs\native-ui\1.1\validation\identity-repeat
```

Последние два runner создают только временные установки, не принимают путь к рабочей БД. `--isolate-license` добавляется явно только для CI без криптографии. `--bridge` — только при реальном запрете прямой навигации, не по умолчанию. Для обычного запуска тесты и Node не нужны.

## 7. Границы и состав

Вход остаётся admin-only. Не заявляются все пользовательские классы, весь Global template/preview/advanced функционал, полная plugin/review админка, multiworker/multisite или полное headless-ядро. Чтение конфигурационного sidebar не доказывает реализацию каждого возможного обработчика внутри него.

`START_LEGACY.bat` возвращает прежний рендерер, не откатывая данные. Не удалять `src/tactic/ui`, `src/pyasm/widget`, `src/pyasm/web`. Для отката исходников — предыдущий архив, для данных — проверенные резервные копии.

В поставке есть source map, актуальная матрица Global, `changes-from-1.0.patch`, файловые хеши и отчёты. Старые отчёты 0.x–1.0 остаются историческими. Нет `.runtime`, рабочих/private test баз и конфигов, паролей пользователя, кешей/pyc, font-файлов. Штатные исходные seed-базы сохранены побайтно.
