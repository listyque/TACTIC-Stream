# TACTIC 5.0 — native Vue source fork 0.8

Полное дерево исходников — продолжение 0.7. Этот этап исправляет **SETUP_ENV и управляемый локальный SQLite-upgrade из присланного лога**, а также расширяет штатный экран System Info диагностикой структуры. Новая БД приложения, альтернативные таблицы задач и жёстко заданный sidebar не создаются. Предыдущие конфигурационные таблицы, формы, фильтры, коллекции, сообщения, файлы и остальные перенесённые функции сохранены.

Ядро: `5.0.0.a02`, первоначальный commit `17c78e0dfb20a6fef16d70df6aa7b0c9bf20a596`. Нативный UI: **0.8**. Vue в поставке — **3.5.13**, готовая сборка включена. Полный перенос всех виджетов TACTIC всё ещё не завершён.

## 1. Исправление загрузчика

Исправлен конкретный URL закреплённого pip zipapp:

```text
https://bootstrap.pypa.io/pip/zipapp/pip-26.2.1.pyz
```

Это файл из указанного пользователем каталога `https://bootstrap.pypa.io/pip/zipapp/`, а не сама HTML-страница каталога. Наличие файла подтверждено по официальному индексу PyPA. В этой среде бинарный файл заново не скачан: сетевой доступ из рабочего контейнера не позволил получить его. Полный Windows SETUP здесь не исполнялся.

Перед запуском проверяются размер, ZIP-структура, `__main__.py`, CRC и соответствие версии. При ошибке удаляется только невалидный управляемый pip-кэш; Python и базы не удаляются. После удаления повторите SETUP. Эти проверки не заменяют криптографическую подпись: заранее закреплённого SHA-256 pip по-прежнему нет, доверие к загрузке основано на HTTPS официального источника. Python проверяется по прежнему закреплённому SHA-256 и Authenticode; зависимости заданы прежними диапазонами, а не новым lockfile.

Исправлен поиск соседних модулей launcher/worker в изолированном embedded Python (`._pth`). Скрипты добавляют только свой `tools/local` явно. BAT запускают Python с `-X utf8` для Unicode-путей и логов. Node для обычного запуска не нужен.

## 2. Что случилось с апгрейдом в логе

Лог содержит **SQLite**, не MySQL: `SqliteConfigUpgrade`, `SqliteSthpwUpgrade`, `SqliteDefaultUpgrade`. Сообщение «no expiry on ticket for Sqlite and MySQL» общее и не определяет выбранный движок.

Проблемы не сводились к одной строке:

- У штатного seed не заполнен `last_version_update`; старые миграции пытаются повторить уже присутствующие объекты схемы.
- Старые/новые имена некоторых config-таблиц различаются (`widget_config` и `spt_widget_config`, аналогично naming/prod_setting/custom_script). У проектного seed недостаёт части этих таблиц.
- Исходный SQLite-конвертер не переводит ряд PostgreSQL-команд: `ADD/DROP CONSTRAINT`, `ALTER COLUMN TYPE`, `DROP NOT NULL`, `USING btree`.
- `fix_search_code.py` запускался shell-командой в дочернем интерпретаторе без настроенного `tacticenv`; код возврата игнорировался.
- Исходный апгрейдер мог записать новую версию проекта даже при ошибках. Следующий запуск уже нельзя было надёжно направлять только по этому значению.

**Исправление не состоит в отключении ошибок или ручной записи версии 5.0.**

## 3. Новый порядок локального SQLite-upgrade

`UPGRADE_LOCAL_SQLITE.bat` принимает только установку, ранее созданную `INIT_LOCAL_SQLITE`: соответствующий `local-install.json`, vendor Sqlite, собственный `db` и существующие зарегистрированные базы. Сторонний MySQL/PostgreSQL, внешние db_resource, нестандартные типы проектов, общие базы нескольких проектов, отсутствующие файлы и неоднозначные config-хранилища не принимаются автоматически.

Порядок:

1. Остановить серверы и инструменты, открывшие базу. Новый launcher и upgrader используют общий локальный OS-lock. Активный SQLite-журнал не удаляется и не игнорируется.
2. Создать резервные копии через SQLite backup API. Скопировать базы в отдельный staging-каталог внутри `local_data/backup/<date-id>/stage`.
3. Направить исходные миграции TACTIC на эти копии. При старой/ошибочной отметке версии выполняется проверяемый исторический проход. Прежние БД пока не заменяются.
4. Проверить результат: ошибки всех шагов, обязательная структура UI, `integrity_check`, `foreign_key_check`.
5. Сверить, что исходные базы и управляющая конфигурация не менялись параллельно. Только затем установить проверенные файлы, сохранив прежние файлы в `backup/.../original-files`.
6. Записать успешную отметку в `local-install.json` после установки всех файлов.

Миграционный worker использует **оригинальные upgrade-классы и их методы**. Для управляемого offline-прохода SQL исполняется через новый SQLite-адаптер. Миграция схемы не записывается в ещё не обновлённый `transaction_log`: каждый её метод выполняется в отдельной SQLite-транзакции. Это не меняет транзакционные обёртки обычных UI-команд, check-in и workflow.

### Перевод и проверка SQL

Уже существующие столбцы сохраняют значения. Индексы сверяются по таблице, полям, уникальности, полной/частичной области и collation. Уникальные ограничения не ослабляются: конфликтующие данные приводят к остановке, не к дедупликации. Старые имена config-таблиц разрешаются по настоящему `search_object`; параллельное пустое хранилище вместо существующего не создаётся.

Для нужных изменений SQLite-таблица перестраивается по последовательности create/copy/drop/rename. Проверяются значения **и SQLite storage class**, сохраняются rowid, индексы, собственные триггеры и autoincrement high-water mark. Строка `001` не превращается незаметно в число 1. `writable_schema` не используется. Неизвестные DDL, неоднозначные inline constraints, generated/hidden columns, затрагиваемые custom views и разрушительные операции с пользовательскими данными прекращают обновление. Это адаптер проверенных исходных миграций, не универсальный SQL-транспилятор.

`fix_search_code` теперь вызывается в текущем процессе. Заполненные search_code не затираются; отсутствующие заполняются по оригинальному parent search_type/search_id. Не найденный родитель — ошибка для разбора. История и архивные строки не исключаются. Общий original upgrade больше не ставит версию проекту с зарегистрированными SQL-ошибками.

### Сбой и восстановление

Обычная ошибка worker оставляет прежние файлы БД на месте. При ошибке установки нового набора выполняется возврат прежних файлов. Сбой процесса между заменой отдельных БД оставляет `.sqlite-promotion.json`; новый launcher отказывается запускать сервер до восстановления.

```bat
RESTORE_LOCAL_SQLITE.bat --data-dir "D:\TACTIC_TEST\local_data"
```

Нужно подтвердить `RESTORE`. Проверяются хеши и все файлы до восстановления. Если после сбоя данные изменены сторонним процессом или копия повреждена, автоматическое затирание запрещается.

Это команда **только для прерванной установки**, не откат уже работающей базы после новых пользовательских записей. Для обычного отката нужна осознанная работа с резервной копией. Журнал+lock проверены при аварийном завершении процесса на Linux; отключение питания, сетевые FS и Windows-ветка OS-lock здесь не тестировались. Старый сервер не знает нового cooperative lock: остановка всех старых процессов обязательна. Произвольные внешние эффекты пользовательских Python-классов/плагинов не покрыты этим тестом.

Конфигурация, пользовательские assets и templates не заменяются staged-копиями. Backup содержит копию конфигурации: храните его как приватные данные с теми же ограничениями доступа, что у исходной установки. Исправление не является автоматической миграцией чужой production-инсталляции или любого исторического варианта схемы.

## 4. Как повторить апгрейд из 0.6 / 0.7

**Не удаляйте существующий `local_data`, не запускайте для него INIT заново и не ставьте `state=upgraded` вручную.** Распакуйте весь 0.8 отдельно. Используйте BAT именно из нового дерева.

В командной строке, открытой в корне нового `TACTIC-5.0`:

```bat
rem Укажите существующий каталог данных старой установки:
set "DATA=D:\TACTIC_OLD\TACTIC-5.0\local_data"

rem Вариант A: скачать локальное окружение в новом дереве:
SETUP_ENV.bat

rem Вариант B вместо SETUP: использовать уже рабочий интерпретатор:
rem set "TACTIC_PYTHON=D:\TACTIC_OLD\TACTIC-5.0\.runtime\python\python.exe"

CHECK_ENV.bat
CHECK_LOCAL_DB.bat --data-dir "%DATA%"
UPGRADE_LOCAL_SQLITE.bat --data-dir "%DATA%"
CHECK_LOCAL_DB.bat --data-dir "%DATA%"
START_TACTIC.bat --data-dir "%DATA%" --port 9123
```

Вместо `D:\TACTIC_OLD` подставьте свой прежний путь. Перед UPGRADE остановите TACTIC. В первом CHECK_LOCAL_DB код **3** означает «ещё не готова» и ожидаем до успешного исправления; команда ничего не меняет. Не объединяйте этот первоначальный CHECK с UPGRADE через `&&`, иначе ожидаемый код 3 не позволит продолжить.

В логе пользователя импорты уже прошли успешно. Поэтому существующий совместимый Python можно оставить через `TACTIC_PYTHON`; перенастраивать системный Python не требуется. Путь к исходникам берётся из нового launcher, а не из старого runtime.

UPGRADE потребует `UPGRADE`. При ошибке покажет конкретный `backup/.../worker.log` и `upgrade-report.json`. Не запускайте сервер с ошибочной схемой и не удаляйте неудачную копию до разбора причины. Исходные зарегистрированные файлы должны существовать; пустая БД на месте отсутствующей не создаётся.

Адрес после успешного запуска: `http://127.0.0.1:9123/tactic/admin/`. Порт можно изменить. Нужна реальная учётная запись администратора. PostgreSQL-сервер SETUP не устанавливает.

### Совершенно новая локальная установка

Только для нового пустого каталога: SETUP → INIT_LOCAL_SQLITE → UPGRADE_LOCAL_SQLITE → CHECK_LOCAL_DB → START_TACTIC. Копирование/инициализация пароля и полноценная авторизация Windows-сервера здесь не проверялись; см. границы тестирования.

### Обычная существующая PostgreSQL-инсталляция

Прежний путь сохранён:

```bat
START_TACTIC.bat --config "D:\TACTIC_TEST\config\tactic-conf.xml" --data-dir "D:\TACTIC_TEST" --port 9123
```

Новый managed SQLite-upgrade **не** принимает этот вариант и не объявляется исправлением MySQL-миграций. Сам присланный лог относится к SQLite.

## 5. Продолжение UI: System Info

Штатная конфигурационная ссылка `system_info` / `tactic.ui.app.SystemInfoWdg` открывает расширенную системную панель. Sidebar и набор представлений не переписывались. В панели появились обязательные для перенесённого UI таблицы и поля текущего проекта и sthpw, различие между отсутствующей регистрацией, таблицей и колонками, текущая версия native UI.

Имена физических config-таблиц читаются из исходного реестра, не заменяются предположением «везде spt_». Метаданные запрашиваются реальными Search/DbContainer. Панель не возвращает пароли, DSN, licence keys, окружение или пути к файлам. Ошибки чтения метаданных обозначаются без выдачи чувствительного traceback.

**Кнопки запуска миграции из браузера нет.** Проверка read-only; флаг «обязательная структура найдена» не доказывает исправность всех пользовательских данных, прав, триггеров и файлов. Для базы, которую сервер ещё не может открыть, отдельный CHECK_LOCAL_DB работает до проверки криптографических/серверных зависимостей. Результат сохраняется в `.runtime/local-db-check.json` нового дерева.

Версия UI теперь берётся из `NATIVE_UI_VERSION`: исправлена прежняя устаревшая строка 0.4 в System Info. Build и `/health` используют тот же источник. `/health` по-прежнему не проверяет БД.

## 6. Проверки и ограничения доказательств

Точные текущие отчёты: `docs/native-ui/0.8/validation/`; карта изменений: `docs/native-ui/0.8/SOURCE_MAP_08.md`.

- Полные копии оригинальных **sthpw.db и unittest.db**: чистый seed и частично изменённый seed с ошибочной отметкой 5.0. По **402 исходных метода**, без зарегистрированных SQL-ошибок; повтор — **0** старых методов. Проверены структура, integrity/foreign keys, сохранность XML widget_config и хеши исходных backup-файлов. SQL и сами базы не эмулируются.
- В тестовом subprocess **только получение лицензии заменено заглушкой**, поскольку в контейнере отсутствует Cryptodome. Это явно записано в отчётах и включается тестовым флагом. Production worker не импортирует тестовый код, не отключает лицензию и не меняет авторизацию. Результат — проверка миграций/файлов, **не полноценного входа и запуска TACTIC**.
- SQL-rebuild, ошибки уникальности, конфликтующие данные, сохранность индексов/триггеров/rowid, отказ публикации, сбой второго rename, смерть процесса в середине публикации, поиск tacticenv, изолированный запуск и проверка pip-кэша имеют отдельные регрессии.
- Сравнение конфигураций: 80 штатных XML, 487 views, 11 370 сравнений; без расхождений в прежней области. Это не полное поведенческое покрытие всех Wdg.
- **768 unit-тестов, 253 HTTP-сценария и 157 браузерных сценариев** прошли в финальном прогоне. Точные результаты каждого набора — `validation/summary.json`. HTTP/browser запускают чистое тестовое хранилище для каждого набора, не рабочую PostgreSQL. Новая System Info-панель читает настоящие метаданные исходного seed, но auth/context в этом harness тестовые.

Прямая навигация Chromium заблокирована `ERR_BLOCKED_BY_ADMINISTRATOR`. Использован явный HTTP-мост; нативные cookies/CSP/navigation/WebCrypto этими браузерными проверками не доказаны. Скриншоты помечены TEST FIXTURE. Полный Windows BAT/PowerShell, фактическая загрузка окружения, рабочий PostgreSQL/MySQL, полная авторизация и пользовательские внешние callback-эффекты здесь не проверены.

Повтор developer-проверок:

```bat
python -W ignore -m unittest discover -s tests/native_ui -v
python tests\native_ui\run_validation_08.py --chromium "C:\path\to\chrome.exe"
python tests\native_ui\run_migration_08.py --output "D:\temporary-migration-test-report"
```

Последний runner по умолчанию использует настоящее получение лицензии и временные копии seed. Только для CI без криптографических зависимостей предусмотрен явный **тестовый** `--isolate-license`. Для запрещённой навигации у browser runner существует `--bridge`; по умолчанию он не включён. Инструменты тестов не заменяют START_TACTIC.

## 7. Пределы и откат

Вход native UI остаётся **admin-only**. Запись и загрузка по умолчанию **выключены** в `src/tactic/ui_api/config.json`. Это не распространяется на отдельный подтверждаемый offline schema-upgrade: он специально меняет структуру управляемой локальной базы. После проверки своей тестовой установки прежние allow_writes/allow_uploads включаются отдельно.

Все прежние ограничения multisite/multiworker, неперенесённых custom layouts/expressions/widgets, частей workflow/review/системной и плагинной админки, ресурсного планирования и расширенного check-in остаются. Старые `tactic/ui`, `pyasm/widget`, `pyasm/web` удалять нельзя. Этап 0.8 не добавляет новые сущности приложения и не претендует на завершение всех UI.

`START_LEGACY.bat` / `TACTIC_UI=legacy` переключает рендерер, но не откатывает данные и миграции. Для возврата исходников есть исходный архив 0.7; для БД — private backup. Не используйте автоматическое восстановление прерванной публикации как откат после продолжения работы.

Поставка не содержит `.runtime`, пользовательских баз/паролей, caches/pyc, тестовых payload и файлов шрифтов. Оригинальные seed-базы в `src/install/start` сохранены; изменялись только их временные тестовые копии.
