# TACTIC 5.0 — Vue source fork 0.16

Полный исходный форк **0.15**, не отдельный сайт и не накладка. Ядро остаётся `5.0.0.a02`, Vue — включённый `3.5.13`, 41 SFC, готовая сборка. Этот этап исправляет **диагностический журнал действий и исходные пути открытия специальных админских виджетов**. Новых зависимостей и миграций существующей БД нет. Пользовательские `widget_config`/WidgetSettings не сбрасываются.

## 1. Обновление

**Не удалять local_data. Не запускать INIT и не повторять SETUP/UPGRADE ради 0.16.** Сохраните резервную копию своей тестовой установки; остановите ВСЮ прежнюю группу. Распакуйте 0.16 отдельно и запускайте BAT из нового дерева с фактическими рабочими Python и данными:

```bat
set "TACTIC_PYTHON=D:\TACTIC_OLD\TACTIC-5.0\.runtime\python\python.exe"
set "DATA=D:\TACTIC_OLD\TACTIC-5.0\local_data"
START_CLUSTER.bat --data-dir "%DATA%" --port 9123 --workers 3
```

Пути здесь — примеры. При внешнем XML сохраните свой `--config`. Для одного процесса используйте `START_TACTIC.bat --data-dir "%DATA%" --port 9123`. Адрес: `http://127.0.0.1:9123/tactic/admin/`. После обновления выполните Ctrl+F5. Node для запуска не требуется. Остановка группы — Ctrl+C. Старые BAT и runtime manifest сохранены, доступность загрузок/Windows-исполнение заново не проверены.

Запись и uploads продолжают управляться `<data-dir>/config/native-ui.json`; обновление не включает их самовольно. Read-only не отменяется для демонстрации кнопки сохранения. Вход остаётся admin-only. Сессии/балансировка 0.14, DB-настройки интерфейса и проектный мастер 0.15 сохранены.

## 2. Pipeline/Schema — это не один тип страницы

Исходники содержат **разные функции**, которые нельзя свести к одному экрану:

| Исходный вход | Что должно открыться и что исправлено |
|---|---|
| `project_admin/project_workflow` | `PipelineToolWdg`, нативный GraphEditor. Проверены исходный полный class path и явные штатные короткие/module-пути. |
| `project_admin/project_schema` | `SchemaToolWdg`, граф схемы исходного текущего проекта. |
| `project_essentials/sthpw_pipelines` | Исходный `sthpw/pipeline`, view `manage`: **таблица**, содержащая отдельную кнопку `editor`. Кнопка теперь открывает GraphEditor в НОВОЙ ОСНОВНОЙ ВКЛАДКЕ, как исходный `spt.tab.add_new`, с выбранным search_key. |
| `project_essentials/sthpw_schema` | Исходный `sthpw/schema/manage`: **таблица** с кнопкой `create`. Она открывает SchemaToolWdg в основной вкладке для текущего проекта, как исходный callback с пустыми kwargs. |
| System Config / System Info / Script Editor / Users In Groups / Create Project | Проверены исходные handler/options и специализированный kind. Эти экраны не подменяются таблицей по наличию search_type. |

Ранее в двух management-таблицах отсутствовал адаптер штатного `ButtonElementWdg`. В первом браузерном прогоне нового адаптера найдено ещё одно расхождение: общий обработчик ячейки открывал popup вместо исходной основной вкладки. Исправлено именно расположение этих двух действий; HiddenRow, обычные popup-ячейки, назначение участников и вложенные таблицы сохраняют свои прежние контексты.

### Определения кнопок и разрешение классов

Кнопки сопоставляются с **точными нормализованными исходными определениями cbjs_action** из `pipeline-conf.xml` / `schema-conf.xml`, а не по одному названию поля. Хеши определений сверяются тестом. Пользовательский JavaScript не исполняется новым endpoint. Изменённый custom callback не получает произвольное поведение под видом штатного.

Для уже поддержанных редакторов добавлены только известные короткие имена и настоящие module paths TACTIC; произвольный сторонний `some_plugin.SchemaToolWdg` не сопоставляется по basename. Поля/опции/состав sidebar по-прежнему разрешаются исходным widget_config. Пользовательские записи в БД не переписываются ради исправления маршрута.

### Выбор и обновление pipeline

В `GraphService` восстановлено исходное начальное `search_key`: при нажатии кнопки строки выбран именно её pipeline, не первый по алфавиту. Проверяются исходный тип, владелец, проект, фильтр SearchType и архивный статус. Начальный выбор **не превращается в искусственный запрет** выбирать другие разрешённые pipeline. Явные native_fixed ограничения сохраняются.

Кнопка «Обновить» реально перечитывает GraphEditor, в том числе вложенный. Восстановление основных вкладок из исходного WidgetSettings хранит target ID и заново разрешает kind на сервере; тип редактора не берётся из произвольной сохранённой табличной формы.

Встроенная схема `admin` остаётся read-only, как в исходном Schema.get. Кнопка schema/manage в admin не начинает редактировать базу другого проекта лишь потому, что в строке указан другой code. Для изменения рабочей схемы нужно открыть соответствующий рабочий проект.

## 3. Содержательный журнал вместо одной строки доступа

Для native UI введены два **различимых** вида диагностических записей:

- `source=client` / `UI ...`: явное действие интерфейса — открытие/переключение/закрытие вкладки, меню, переход проекта, изменение/применение ячейки в буфер, Save, выбор/сохранение графа. Это сообщение о действии, **не доказательство выполнения команды в БД**.
- `source=server`: выполненный запрос — method, краткая операция, авторизованный пользователь/site/project, target, разрешённый исходный handler, native renderer, SearchType/view, безопасная форма фильтра/сортировки/страниц, количество строк, действительные классы команд, HTTP-результат, длительность и request_id.

Связь между ними — короткий `action_id`; каждый запрос имеет собственный серверный `request_id`. Клиентская корреляция — только диагностическая подсказка, не разрешение или авторизация. В ошибочном JSON тот же request_id, что и в логе.

**В файл не сериализуются тела запросов/ответов целиком.** Не собираются набранные значения полей, пароли, tickets, CSRF, cookies, тела скриптов/XML, фильтруемые значения, содержимое сообщений и файлов. У фильтров показаны поле/оператор и `(?)`, у сохранения — названия изменённых полей и количество записей. Это сознательно не дословный dump legacy API с его секретами.

Клиентская часть не слушает все клавиши/DOM-inputs, не записывает clipboard и не отправляет текст каждого нажатия. Подключены явные действия базовых перенесённых виджетов. Все произвольные неперенесённые callbacks и каждое движение мышью НЕ объявляются покрытыми. Очередь ограничена, передаётся пакетами, без повторов; сбой диагностического транспорта не повторяет и не блокирует бизнес-команду.

### Где виден журнал

**По умолчанию включён автоматически**, никаких изменений БД для этого не нужно.

В обычном START_TACTIC — читаемые строки в том же терминале и JSON Lines:

```text
<data-dir>/log/native-actions/actions-standalone.jsonl
```

В START_CLUSTER каждый worker пишет отдельный файл, а supervisor выводит эти структурированные записи в **общее окно запуска**:

```text
<data-dir>/native-cluster/<run-id>/actions/actions-1.jsonl
<data-dir>/native-cluster/<run-id>/actions/actions-2.jsonl
<data-dir>/native-cluster/<run-id>/actions/actions-3.jsonl
```

В строке видны worker и PID. Потоки запросов связываются идентификаторами, а не предполагаемым порядком строк разных процессов. Ротация — 5 МиБ и три резервных файла на worker. Tailer выдерживает частичные строки и смену файла/worker; это **диагностическая доставка**, не гарантированно без потерь при аварии/перегрузке и не юридически неизменяемый аудит.

Настоящие transaction/sobject/status logs TACTIC остаются отдельными. Сырые `worker-*.log` legacy не транслируются в общий терминал: они могут содержать чувствительные данные исходного ядра. Новый безопасный журнал не означает автоматическую очистку всех прежних логов. Каталог данных защищать правами ОС, на Windows действуют наследуемые ACL.

### Уровни детализации

В том же cmd **до запуска**:

```bat
rem По умолчанию: действия + запросы, без успешных служебных GET
set "TACTIC_ACTION_LOG=actions"

rem Также показывать успешные опросы session/health/ui-state/upload-status:
set "TACTIC_ACTION_LOG=verbose"

rem Отключить новый журнал и вернуть обычные access lines native API:
set "TACTIC_ACTION_LOG=off"
```

Выберите одну настройку. Уровни не включают запись секретов. `PATCH ui-state`, ошибки и бизнес-запросы не теряются в режиме actions. Ключевые действия локального буфера видны отдельно от окончательного POST/команды.

Дублирующие access-строки **native API** убраны, когда новый журнал включён. Legacy-службы, сообщения ошибок и остальное логирование не отключены глобально.

## 4. WARNING: site is empty

Причина повторяющегося предупреждения — безусловный `Site.set_site('')` при каждом native-запросе в штатной single-site установке. Для пустого site этот вызов теперь пропускается, после обычной инициализации и с прежним cleanup контекста. Для непустого site исходный setter продолжает работать. Это не присвоение выдуманного имени site и не глобальное отключение warnings.

Дополнительно исполняются прежние project-wizard/UI-state, таблицы/формы, Global, Fill и cluster-restart сценарии.

Браузер сначала пробует прямую навигацию. Здесь она блокируется ERR_BLOCKED_BY_ADMINISTRATOR, поэтому явно используется HTTP-мост к оригинальному backend. **Нативные browser cookies/CSP/navigation этим не доказаны. Windows BAT/PowerShell, PostgreSQL/MySQL, полный набор произвольных пользовательских конфигураций и внешних плагинов в этом этапе не проверялись.**

Повторение в developer-окружении:

Runner создаёт собственную тестовую установку и не принимает путь к рабочей БД. `--bridge` добавлять только при реальной блокировке прямой навигации, `--isolate-license` — только в изолированном тестовом CI. В runner есть пауза между сериями входов, чтобы не отключать/повышать настоящий security rate-limit ради тестов.

## 6. Состав и пределы

Полный source fork, compiled JS/CSS, исходные BAT и seed, source map, патч к 0.15, хеши, отфильтрованные результаты. Нет .runtime, рабочих/частных тестовых БД/паролей, сырых worker logs/tickets, .git, bytecode/cache и файлов шрифтов. Каталог новых логов создаётся только в пользовательском data-dir при запуске.

Не заявляется полный перенос каждой специальной админской операции, arbitrary JS/Python widgets, всех версий legacy-конфигураций из рабочей БД, multi-site/multi-machine или обычных пользовательских ролей. Неизвестные обработчики продолжают выдавать явную диагностику; новый request log показывает исходный handler/target/renderer для дальнейшего разбора. **Старые UI-каталоги не удалять.** START_LEGACY возвращает рендерер, а не отменяет записи в БД; откат данных требует своих резервных копий.
