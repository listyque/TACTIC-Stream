Полное дерево исходников, продолжение **0.8**. В этом этапе исправлен запуск с `NameError: name 'Api' is not defined`, устранены аналогичные зависимости от неявных `exec`-locals в разрешении виджетов, перенесён штатный редактор сохранённых скриптов. Отдельный сайт/новая БД не создавались. Sidebar и админка по-прежнему определяются оригинальными widget_config, project XML и definitions.

Ядро — **5.0.0.a02**, исходный commit `17c78e0dfb20a6fef16d70df6aa7b0c9bf20a596`. `NATIVE_UI_VERSION` — **0.9**. Комплект включает прежний Vue **3.5.13** и готовую браузерную сборку; это не утверждение о последнем релизе Vue. Полный перенос всех UI ещё не завершён.

## 1. Ваш случай: SETUP, INIT и UPGRADE уже прошли

**Не удалять local_data, не создавать базу заново и не повторять апгрейд ради этого исправления.** Последний присланный traceback относится к регистрации HTTP/XML-RPC-контекстов, а не к миграции схемы.

Распаковать 0.9 отдельно. Остановить старый TACTIC. Открыть командную строку в новом корне `TACTIC-5.0` и использовать существующие окружение/данные:

```bat
set "OLD=C:\Users\listy\Downloads\TACTIC_5_Vue_Source_Fork_0.8\TACTIC-5.0"
set "TACTIC_PYTHON=%OLD%\.runtime\python\python.exe"

CHECK_STARTUP.bat --data-dir "%OLD%\local_data"
START_TACTIC.bat --data-dir "%OLD%\local_data" --port 9123
```

`OLD` — путь из присланного лога; изменить его, если установка перемещена. **BAT запускать именно из 0.9**, не из прежнего каталога. Интерпретатор может остаться прежним: новые пути к исходникам настраивает новый launcher. Старый каталог данных/asset repository продолжает использоваться по существующей конфигурации.

Адрес после успешного запуска:

```text
http://127.0.0.1:9123/tactic/admin/
```

Вход — настоящий администратор TACTIC. Node для запуска не нужен. Сервер слушает localhost. Остановка — Ctrl+C.

Для внешней конфигурации прежний вариант сохранён:

```bat
START_TACTIC.bat --config "D:\TACTIC_TEST\config\tactic-conf.xml" --data-dir "D:\TACTIC_TEST" --port 9123
```

Перемещение исходников **не** меняет абсолютные пути внутри пользовательской конфигурации. Работайте с тестовой копией установки/данных; существующие резервные копии сохранить.

## 2. Причина Api NameError и исправление

В старом `CherryPyStartup.register_project` первый `exec` импортировал класс контекста, а следующий `exec` пытался найти этот класс по имени. На Python 3.13 неявные локальные пространства этих вызовов больше не работают как одно изменяемое хранилище. Исходный метод 0.8 воспроизвёл тот же `Api NameError` на Python 3.13.5 при алфавитном порядке контекстов, соответствующем логу Windows.

Исправлено **не понижение Python и не сокрытие исключения**:

- `context_registry.load_contexts` явно импортирует исходный модуль `tactic_sites.<project>.context.<Context>` / `sites.<project>.context.<Context>` и получает его экспортированный класс через `getattr`;
- контексты и страницы присоединяются через `setattr`; ни project/site, ни имя контекста не подставляются в исполняемый исходный текст;
- прежние классы `Api`, `XMLRPC`, `UploadServer` и остальные контексты сохраняются; фиктивный пустой Api не создаётся;
- ошибки импорта/конструктора не подавляются и сохраняют traceback;
- параметры XML-RPC применяются также к уже смонтированному CherryPy-приложению; для site используются правильные site-prefixed пути;
- исправлен общий изменяемый аргумент `need_upgrade`.

Проверены все **11 штатных default-контекстов** настоящего TACTIC, регистрация admin, site-префиксы и реальное конфигурирование XML-RPC в bundled CherryPy. В тесте использовались реальные объекты контекстов и метод регистрации, но не полный конструктор сервера с лицензией/БД/аутентификацией.

Большое количество `SyntaxWarning: invalid escape sequence` в консоли — отдельные предупреждения старого Python/встроенного JavaScript, а не причина последнего падения `Api`. Массовая замена строк или глобальное отключение предупреждений не выполнялись: такая правка могла бы поменять смысл встроенных скриптов.

Официальное пояснение Python: https://docs.python.org/3.13/library/functions.html#exec

## 3. CHECK_STARTUP — отдельная проверка регистрации

`CHECK_ENV` по-прежнему проверяет импорты зависимостей и **не доказывает**, что сервер зарегистрирует свои сервисы. Для следующего уровня добавлен **`CHECK_STARTUP.bat`**.

Он выполняет обычные FirstRunInit и создание CherryPyStartup, подключает native mount, проверяет реальные `default/Api`, `default/XMLRPC`, `default/UploadServer` и настройки XML-RPC. HTTP-слушатель не запускается; периодический scheduler конструктора останавливается перед выходом. Результат: `.runtime/startup-check.json` в новом дереве.

**Это не read-only проверка БД:** исходная инициализация может выполнять свои штатные записи/действия, включая auto_upgrade при его включении в пользовательском config. Она не отключена ради диагностики. Команду запускать только при остановленном сервере; сохраняются проверка состояния managed SQLite и общий локальный lock.

Успешный CHECK_STARTUP — не проверка входа по HTTP, всех запросов браузера, PostgreSQL или пользовательских триггеров. При падении сохраняется обычный `.runtime/last-launch-error.txt`.

## 4. Аналогичный дефект в конфигурационных обработчиках

Добавлен `Common.resolve_class`: разрешение **доверенного серверного** class path через importlib без создания экземпляра только ради поиска default-handler. Сохраняется plugin loader и порядок коротких имён widget → command → web. Это не новый HTTP endpoint для произвольного вызова Python-классов.

В выделенном `WidgetConfig` / `WidgetConfigView` заменены парные `exec`/`eval`, использовавшиеся для `has_config`, default display/edit handler и default widget. В `EditCmd` так же исправлен выбор `get_default_action`: пропавший импорт не должен незаметно приводить к стандартному DatabaseAction вместо исходного action.

Приоритеты XML/DB-слоёв, порядок полей и lookup опций не переписывались. **80 штатных XML, 487 views, 11 370 сравнений — ноль расхождений в проверенной области.** Это сравнение метаданных, не гарантия полного переноса поведения каждого виджета.

Дополнительно исправлена ошибка сохранения визуального view designer: в `ViewService.view_operation(PATCH)` находился посторонний фрагмент с неопределённым `opts`. Удалён именно ошибочный фрагмент. Правильная обработка опций внутри отдельного `saved_view` сохранена. Новый тест исполняет настоящий путь сохранения view и проверяет другие views, неизвестные атрибуты, ревизию и персональные права.

## 5. Следующий UI: оригинальный редактор сохранённых скриптов

Штатная ссылка **Script Editor** из админки (`tactic.ui.app.ShelfEditWdg`) теперь открывает нативный `ScriptEditor.vue`. Поддержаны также `ScriptEditorWdg` и полные пути `shelf_wdg.*`. Сам пункт меню не зашит во Vue: он приходит из исходной конфигурации и разрешается по handler/options.

### Хранилище и права

Остаётся **`config/custom_script`**, а не файлы на диске и не новая таблица. Папка/название — виртуальный путь записи TACTIC. Чтение и сохранение каждый раз проверяют исходное `builtin/view_script_editor`, текущий проект и разрешённый конфигурацией target. Прямой доступ к таблице/записи также проверяет это право. Обычный generic edit не обходит специальный путь редактора.

Сохранение повторяет границу исходного `shelf_wdg.save_script_cbk`: **`TacticServerStub.insert` / `update`** внутри прежней серверной транзакции. Непосредственного SQL UPDATE из Vue нет. Пустая папка становится `default`, ведущие `/` названия удаляются как в исходнике. Пробелы, переносы строк, Unicode и код скрипта не переформатируются.

Существующие server triggers/workflow могут использовать этот код после сохранения. Поэтому отсутствие кнопки Run **не делает редактирование произвольного кода безопасным для production**: разрешение оставлено административным, запись по умолчанию выключена.

### Возможности

Каталог со страницами по 40 (API до 100), поиск по папке/названию с буквальным `%`/`_`, фильтр папки, группировка загруженной страницы по папкам. Количество показывает общую серверную выборку; каталог не скачивает все тела скриптов. Поддержано открытие первоначального `script_path` / `search_key` из конфигурации.

Создание, загрузка, изменение, создание копии, описание, выбор исходных языков `javascript/server_js/python/expression/xml`. Код редактируется как текст с переносом строк, табуляцией, счётчиком строки/столбца, поиском следующего совпадения. Есть Ctrl+S, контроль несохранённых изменений, подтверждение отмены, экспорт текущего текста в локальный файл.

Ревизия проверяется перед update. Конфликт не стирает набранный текст. Дубликат folder/title не перезаписывается автоматически; копии нужно отдельное название. Неизвестный существующий язык можно сохранить неизменным, а создавать новые записи с произвольным языком нельзя.

Кнопка «Таблица по конфигурации» воспроизводит исходную Manage-ветку: настоящий view `config/custom_script/table`, `element_names=folder,title,description,language`, `show_shelf=false`, через существующую конфигурационную таблицу. Не отдельный захардкоженный список полей вместо всего TACTIC.

### Проверка синтаксиса и границы

Python проверяется **AST-разбором без исполнения**; XML — ограниченным XML-parser без внешних сущностей. Ошибки показываются, но сохранение синтаксически незавершённого текста допустимо, как в исходном редакторе. Корректный синтаксис не доказывает наличие импортов, правильность имён или безопасность workflow.

Для JavaScript, server_js и expression возвращается явное «проверка не реализована», а не выдуманное «валидно». HTML/JS из тела скрипта не рендерится и не исполняется в браузере. В production нет нового универсального Run/Test/eval endpoint.

**Run/debugger, diff истории, полноценная подсветка Ace, выполнение server_js/expression и custom панели редактора пока не перенесены.** Лимит тела скрипта — 256 КиБ UTF-8; большой существующий скрипт не обрезается и не перезаписывается. Группы папок относятся к текущей странице каталога. Межпроцессная уникальность folder/title против параллельных legacy-клиентов не гарантируется новой проверкой и не обеспечивается скрытым DDL.

## 7. Окружение, данные и дальнейшие пределы

`SETUP_ENV.bat`, pip URL, runtime-manifest и зависимости **не изменялись**: пользователь сообщил, что эти этапы прошли. Заново скачивание окружения не проверялось. Остаются существующие CHECK_ENV, CHECK_LOCAL_DB, INIT/UPGRADE/RESTORE_LOCAL_SQLITE, START/LEGACY и BUILD_VUE. SETUP не устанавливает PostgreSQL-сервер.

Для совершенно новой managed SQLite по-прежнему нужны SETUP → INIT → UPGRADE → CHECK_LOCAL_DB. Это **не** инструкция повторять инициализацию для уже обновлённой базы. Историческое описание безопасной миграции 0.8 сохранено в `docs/native-ui/0.8/README_REFERENCE_RU.md`.

Вход native UI **admin-only**, `src/tactic/ui_api/config.json`:

```json
{"site":"", "allow_writes":false, "allow_uploads":false}
```

Разрешать запись только после проверки тестовой установки. Это касается и изменения скриптов/view designer. Включение uploads отдельно от writes. Никакие флаги не включены ради скриншота в production-конфигурации.

Сохранены прежние таблицы, формы, sidebar, поиск, задачи, work hours, схемы/pipeline, коллекции, сообщения, уведомления, timeline, файлы и загрузки. Полные custom layouts/expressions/widgets, части workflow/review/плагинной/лицензионной админки, ресурсное планирование, расширенный check-in и полный headless bootstrap ещё не закрыты. **Старые UI-каталоги не удалять.** Ограничения multiworker/multisite и работы обычных ролей не объявляются снятыми.

`START_LEGACY.bat` / `TACTIC_UI=legacy` возвращает прежний рендерер, но использует общие исправленные классы. Это не откат записанных данных. Откат исходников — из 0.8, данных — из резервной копии.

Архив содержит полный source fork, готовую сборку, source map, патч/хеши и тесты. Не содержит `.runtime`, кешей/pyc, рабочих пользовательских БД/паролей, внешних тестовых зависимостей и файлов шрифтов. Оригинальные seed-базы не изменены.
